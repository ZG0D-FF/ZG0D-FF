Module 1: Relational Joins & Key Matching

1 Problem • Foreign Key Constraints • Hash vs Nested-Loop Join
PROBLEM 01

African Cities

Source: african-cities-English.pdf • Matching Keys: CITY.CountryCode = COUNTRY.Code

Curriculum Problem Statement:

Given the CITY and COUNTRY tables, query the names of all cities where the CONTINENT is 'Africa'.

Note: CITY.CountryCode and COUNTRY.Code are matching key columns.
Canonical SQL Queries: Relational Algebra: $\pi_{\text{CITY.NAME}}(\sigma_{\text{CONTINENT}='Africa'}(\text{CITY} \bowtie_{\text{CountryCode}=\text{Code}} \text{COUNTRY}))$ 
-- ANSI SQL:1992 Standard INNER JOIN (Recommended Industry Standard)
SELECT c.NAME
FROM CITY c
INNER JOIN COUNTRY co 
    ON c.CountryCode = co.Code
WHERE co.CONTINENT = 'Africa';

-- Alternative: Implicit Comma Join (Valid logically, but prone to cartesian product errors)
SELECT CITY.NAME
FROM CITY, COUNTRY
WHERE CITY.CountryCode = COUNTRY.Code 
  AND COUNTRY.CONTINENT = 'Africa';
💡 Lucid Understanding: Physical Join Mechanics & Cost Analysis

1. Why Explicit INNER JOIN Beats Implicit Comma Join: While both produce identical result sets logically, an explicit INNER JOIN ... ON ... syntactically separates the relational integrity linking condition from the tuple filtering predicate (WHERE). Omitting the join predicate in comma notation creates an unintentional Cartesian Product ($|R| \times |S|$ rows) that exhausts buffer pools on large tables.

2. Optimizer Join Algorithms: Depending on table statistics and indexes:

  • Nested Loop Join: Optimal when COUNTRY.Code has a unique B-Tree index and the filtered outer table has few rows. Cost: $\mathcal{O}(M \cdot \log N)$.
  • Hash Join: Optimal for large unindexed joins. Builds an in-memory hash table on COUNTRY (CONTINENT='Africa'), then probes with CITY. Cost: $\mathcal{O}(M + N)$.
  • Sort-Merge Join: Optimal when both relations are pre-sorted on the join key. Cost: $\mathcal{O}(M \log M + N \log N)$.

Exam Trap (Ambiguous Column Reference): If you write SELECT NAME without specifying CITY.NAME or an alias c.NAME, the query will crash with an ORA-00918: column ambiguously defined error because both CITY and COUNTRY contain a column named NAME!

PROBLEM 02

Japanese Cities' Names

Source: japanese-cities-name-English.pdf • Filter: COUNTRYCODE = 'JPN'

Query the names of all the Japanese cities in the CITY table. The COUNTRYCODE for Japan is 'JPN'. 
SELECT NAME
FROM CITY
WHERE COUNTRYCODE = 'JPN';
💡 Lucid Understanding: Projection Pruning & String SARGability

1. Selective Projection Pruning: By selecting NAME instead of *, the database engine avoids reading unneeded columns from the storage blocks. If a composite index on (COUNTRYCODE, NAME) exists, the engine performs an Index-Only Scan (Covering Index) with 0 table heap lookups.

2. SARGable Predicates: WHERE COUNTRYCODE = 'JPN' is Search Argument Able (SARGable). Wrapping the column in functions (e.g. WHERE UPPER(COUNTRYCODE) = 'JPN') invalidates standard B-Tree indexing, forcing a full table scan $\mathcal{O}(N)$.

PROBLEM 03

Revising the Select Query I

Source: revising-the-select-query-English.pdf • Predicate: COUNTRYCODE = 'USA' AND POPULATION > 100000

Query all columns for all American cities in the CITY table with populations larger than 100,000. The CountryCode for America is 'USA'. 
SELECT *
FROM CITY
WHERE COUNTRYCODE = 'USA' 
  AND POPULATION > 100000;
Exam Trap (Strict Inequality & Numeric Commas): Never write POPULATION > 100,000. In SQL, commas in numeric literals cause a syntax error (interpreted as an illegal expression separator). Always write pure digits: 100000. Furthermore, the problem states larger than, which requires strict inequality >, not >=.

PROBLEM 07

Weather Observation Station 3

Source: weather-observation-station-3-English.pdf • Filter: EVEN ID & DISTINCT CITY

Query a list of CITY names from STATION for cities that have an even ID number. Print the results in any order, but exclude duplicates from the answer. 
-- Universal ANSI / Oracle / PostgreSQL / MySQL Standard Syntax
SELECT DISTINCT CITY
FROM STATION
WHERE MOD(ID, 2) = 0;

-- Dialect Operator Alternative (MySQL / SQLite / SQL Server % operator)
SELECT DISTINCT CITY
FROM STATION
WHERE ID % 2 = 0;
💡 Lucid Understanding: Physical Deduplication (Sort vs Hash Aggregate)

How DISTINCT Executes Under the Hood: Evaluating DISTINCT forces the database engine into one of two physical operators:

  • Sort Unique / Sort Deduplication: Sorts the projected attribute stream in $\mathcal{O}(N \log N)$, then scans linearly and discards adjacent duplicate values. If memory is tight, intermediate runs spill to disk temp tables.
  • Hash Aggregate (Hash Table): Creates an in-memory hash set of seen keys in $\mathcal{O}(N)$ average time. Faster than sorting, but memory consumption scales with the number of unique city names.

Module 4: Aggregations & Group Operations

1 Problem • COUNT(*) vs COUNT(column) • NULL Semantics
PROBLEM 08

Revising Aggregations - The Count Function

Source: revising-aggregations-the-count-function-English.pdf • Filter: POPULATION > 100000

Query a count of the number of cities in CITY having a Population larger than 100,000. 
-- Canonical Aggregation Query
SELECT COUNT(*)
FROM CITY
WHERE POPULATION > 100000;
💡 Lucid Understanding: Deep Dive on COUNT(*), COUNT(col), and NULLs
COUNT(*)
Counts every qualifying tuple, regardless of whether individual columns contain NULL. Allows covering index scans.
COUNT(column)
Counts ONLY rows where column IS NOT NULL. If a row has NULL in that attribute, count is skipped.
COUNT(DISTINCT col)
Counts unique non-null values. Requires sort or hash dedup buffer before returning scalar count.

Execution Order Insight: WHERE executes before aggregation. Hence, rows with POPULATION ≤ 100000 are filtered out before reaching the aggregate accumulator. If the question required grouping by district, you would use GROUP BY DISTRICT HAVING COUNT(*) > 5.

PROBLEM 09

Higher Than 75 Marks

Source: more-than-75-marks-English.pdf • Slicing: RIGHT(Name, 3) ASC, ID ASC

Query the Name of any student in STUDENTS who scored higher than 75 Marks. Order your output by the last three characters of each name. If two or more students both have names ending in the same last three characters (e.g., Bobby, Robby), secondary sort them by ascending ID.

Sample Input (STUDENTS): Samantha (75) excluded
IDNameMarks
1Ashley81
2Samantha75
4Julia76
3Belvet84
Sample Output:
Ashley ['ley']
Julia ['lia']
Belvet ['vet']

Explanation: Marks > 75 filters to Ashley, Julia, Belvet. Last 3 chars: 'ley' < 'lia' < 'vet' ('e' < 'i' < 'v').

Multi-Dialect Solutions:
MySQL & MS SQL Server:
SELECT Name
FROM STUDENTS
WHERE Marks > 75
ORDER BY 
    RIGHT(Name, 3) ASC, 
    ID ASC;
Oracle 19c & PostgreSQL:
SELECT Name
FROM STUDENTS
WHERE Marks > 75
ORDER BY 
    SUBSTR(Name, -3) ASC, 
    ID ASC;
💡 Lucid Understanding: Deterministic Tie-Breaking & Expression Indexes

1. Why Secondary ID Ordering is Mandatory: Without ID ASC as the secondary tie-breaker, two names ending in the same suffix (e.g. Bobby and Robby both ending in bby) produce non-deterministic sort order. Relational engines do not guarantee arrival order. Adding unique primary key ID guarantees mathematical determinism across parallel execution threads.

2. Performance (Function-Based Indexes): Standard B-Tree indexes on Name cannot accelerate RIGHT(Name, 3) because the comparison occurs on a transformed expression. To avoid an $\mathcal{O}(N \log N)$ sort step on a billion-row table, one must create an expression-based index: CREATE INDEX idx_student_sub ON STUDENTS(SUBSTR(Name, -3), ID);

PROBLEM 10

Employee Names

Source: name-of-employees-English.pdf • Ordering: ORDER BY name ASC

Write a query that prints a list of employee names (i.e.: the name attribute) from the Employee table in alphabetical order. 
SELECT name
FROM Employee
ORDER BY name ASC;
Collation & Character Set Awareness: In production databases, alphabetical order is governed by the table's Collation (e.g. utf8mb4_general_ci vs utf8mb4_bin). Binary collations sort uppercase letters before lowercase (ASCII 'Z' = 90 < 'a' = 97). In Case-Insensitive collations (_ci), 'Angela' and 'angela' compare equally. HackerRank evaluates under standard case-insensitive ASCII ordering.

SQL Exam & Technical Interview Traps Vault

The most common pitfalls that trip up candidates on HackerRank and technical rounds.

Trap 1: WHERE vs. HAVING Placement

WHERE filters individual tuples prior to grouping and aggregation. HAVING filters aggregated groups after the grouping step. Never write WHERE COUNT(*) > 5; aggregate functions cannot appear in the WHERE clause.

Trap 2: COUNT(*) vs. COUNT(Column) on NULLs

If a table has 10 rows and 3 of them have NULL in column bonus, COUNT(*) returns 10, while COUNT(bonus) returns 7! In aggregate grading, using COUNT(col) when total row count is expected fails tests whenever optional nullable columns exist.

Trap 3: Strict Inequality vs Boundary Inclusion

Phrasing like "scored higher than 75" or "populations larger than 100,000" requires >. Writing >= will pull boundary records (like Samantha with Marks = 75 in Problem 9), causing zero test case score.

Trap 4: Non-Deterministic ORDER BY without Unique Key

When sorting on non-unique columns (e.g. RIGHT(Name, 3)), two records with identical keys can appear in arbitrary order. Always append the primary key (e.g. , ID ASC) to ensure consistent test results.
