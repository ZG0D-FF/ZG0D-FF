PROBLEM 01

African Cities

Source: african-cities-English.pdf • Matching Keys: CITY.CountryCode = COUNTRY.Code

Curriculum Problem Statement:

Given the CITY and COUNTRY tables, query the names of all cities where the CONTINENT is 'Africa'.

Canonical SQL Query: $\pi_{\text{c.NAME}}$($\sigma_{\text{co.CONTINENT}='Africa'}$(CITY $\bowtie_{\text{Key}}$ COUNTRY)) 
SELECT c.NAME
FROM CITY c
JOIN COUNTRY co ON c.CountryCode = co.Code
WHERE co.CONTINENT = 'Africa';
💡 Lucid Understanding: Explicit vs. Implicit Joins

An explicit JOIN ... ON cleanly separates the table linking integrity predicate from the business filter WHERE co.CONTINENT = 'Africa'. Implicit comma joins (FROM CITY, COUNTRY) are hazardous on large datasets because accidentally omitting a where-condition causes an uncontrolled Cartesian explosion ($|R| \times |S|$ rows).

PROBLEM 14

Average Population of Each Continent

Source: average-population-of-each-continent-English.pdf • Function: FLOOR(AVG())

Query the names of all the continents (COUNTRY.Continent) and their respective average city populations (CITY.Population) rounded down to the nearest integer.
Canonical SQL Query: $\gamma_{\text{Continent}, \text{FLOOR}(\text{AVG}(\text{Pop}))}$(CITY $\bowtie$ COUNTRY) 
SELECT 
    co.Continent, 
    FLOOR(AVG(c.Population))
FROM CITY c
JOIN COUNTRY co ON c.CountryCode = co.Code
GROUP BY co.Continent;
Exam Trap (FLOOR vs. ROUND): The problem specification strictly demands "rounded down to the nearest integer". Writing ROUND(AVG(c.Population)) will round 124.6 up to 125, failing the grader. You must use FLOOR() to truncate fractional decimals downward.

PROBLEM 15

The Report (Ketty's Grade Report)

Source: the-report-English.pdf • Join: Marks BETWEEN Min_Mark AND Max_Mark

Curriculum Problem Statement:

Generate a report containing three columns: Name, Grade and Mark.

  • Ketty doesn't want names of students who received a grade lower than 8 (print 'NULL' as their name).
  • Order by: Grade DESC (higher grades entered first).
  • If same grade (8–10): order those students alphabetically by Name ASC.
  • If grade < 8: order those students by Marks ASC.
Canonical SQL Solution (Cleanest ANSI Standard): $\tau_{\text{Grade}\downarrow, \text{Name}\uparrow, \text{Marks}\uparrow}$($\pi_{\dots}$(Students $\bowtie_{\text{Marks} \in [\text{Min}, \text{Max}]}$ Grades)) 
SELECT 
    CASE 
        WHEN g.Grade >= 8 THEN s.Name 
        ELSE NULL 
    END AS Name,
    g.Grade,
    s.Marks
FROM Students s
JOIN Grades g 
    ON s.Marks BETWEEN g.Min_Mark AND g.Max_Mark
ORDER BY 
    g.Grade DESC,
    s.Name ASC,
    s.Marks ASC;
💡 Lucid Understanding: Why Compound Sort Order Naturally Cascades

How the Triple ORDER BY Works Effortlessly: Notice that for students with Grade ≥ 8, s.Name is a distinct string, so s.Name ASC resolves all ties immediately without looking at s.Marks ASC. For students with Grade < 8, the projected name is NULL (or identical). Therefore, the s.Name sort key ties for all of them, causing the engine to naturally drop to the third sorting criterion: s.Marks ASC! You do not need complex conditional expressions inside the ORDER BY clause.

PROBLEM 16

Placements (Friends Salary Comparison)

Source: placements-English.pdf • Join: Students ⋈ Friends ⋈ sp(Packages) ⋈ fp(Packages)

Curriculum Problem Statement:

Write a query to output the names of those students whose best friends got offered a higher salary than them. Names must be ordered by the salary amount offered to the best friends. It is guaranteed that no two students got same salary offer.

Canonical SQL Solution (Self-Join Pattern): $\pi_{\text{s.Name}}$($\sigma_{\text{fp.Sal} > \text{sp.Sal}}$(Students $\bowtie$ Friends $\bowtie \rho_{\text{sp}}$(Pkg) $\bowtie \rho_{\text{fp}}$(Pkg))) 
SELECT s.Name
FROM Students s
JOIN Friends f ON s.ID = f.ID
JOIN Packages sp ON s.ID = sp.ID
JOIN Packages fp ON f.Friend_ID = fp.ID
WHERE fp.Salary > sp.Salary
ORDER BY fp.Salary ASC;

SQL Exam & Technical Interview Traps Vault

The most common pitfalls that trip up candidates on HackerRank and technical rounds.

Trap 1: WHERE vs. HAVING Placement

WHERE filters individual tuples prior to grouping and aggregation. HAVING filters aggregated groups after the grouping step. Never write WHERE COUNT(*) > 5; aggregate functions cannot appear in the WHERE clause.

Trap 2: COUNT(*) vs. COUNT(Column) on NULLs

If a table has 10 rows and 3 of them have NULL in column bonus, COUNT(*) returns 10, while COUNT(bonus) returns 7! In aggregate grading, using COUNT(col) when total row count is expected fails tests whenever optional nullable columns exist.

Trap 3: Strict Inequality vs Boundary Inclusion

Phrasing like "scored higher than 75" or "populations larger than 120,000" requires strict >. Writing >= pulls boundary records into the result, causing zero test case score.

Trap 4: Non-Deterministic ORDER BY without Unique Key

When sorting on non-unique columns, two records with identical keys can appear in arbitrary order across parallel threads. Always append a deterministic tie-breaker (e.g. , ID ASC or s.Marks ASC) to ensure consistent test grading.
