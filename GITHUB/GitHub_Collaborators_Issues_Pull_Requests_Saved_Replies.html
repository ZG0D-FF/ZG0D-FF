Assigning Collaborators, Starting with Issues, Pull Requests & Saved Replies

Practical GitHub Project Management and Collaboration • Understanding-first course notes

What these lessons are actually building

These lessons move from assigning project work to collaborators into the broader ways GitHub connects projects, issues, pull requests, repository access, and collaboration conversations.

Project item → Assignee → Repository access → Issue → Milestone → Project tracking → Collaboration

A second path begins outside Projects: an issue can be created directly in a repository and then added to a project. Pull requests provide another type of project item for proposed changes and review. Saved replies make recurring collaboration responses faster.

1. Adding a setup item in Table view

The instructor switches to the project's Table view and creates another item for updating the repository README file.

  • The item is assigned to the instructor.
  • Another person can also be added as an assignee.
  • Status is set to Todo.
  • A due date is added.
  • The item is assigned to Sprint 1.

Table view → Add item → Assign → Status → Due date → Sprint

2. Converting the project item into an issue

The README task is converted from a project item into an issue by selecting Convert to issue.

The instructor selects the previously created project/repository playground. After conversion, the item becomes issue #2.

Project item → Convert to issue → Select repository/project → Issue #2

Key idea: A project item can become a repository issue while remaining tracked in the project.

3. Project collaborators and repository collaborators are different

The instructor tries to assign the issue to Jojo. Although Jojo is already part of the project, she is not yet part of the repository.

Important: Being a collaborator on a project does not automatically make someone a collaborator on the repository that owns an issue.

The instructor goes to repository Settings → Collaborators, chooses Add people, finds Jojo, and sends her an invitation.

Project collaborator → Repository access required → Invite collaborator

4. A repository invitation must be accepted

After Jojo is invited to collaborate on the repository, she is not immediately available as an issue assignee. The instructor notes that she must first accept the invitation.

Once time has passed and the invitation is accepted, Jojo becomes available in the issue's Assignees list.

Invite → Email invitation → Accept → Available as assignee

5. Assigning multiple people to an issue

After Jojo accepts the invitation, the instructor assigns her to the README issue alongside the instructor.

The issue can therefore have two assignees working together on the same task.

The project automatically reflects both assignees for the item.

Collaboration model: Repository access enables the person to participate in repository-owned issue work, while the project continues tracking the task.

6. Milestones can track related issue work

The instructor adds the setup milestone to the README issue because the task is part of the setup work.

When more than one milestone is represented in the repository and one has been completed, the milestone progress can show partial completion. In the demonstration, the setup milestone reaches 50% complete.

Related issues → Milestone → Completed issues → Progress percentage

7. Project fields remain synchronized

Back in the project, the README task shows both assignees automatically.

  • Assignees are reflected in the project.
  • The item remains associated with Sprint 1 initially.
  • The due date can be changed from the project.
  • The item continues to exist as an issue while being tracked in Projects.

The instructor later moves the due date to Friday of the following week and associates that work with the second sprint because the demonstrated dates span May 23 to May 29.

8. Starting a conversation with a collaborator

The instructor adds a start date and begins a conversation with Jojo about improving the README.

GitHub supports direct references inside comments:

@ mentionUse the @ sign to refer to an individual such as Jojo.
# referenceUse the # sign to refer to an issue by its number.

@ → Person reference    # → Issue reference

The instructor can also use the mention button to select a person from the available dropdown.

9. Why mentions matter for collaboration

When Jojo is mentioned in a comment, GitHub can notify her through its notification system. Depending on her GitHub settings, this may also result in an email.

The instructor presents mentions as a practical way to make collaborators aware of project activity and tasks that need attention.

Collaboration pattern: Assign the work → mention the collaborator → continue the conversation in the issue.

10. Creating an issue directly instead of starting in Projects

Projects do not have to be the starting point. An issue can be created directly from the repository's Issues section and added to a project later.

The instructor creates an issue titled Add a license to project.

Repository → Issues → New issue → Configure issue → Add to project

11. Configuring the new license issue

The instructor configures the issue with the people and project information needed for tracking.

  • Assigns the issue to the instructor and Jojo.
  • Selects the GitHub Projects project.
  • Uses the setup milestone.

Once it is added to the project, the repository issue becomes an item that can be tracked alongside the other project work.

12. Issue #3 appears in the project

The newly created license issue becomes issue #3.

The instructor changes its project Status to In Progress because work has started.

The project item appears without requiring a manual page refresh in the demonstration.

Create issue #3 → Add to project → Set In Progress → Appears in project

13. Issues and Projects can expose different fields

The instructor points out that some project information may need to be managed from the Projects interface rather than directly from the issue.

For the license task, the instructor sets:

  • Iteration: Sprint 1
  • Due date: Tomorrow
  • Status: In Progress
Practical point: You may move between the issue and project interfaces because they expose different fields and controls.

14. Resolving the license task through collaboration

Jojo replies to the issue and recommends using an MIT license.

The instructor then goes to the repository's code area and creates a new file named license.

GitHub provides template help for certain repository tasks, including licenses.

Issue conversation → Recommendation → Repository → Create license file

15. Choosing and committing the MIT license

The instructor selects the MIT license template. GitHub provides information about different licenses and allows the author's name and year to be added.

The prepared license is then committed as a new file to the main branch.

License template → MIT → Name/year → Review → Commit changes

After the commit, the license file appears in the repository code.

16. Closing the completed issue

Once the license file has been added, the instructor returns to the issue, thanks Jojo in a comment, and closes the issue because the task is complete.

The project automatically reflects the issue's closed state.

Complete repository work → Comment → Close issue → Project updates

17. Synchronization between Issues and Projects

The instructor emphasizes that changes made through Issues and changes represented in Projects are synchronized automatically.

IssueTracks repository work and collaboration.
ProjectTracks planning fields such as status, sprint, assignees, and dates.
RepositoryContains the actual code and files being changed.

Issue ↔ Project ↔ Repository

This synchronization allows a task to be worked on through the issue while remaining visible in the project.

18. Pull requests as another project item

A pull request is another way to work with project items. It communicates that a change is being proposed and may need another person's review.

The instructor demonstrates this by creating a .gitignore file and proposing the change through a new branch.

Code change → New branch → Propose changes → Pull request → Review

19. Creating the .gitignore pull request

The instructor creates .gitignore and notices that GitHub offers templates. Because the project is a web project and no suitable template is selected, the file is left blank initially.

The changes are committed to a new branch named add gitignore, and the instructor chooses Propose changes.

20. Configuring the pull request for collaboration

The new pull request can be configured with project and collaboration information.

  • Add another person as a reviewer.
  • Add the pull request to a project.
  • Associate it with the setup milestone.
  • Set its project Status to In Progress.
  • Assign the work to the instructor and Jojo.

Pull request → Reviewer → Project → Milestone → Status → Assignees

21. Review feedback changes the work

After Jojo reviews the pull request, she suggests three additional definitions for the .gitignore file.

The instructor can use that feedback as the next step in completing the proposed change.

Review loop: Propose change → Request review → Receive feedback → Modify code → Push changes

22. Using Codespaces to modify the pull request

The instructor opens a Codespace on the add gitignore branch to make the requested modifications.

The Codespace provides an editor similar to Visual Studio Code and allows the instructor to edit the .gitignore file directly.

The instructor notes that the changes could also have been made through the regular GitHub interface, but Codespaces provides a convenient environment for more involved changes.

23. Commit and synchronize Codespace changes

After editing the file, the instructor uses Source Control to commit the changes.

  • Add a commit message describing the modification.
  • Commit the changes.
  • Sync the changes so they are pushed to the repository.
  • Close the Codespace.

Edit → Commit → Sync/push → Pull request updated

24. Pull requests are separate from Issues

Important: The instructor explicitly points out that the pull request should be viewed from the Pull requests section, not the Issues section.

The pull request remains a pull request while it is being reviewed and modified. After the requested changes are complete, the instructor merges it and confirms the merge.

25. Merging the pull request completes the project item

After the pull request is successfully merged and closed, the corresponding project item is marked Done.

The .gitignore file in the repository now contains the changes made during the review process.

The instructor then adds the remaining project tracking details, including a due date and Sprint 1.

Merge pull request → Pull request closes → Project item becomes Done

26. Pull requests can be tracked like project work

The lesson demonstrates that a project item does not have to originate from an issue.

A completed project item can instead represent a pull request, with project fields such as Status, Due date, Iteration, and Assignees used to track it.

Issue-based itemRepository issue tracked in Projects.
Pull-request-based itemProposed code change tracked in Projects.
Shared trackingBoth can carry project-management information.

28. Saved replies speed up recurring responses

GitHub also provides saved replies for frequently used responses to issues and other comments.

From a comment's writing menu, the instructor opens the saved-reply option and can select an existing response.

Comment box → Saved replies menu → Select reusable response

29. Creating a new saved reply

The saved-reply interface also provides an option to create a new saved reply. The instructor demonstrates creating one called Ship It.

The response contains a short team message and an emoji entered using colon-based search.

A preview is available before saving the reply.

Create saved reply → Name → Write response → Preview → Save

30. Managing saved replies from Settings

Saved replies can also be managed through the user's profile settings.

The demonstrated navigation is:

Profile icon → Settings → Saved replies

From there, saved replies can be created, viewed, and edited.

31. Saved replies are available across repositories

Once a saved reply is configured, it can be selected from comment sections in the repositories available to the user.

This provides a reusable response mechanism rather than requiring the same message to be typed repeatedly.

Practical benefit: Saved replies reduce repetitive typing while keeping common collaboration responses readily available.

34. Important synchronization relationships

The demonstrations show several connected relationships:

  • An issue created directly in a repository can later become a project item.
  • A project item can be converted into a repository issue.
  • Project assignees reflect issue information.
  • Closing an issue can update the project's Status.
  • Closing a pull request can update the project's Status.
  • Milestone completion reflects the state of associated issues.
  • Repository code changes can be performed through the normal interface or a Codespace.

Repository activity ↔ Issues / Pull requests ↔ Project tracking

37. What you should remember

The strongest mental model from these lessons is:

People need access → Work is assigned → Issues track tasks → Pull requests propose changes → Projects organize the work → GitHub synchronizes the state

Project collaboration involves more than assigning an item. Repository permissions determine who can participate in repository-owned work. Issues provide a place for tasks and conversation, while pull requests provide a workflow for proposing and reviewing code changes.

The project remains a shared tracking layer: issue and pull-request activity can be reflected through project fields such as Status, Assignees, Iteration, and Due date.

Finally, GitHub's collaboration features extend into communication itself. @ mentions notify people, # references connect conversations to issues, and saved replies make recurring responses reusable.

Lesson connection

These lessons build on the earlier project settings, fields, views, and issue-conversion concepts. After learning how project items connect to repositories, the next layer is collaborative work: assigning people, handling repository access, creating issues from the repository, tracking milestones, working with pull requests and reviewers, using Codespaces for changes, and streamlining repeated comments with saved replies.

The result is a connected workflow in which people, repository work, project tracking, code changes, review, and communication can all participate in the same GitHub collaboration process.
