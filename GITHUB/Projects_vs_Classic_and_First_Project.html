Projects vs. Classic Projects & Starting Your First Project

Practical GitHub Project Management and Collaboration • Understanding-first course notes

What these lessons are actually teaching

These lessons introduce GitHub Projects from two angles: understanding the difference between the newer Projects experience and Classic Projects, then creating and configuring a first project.

Classic Projects → understand the legacy model → New Projects → create a project → configure views → add and manage items

The main idea is that GitHub Projects provides different ways to organize work, while the newer experience makes projects organizational-level resources that can be viewed through tables, boards, and roadmaps.

1. GitHub has two Projects experiences

The instructor explains that there are two versions of GitHub Projects:

  • New GitHub Projects Experience — this is where new projects are created.
  • Classic Projects Experience — an older project model that you may still encounter in an existing repository or organization.
Important: According to the lesson, you cannot simply create a new Classic Project from scratch. A new Classic Project can be created only when an organization already has at least one existing Classic Project.

2. What makes Classic Projects different?

Classic Projects are built around a board-style collection of work. The instructor describes them as being made up of:

IssuesWork items from GitHub repositories.
Pull requestsCode changes that can be tracked on the project board.
NotesFree-form items that can be placed on the board.

They are similar to the board experience in New Projects, where cards can be moved between columns representing different statuses.

3. Repository-level vs. organization-level projects

One of the major differences is where the project lives.

Classic Projects New Projects
A project can be added at the repository level. Projects are created at the organizational level.
The project is associated with the repository where it was created. A project can be attached to any of the relevant repositories.
Finding projects may require looking through individual repositories. The organization-level model makes projects easier to find in one place.

Classic: Repository → Project

New: Organization → Project → Repositories

4. Migrating a Classic Project

If you encounter a repository that still has a Classic Project, the lesson says the project is marked with (Classic).

When the Classic Project is opened, GitHub provides an option at the top to migrate it to the New Projects Experience.

Classic Project → Open project → Migrate → New Projects Experience

5. What a Classic Project looks like

The instructor demonstrates a repository's Projects tab and points out a section labeled Projects (Classic).

Because an existing Classic Project is present, the interface also allows another Classic Project to be created. Without an existing Classic Project in the organization, that creation option would not be available according to the lesson.

Opening the project shows a familiar board-style interface:

  • Cards represent work.
  • Cards can be dragged between columns.
  • Columns represent status or stages.
  • Additional columns can be added.
  • The project can be migrated to the New Projects Experience.

6. What a New Project looks like

The instructor then switches to a New Project from the profile-level Projects area rather than entering through a specific repository.

The default view shown is a Table View. The project can also have a Board View.

The Board View resembles the older Classic board experience:

  • Items can be moved around.
  • New items can be added.
  • The board provides a visual way to manage work.

The instructor describes this as a simplified board-style experience compared with the other available New Projects views, such as Tables and Roadmaps.

7. The three main New Projects views

Table A spreadsheet-like view using rows and columns. Useful for working with project data in a structured list.
Board A Kanban-style view where work items can be moved between status columns.
Roadmap A timeline-oriented project management view that visualizes work over time.

A key point from the lesson is that you do not have to permanently commit to the first view you choose. The instructor explains that you can move between different views later.

One project → multiple views → different ways of seeing the same work

8. Creating your first project

The instructor recommends following along with your own GitHub account and creating a project yourself.

Projects live in a dedicated Projects section and can also be associated with a specific repository.

The basic creation flow is:

Projects → New project → Choose a view → Name project → Create

For the demonstration, the instructor starts with the classic table-style view and names the project Github Projects.

9. Naming and organizing views

After creating the project, the instructor renames the initial view to identify it as the table view.

The exact name is flexible. It could instead be called something like an overview, depending on how the project is organized.

Mental model: The project is the overall workspace; views are different ways of looking at the information inside that workspace.

10. Project settings and documentation

The project interface provides access to settings and documentation areas.

  • You can edit the project's name.
  • You can add a short description.
  • You can create a more detailed README.
  • Markdown can be used in the documentation area.
  • Files such as images or videos can be added through the interface.
  • You can make a copy of an existing project.

This makes an existing project useful as the starting point for another project or as a reusable template.

11. Visibility, closing, and deleting a project

Visibility

The instructor explains that projects are commonly private, but a project can also be made public, particularly in an open-source context.

Close

Closing a project disables its workflows and removes it from the normal project list.

Delete

Deleting the project completely removes it, so the instructor emphasizes that this should only be done when you really intend to delete it.

Important distinction: Closing and deleting are not the same operation. Closing removes the project from normal use, while deleting completely deletes the project.

12. GitHub's “no Save button” behavior

One useful interface concept from the lesson is that GitHub generally does not use a traditional Save button.

When you type or modify an element, the change is made directly.

Edit → Change is applied

This is different from applications where you must explicitly click Save after making changes.

13. Project insights and quick access

The project interface includes several additional controls.

  • Insights — provides project analytics; there may be little or nothing to display before the project contains meaningful data.
  • Quick access side panel — provides convenient access to the project description and README.
  • Project menu — provides navigation to different areas of the Projects experience.
  • Archived items — lets you view items that have been archived and therefore are no longer displayed in the normal list.
  • Documentation and feedback links — provide access to supporting resources and information about what is new.

14. A project can have multiple views

You can create as many views as you need for a project.

Each view can present the same underlying project information differently.

For a view, the lesson demonstrates options for:

  • Changing the layout.
  • Grouping items.
  • Sorting items.
  • Generating charts.
  • Duplicating the current view.
  • Filtering the displayed items.

Same project data → different configurations → different saved views

15. Filtering and saving useful views

The filter control provides a quick way to narrow down the items shown in a view.

If the project contains many items, filtering can help isolate exactly the information you want to work with.

Once a useful filter has been configured, the resulting view can be saved.

For example, the instructor describes creating a view that shows only items matching a particular term such as pull request.

Why this matters: Multiple saved views let different people or workflows see the same project through the information that matters to them.

16. Adding items to a project

The project provides a place to add additional items.

Items can be connected to a specific repository, but the instructor also introduces draft items.

Draft items are useful for brainstorming ideas before they necessarily correspond to a repository issue or another existing GitHub item.

Project → Add item → Repository item or Draft item

17. Creating the first draft item

The instructor creates a task called Create a Repository for the project.

The item can be created by clicking and typing, rather than relying only on the keyboard shortcut.

The lesson mentions Control + Space as a shortcut, while noting that the same key combination may conflict with another function on a Mac.

18. Assigning the item and setting its status

After creating the draft task, the instructor assigns it to themselves.

A status can then be selected. The demonstrated statuses include:

TodoWork that has not started yet.
In ProgressWork that is currently being done.
DoneWork that has been completed.

Additional statuses can also be added.

Create item → Assign item → Set status

20. Classic vs. New Projects: the core comparison

Concept Classic Projects New Projects
Availability Existing legacy projects may still be encountered. New projects use the New Projects Experience.
Location Can be created at repository level. Created at organizational level and can be attached to repositories.
Board experience Board with cards and columns. Board is one of several available views.
Views The lesson focuses on the board-style experience. Table, Board, Roadmap, and additional configurable/saved views.
Migration Can be migrated from Classic to New Projects. Destination for migrated Classic projects.

  1. GitHub has both a New Projects Experience and a Classic Projects Experience.
  2. New projects are created with the New Projects Experience.
  3. According to the lesson, a new Classic Project can be created only when an organization already has an existing Classic Project.
  4. Classic Projects are made up of issues, pull requests, and notes arranged in a board-style experience.
  5. Classic Projects can exist at the repository level.
  6. New Projects are created at the organizational level and can be associated with repositories.
  7. A Classic Project can be migrated to the New Projects Experience.
  8. New Projects can use Table, Board, and Roadmap views.
  9. A project can contain multiple saved views.
  10. Views can be configured using grouping, sorting, filtering, charts, and duplication.
  11. Project items can be repository-linked or draft items.
  12. Items can have assignees and statuses such as Todo, In Progress, and Done.

23. What you should remember

The most useful mental model from these lessons is:

Project = workspace → Views = ways to see the workspace → Items = work being managed

Classic Projects represent the older repository-oriented board model. New Projects move the project itself to an organizational context and provide multiple ways to visualize and manipulate the same project information.

Once a project exists, the workflow becomes less about creating another project for every perspective and more about creating useful views of the same project.
