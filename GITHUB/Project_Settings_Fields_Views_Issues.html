Project Settings and Fields, View Categories & Converting Drafts to Issues

Practical GitHub Project Management and Collaboration • Understanding-first course notes

What these lessons are actually building

These lessons move from basic project creation into the configuration and data model that make GitHub Projects useful for real work.

Project settings → Access → Custom fields → Views → Dates & iterations → Repository issues → Milestones → Automatic synchronization

The central idea is that a GitHub Project is not just a board. It is a shared workspace whose items can carry structured fields, appear in multiple views, and connect directly to repository issues.

1. Opening Project Settings

Project settings are reached from the project's hamburger menu.

  • Project name
  • Description
  • README
  • Project-management actions such as closing or deleting the project

The same settings area also contains project access controls and custom-field management.

Project → Hamburger menu → Settings

2. Managing access to a project

A project can be shared with other people so they can contribute to the project.

The instructor demonstrates searching for a person, inviting them, and selecting the level of access they should receive.

Read accessAllows someone to read the project.
Write accessProvides the ability to contribute to the project.
Collaborator managementThe instructor notes that the highest level can allow adding new collaborators to the project.

People can also be removed, and search is useful when a project has many collaborators.

3. Project access is not automatically repository access

Important: The transcript explicitly distinguishes project access from repository permissions.

When a project is associated with a repository, the relevant person may also need permission to access that repository.

The instructor says repository permissions will be examined later when a repository is added to the project.

Project permissions ≠ Repository permissions

4. The default Status field

GitHub automatically adds a Status field to the project.

TodoWork that has not started.
In ProgressWork currently being performed.
DoneWork that has been completed.

The instructor describes Status as a special field that is automatically used as work moves through the project.

5. Adding a custom Status option

The instructor adds a new Status option called Backlog, described as a useful place for brainstorming items.

The option can be dragged to another position. The instructor moves Backlog to the top.

  • Edit the option through the pencil icon.
  • Change its color.
  • Add descriptive text.
  • Save the changes.

Add option → Name it → Reorder → Edit → Save

6. Projects can have multiple custom fields

Projects can contain multiple fields for managing tasks. The lesson introduces these field types:

TextFree-form text, such as a URL or email address.
DateStores a date associated with an item.
Single selectProvides a controlled list of manually defined options.
IterationRepresents recurring periods of work.

7. Creating a Due Date field

The instructor creates a field named Due and chooses Date as its type.

New field → Due → Date → Save

8. Understanding Single Select fields

A Single select field lets you define available choices manually. The existing Status field is presented as an example.

9. Iteration fields

An Iteration field represents recurring periods of work. The instructor uses sprints as the example and demonstrates a weekly schedule.

Iteration field → Start date → Duration → Repeating time periods

10. Configuring iterations

  • Add another iteration.
  • Delete an iteration.
  • Change the starting day.
  • Change duration.
  • Rename iterations.
  • Manually change dates using the date picker.

The instructor notes that the current timeframe advances automatically as the schedule progresses.

11. Creating different views of the same project

The existing Table view displays project information in a spreadsheet-like format. A new Board view is then created.

One project → Table view + Board view + Roadmap view

These are different presentations of the same underlying project data, not separate projects.

12. Board view and drag-and-drop

The Board view organizes tasks according to their status. The instructor moves a task from Todo to In Progress, or to Backlog, by dragging it.

When returning to Table view, the Status field has automatically changed to match the item's new position.

Mental model: Board movement changes the underlying Status value, so other views reflect the same change.

13. Naming and duplicating views

The instructor names the Board view Board, while noting that Kanban is another possible descriptive name.

Views can also be duplicated to create another version based on an existing configuration.

Existing view → Duplicate → Configure the copy

14. Opening an item's detailed information

From a view, an item can be opened to access its description and other fields. The instructor demonstrates changing Status, assigning a Due date, and selecting an Iteration.

Those same field values are then visible in the Table view.

15. Creating a Roadmap view

The Roadmap is a timeline-oriented view. The lesson explains that it requires at least one date or iteration field.

The demonstration uses Due as the target date and creates a separate Start field of type Date for the beginning date.

Start field → Beginning date

Due field → Target date

16. Roadmap display controls

  • Truncate fields shortens long field names.
  • Date fields can be shown or hidden.
  • Markers can identify milestones, due dates, sprints, and start dates.
  • Navigation arrows move through the timeline.
  • Today returns to the current date.
  • Zoom changes the timeline scale, such as quarter or month.
  • Sorting is available.

17. View changes and the blue-dot indicator

A small blue dot appears when a view has been modified. It indicates that the current view configuration has changed and can be saved.

After clicking Save, the dot disappears and the new configuration becomes the default appearance.

Modify view → Blue dot → Save → New default configuration

18. The most important view concept

Table, Board, and Roadmap views are different ways of presenting the same project.

A field changed in one view is reflected in the other views because they use the same underlying project data.

Shared project data → Multiple views → One change → Reflected everywhere

19. Draft items vs. issues

Draft items are useful for brainstorming, but the instructor describes issues as being at the heart of Projects.

A GitHub Issue tracks work on GitHub. Projects are not required to use Issues, but Issues can have a special relationship with Projects.

20. An issue always belongs to a repository

Key relationship: A GitHub Issue belongs to a repository.

For the demonstration, the instructor creates a repository called GitHub Projects Playground and adds a README before converting the draft item.

Repository → Issues → Project item

21. Converting a draft item into an issue

The instructor opens the item's menu and chooses Convert to issue, then searches for and selects the repository.

After selecting GitHub Projects Playground, the draft becomes an issue associated with that repository.

Draft item → Convert to issue → Select repository → Issue

22. What changes when a draft becomes an issue?

AssigneesWho is responsible for the issue.
LabelsIssue-specific categorization.
MilestoneA grouping used to track progress toward a larger goal.
Pull requestsThe issue can be related to pull requests.
RepositoryShows which repository owns the issue.

The project's Status field remains available.

23. Issue numbers

After conversion, the Table view displays an issue number such as #1. In the demonstration, this identifies the first issue created in that repository.

24. Creating a milestone

Milestones are used to track completion of a related series of tasks.

The instructor creates a milestone named setup in the repository and assigns the issue to it.

Related tasks → Milestone → Track completion

25. Milestone progress

The milestone displays a progress bar based on associated issues. The demonstrated milestone is initially empty because its issue is still open.

The instructor notes that additional milestones could be created, such as one for documentation.

After the issue is closed, the demonstrated milestone becomes complete.

26. Closing the issue updates the project automatically

  • The issue becomes closed.
  • The milestone progress updates.
  • The project's Status moves to Done.
  • The Board view moves the task into Done.
  • The changes are reflected in the other project views.

Close issue → Milestone updates → Project status updates → Board position updates

Core lesson: Projects and repositories are connected through synchronized item data, so changes do not have to be manually repeated everywhere.

27. Project history records changes

The issue page shows a history of activity, including actions such as assignment, conversion from a draft, and addition to the project.

Further modifications to the issue or project are also automatically recorded in the history.

28. Associating the project with the repository

Creating a repository separately does not automatically associate it with the existing project.

The repository's Projects area can be used to manually link the project.

Repository → Projects → Select existing project → Repository linked to project

After linking, the repository provides faster direct access to the project.

31. Exam / interview points

  1. Project settings are accessible through the project's hamburger menu.
  2. Project access controls determine who can contribute to the project.
  3. Project access and repository permissions are separate concerns.
  4. GitHub automatically provides a Status field for the project.
  5. Status can contain options such as Todo, In Progress, Done, and the lesson's added Backlog option.
  6. Custom project fields introduced here include Text, Date, Single select, and Iteration.
  7. An Iteration field can represent recurring sprint periods.
  8. Table, Board, and Roadmap views use the same underlying project data.
  9. Moving an item between Board columns can update its Status field.
  10. A Roadmap requires date or iteration information and can use Start and Due fields for its timeline.
  11. A modified view displays a blue-dot indicator until the configuration is saved.
  12. Draft items can be converted into repository issues.
  13. An issue belongs to a repository.
  14. Issues can have labels, milestones, assignees, pull-request relationships, and repository information.
  15. Closing an issue can automatically update milestone progress and project status.
  16. A separately created repository may need to be manually associated with the project.

A: In the project's Settings area.

A: Status, with options such as Todo, In Progress, and Done.

Q: What field was created for a deadline?

A: A Date field called Due.

Q: What field type is useful for recurring sprints?

A: An Iteration field.

Q: What happens when a Board item is dragged from Todo to In Progress?

A: Its underlying Status changes, and that change appears in the other views.

Q: What does a Roadmap need?

A: At least one date or iteration field; the demonstration uses Start and Due date fields.

Q: Where does an issue belong?

A: A repository.

Q: What happens when a draft is converted to an issue?

A: It becomes a repository-owned issue and gains issue-related information such as labels and milestones.

A: The milestone updates, the project status moves to Done, and the Board item moves to Done automatically.

33. What you should remember

The strongest mental model from these lessons is:

Fields describe the work → Views organize the work → Issues connect the work to repositories → GitHub synchronizes the connected state

Settings control the project itself and who can work on it. Custom fields add structured information. Views expose that information in different ways. Draft items allow brainstorming, while repository issues connect project work to GitHub's issue-tracking system.

Because these views and repository connections operate on shared project data, changing an item in one place can automatically change how that item appears elsewhere.

Lesson connection

These lessons build directly on the first-project lesson: after creating a project, you learn how to control access, create meaningful fields, build different views, work with dates and iterations, and connect project items to repository issues and milestones.

The result is a project workspace that connects planning information with actual repository work rather than keeping the two systems separate.
