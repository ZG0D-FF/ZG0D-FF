Question 1

Four significant differences between a file-processing system and a DBMS

AspectFile-processing systemDBMS
Redundancy & consistencyEach application keeps its own files, so the same data is duplicated and copies drift apart (inconsistency).Data is stored centrally; redundancy is controlled (e.g. via normalization) so one fact lives in one place.
Data access & isolationData is scattered in files of different formats; every new query needs a new application program.Uniform data model and a query language (SQL) answer ad-hoc queries without writing new programs.
Integrity & atomicityConstraints are buried in program code; a crash mid-update leaves the data half-changed.Constraints are declared once (keys, checks, foreign keys); transactions are atomic with log-based recovery.
Concurrency & securitySimultaneous updates can overwrite each other; access control is all-or-nothing at file level.Concurrency control (locking/MVCC) keeps results correct; fine-grained authorization per user, table or view.

Bonus: a DBMS also gives data independence — the physical storage can change without rewriting applications.

Question 2

1:1, 1:M and M:N relationships with set diagrams

One-to-one (1:1)

Each element of set A is related to at most one element of set B and vice versa. Example: a Person holds one Passport.

One-to-many (1:M)

One element of A can relate to many elements of B, but each element of B relates to at most one element of A. Example: a Department has many Employees.

Many-to-many (M:N)

Many elements of A relate to many elements of B and vice versa. Example: Students enrol in many Courses; a Course has many Students. Implemented with a junction table.

Question 4

ER diagram for company and employee phones, with (min, max)

Entities: EMPLOYEE (emp_id, name), DEPARTMENT (dept_id, name), PHONE (phone_no). Each constraint is read as (min, max) next to the entity it describes.

  • WORKS_IN: an employee works in 0 to 2 departments → (0,2); a department has any number of employees → (0,N).
  • HAS_PHONE (department phones): every department has at least 1 and at most 3 numbers → (1,3); a number is optional from the phone side → (0,N) because an employee's personal number may be reused as a department number.
  • PERSONAL_PHONE: an employee may have no personal phone, or at most one → (0,1); a phone belongs to at most one employee → (0,1).

The "up to three numbers including personal ones" rule is the (1,3) on DEPARTMENT; it counts both dedicated and personal numbers linked through HAS_PHONE.

Question 7

Create tables and SQL queries

Table definitions

CREATE TABLE Faculty (
  fid     INT PRIMARY KEY,
  fname   VARCHAR(50) NOT NULL,
  deptid  INT
);

CREATE TABLE Student (
  snum   INT PRIMARY KEY,
  sname  VARCHAR(50) NOT NULL,
  major  VARCHAR(50),
  level  VARCHAR(10),
  age    INT
);

CREATE TABLE Class (
  name     VARCHAR(50) PRIMARY KEY,
  meets_at VARCHAR(30),
  room     VARCHAR(20),
  fid      INT,
  FOREIGN KEY (fid) REFERENCES Faculty(fid)
);

CREATE TABLE Enrolled (
  snum   INT,
  cname  VARCHAR(50),
  PRIMARY KEY (snum, cname),
  FOREIGN KEY (snum)  REFERENCES Student(snum),
  FOREIGN KEY (cname) REFERENCES Class(name)
);

i. Junior students in a class taught by 'XYZ'

SELECT DISTINCT s.sname
FROM Student s
JOIN Enrolled e ON s.snum  = e.snum
JOIN Class c    ON e.cname = c.name
JOIN Faculty f  ON c.fid   = f.fid
WHERE s.level = 'Junior' AND f.fname = 'XYZ';

ii. Age of the oldest History major

SELECT MAX(age)
FROM Student
WHERE major = 'History';

iii. Classes meeting in R1 or with five or more students

SELECT c.name
FROM Class c
WHERE c.room = 'R1'
   OR c.name IN (SELECT cname
                 FROM Enrolled
                 GROUP BY cname
                 HAVING COUNT(*) >= 5);
Question 8

Compute B⁺ (attribute closure)

R = (A, B, C, D, E) with F = { A→BC, CD→E, B→D, E→A }

1
Start: result = {B}
2
B → D applies (B ⊆ result): result = {B, D}
3
A → BC needs A — not in result. CD → E needs C — not in result. E → A needs E — not in result.
4
No dependency adds anything new, so we stop.
B⁺ = { B, D }

Since B⁺ ≠ R, B is not a key.

Question 9

FD2 is covered by FD1, but FD1 is not covered by FD2

R(V, W, X, Y, Z) · FD1 = { W→X, WX→Y, Z→WY, Z→V } · FD2 = { W→XY, Z→WX }
"A is a subset of B" here means every FD of A is implied by B (A ⊆ B⁺).

Part 1: every FD in FD2 follows from FD1

FD2 dependencyClosure using FD1Result
W → XYW⁺ = {W} → W→X gives {W,X} → WX→Y gives {W,X,Y}XY ⊆ W⁺ ✓
Z → WXZ⁺ = {Z} → Z→WY gives {Z,W,Y} → W→X gives {Z,W,X,Y} → Z→V gives {Z,W,X,Y,V}WX ⊆ Z⁺ ✓
All FDs of FD2 are implied by FD1, so FD2 ⊆ FD1⁺.

Part 2: some FD in FD1 does not follow from FD2

FD1 dependencyClosure using FD2Result
W → XW⁺ = {W,X,Y}X ∈ W⁺ ✓
WX → Y(WX)⁺ = {W,X,Y}Y ∈ (WX)⁺ ✓
Z → WYZ⁺ = {Z,W,X} → W→XY adds Y → {Z,W,X,Y}WY ⊆ Z⁺ ✓
Z → VZ⁺ = {Z,W,X,Y}; no FD in FD2 produces VV ∉ Z⁺ ✗
Z → V is not implied by FD2, so FD1 ⊄ FD2⁺. Hence FD2 is a subset of FD1, but FD1 is not a subset of FD2.
Question 10

Normalize Professor up to BCNF

Professor(PCode, Department, HOD, Percent_of_time) · keys: (PCode, Department) and (PCode, HOD)
FDs: Department,PCode → HOD,Percent_of_time · Department → HOD · HOD,PCode → Department,Percent_of_time

1
1NF: all attributes are atomic, so the relation is in 1NF.
2
2NF: the only non-prime attribute is Percent_of_time, and it depends on the whole key (PCode, Department). No partial dependency on a non-prime attribute, so it is in 2NF.
3
3NF: Department → HOD has a prime attribute (HOD) on its right side, so 3NF is satisfied.
4
BCNF: Department → HOD violates BCNF because Department is not a superkey (the same HOD is repeated for each professor in a department).

Decomposition on Department → HOD

R1 (Department, HOD)                          key: Department
R2 (PCode, Department, Percent_of_time)       key: (PCode, Department)

Both relations are in BCNF: in R1 the only FD has a key on its left; in R2 the only FD is (PCode, Department) → Percent_of_time. The split is lossless because the common attribute Department is the key of R1.

Note: HOD,PCode → Department,Percent_of_time can no longer be checked inside one table — the usual cost of BCNF (see Question 11).

Question 11

BCNF cannot always preserve dependencies

Example: R(Student, Course, Instructor) with

  • Student, Course → Instructor (a student has one instructor for a course)
  • Instructor → Course (each instructor teaches only one course)

Candidate keys: (Student, Course) and (Student, Instructor).

BCNF check: Instructor → Course violates BCNF, since Instructor is not a superkey. The only decomposition on this FD is:

R1 (Instructor, Course)      holds  Instructor → Course
R2 (Student, Instructor)     holds  only trivial FDs

Dependency check: FDs visible in R1 ∪ R2 are just Instructor → Course. The closure of (Student, Course) using it is {Student, Course} — Instructor never appears. So Student, Course → Instructor is lost: enforcing it needs a join of R1 and R2.

The BCNF decomposition is lossless but not dependency preserving. Here 3NF would keep R intact and preserve all FDs, at the price of some redundancy.
Question 12

Normal form of R{RN, POR, PI, PN, DATE, MA, MT}

F = { RN → POR ; PI → PN, RN ; (PI, DATE) → (MA, MT, POR) }

1
Find the key. (PI, DATE)⁺: PI→PN,RN gives PN, RN; RN→POR gives POR; (PI,DATE)→MA,MT. Result = all attributes, so (PI, DATE) is the candidate key.
2
Prime: PI, DATE. Non-prime: RN, POR, PN, MA, MT.
3
2NF test: PI → PN, RN has a proper subset of the key (PI) determining non-prime attributes: a partial dependency. So 2NF fails.
The relation is in 1NF only (not 2NF). Also RN → POR is a transitive dependency, which would further violate 3NF.
Question 13

Precedence graph and serializability

Rows below follow the schedule in your PDF, top to bottom. Change a row's transaction and everything updates live.

Result

Method: add edge Ti → Tj when an operation of Ti precedes a conflicting operation of Tj on the same item (different transactions, at least one is a write). The schedule is conflict-serializable iff the graph has no cycle; a topological order gives the equivalent serial schedule.

Question 15

Bucket overflow in hash file organization

Causes

  • Insufficient buckets: the number of buckets is too small for the number of records (nB < nr / fr).
  • Skew, from repeated keys: many records share one search-key value, so they all land in the same bucket.
  • Skew, from the hash function: a function that is not uniform or random sends far more keys to some buckets than others.

Reducing overflows

  • Choose the number of buckets as (nr / fr) × (1 + d) with a fudge factor d ≈ 0.2, leaving about 20% spare space.
  • Use a better hash function that spreads keys uniformly and randomly.
  • Handle unavoidable overflow with overflow chaining (linked overflow buckets), or open addressing.
  • Use dynamic hashing (extendable or linear hashing) so the bucket count grows as the file grows.
