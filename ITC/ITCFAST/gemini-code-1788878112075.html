The Big Picture — Slides 1–26

This whole section is basically answering one question:

How can we represent source symbols using as few bits as possible, while still being able to decode them unambiguously?

The progression is:
Variable-length codes → Prefix condition → Kraft inequality → Source coding theorem → Efficiency → Huffman coding → Block coding

1. Why Variable-Length Codes?

Suppose a source produces symbols with different probabilities. Some symbols occur very frequently, while others are rare. It would be wasteful to give every symbol the same number of bits. Instead, we can do this:

  • Frequent symbol → short codeword
  • Rare symbol → long codeword

For example:

Symbol Probability Code
Ahigh0
Bmedium10
Clow110

So instead of using the same number of bits for everyone, we save bits on average. That is the basic idea behind variable-length coding.

But there is a problem: How do we know where one codeword ends?

Suppose:
A = 0
B = 01
Now if we receive: 01
Is it B, or A followed by something? The code boundaries become ambiguous. This leads directly to prefix codes.

2. Prefix Code

Look at Slide 3:

Letter Codeword
A00
B010
C011
D100
E101
F110
G1110
H1111

The important observation is: No codeword is the beginning of another codeword.

  • 00 → nobody else starts with 00
  • 010 → nobody else has 010...
  • 1110 → nobody else starts with 1110

Therefore, once the received bits match a complete codeword, we immediately know the symbol.

Example:
Suppose the received stream is: 0101111
Look at the beginning: 010 → B
Remaining: 1111 → H
So: 010 | 1111 → B H
No guessing is required.

3. Why "Prefix" Matters

A prefix simply means the beginning portion of a sequence. For example, 1011 has prefixes: 1, 10, 101, 1011.

So if we had A = 10 and B = 101, then 10 is a prefix of 101. That violates the prefix condition.

Prefix condition = no complete codeword can be the beginning of another codeword.

Because of this property, the code is also called an Instantaneous code. Why? Because once the complete codeword arrives, we can immediately decode it.

4. Kraft Inequality

Now the slides ask something slightly different. Instead of asking: "Is this particular code a prefix code?", we ask: "Can a prefix code with these codeword lengths even exist?"

That's what Kraft inequality tells us. For a binary prefix code:

$$ \boxed{\sum_{k=1}^{L}2^{-n_k}\leq 1} $$

where $n_k$ is the length of the $k$-th codeword. For an alphabet of size $M$:

$$ \boxed{\sum_{k=1}^{L}M^{-n_k}\leq 1} $$

What should you remember? Don't just memorize the equation. Its meaning is: The proposed codeword lengths must satisfy this inequality for a prefix code to exist.

And importantly, the slide says this condition is necessary and sufficient. So:

$$ \boxed{\text{Kraft condition satisfied} \iff \text{prefix code can exist}} $$

5. Source Coding Theorem

Now we reach the central result. Suppose the source has entropy $H(X)$ and we construct a prefix code. Let its average number of bits per source symbol be $\bar{R}$.

The source coding theorem says we can construct a prefix code such that:

$$ \boxed{H(X) \leq \bar{R} < H(X)+1} $$

This is extremely important. It says: The average number of bits required by a suitable prefix code can be made at least the entropy, but less than entropy + 1 bit. So entropy acts like a fundamental lower bound.

6. Why Can't We Go Below Entropy?

Suppose $H(X)=2.1$. Then you cannot have a prefix code whose average length is $\bar{R}=1.8$ because $\bar{R} \ge H(X)$. The best you could theoretically approach is around $2.1 \text{ bits/symbol}$.

And the theorem guarantees a code with: $2.1 \le \bar{R} < 3.1$.

So if you actually find $\bar{R} = H(X)$, then you've hit the lower bound. That's why Slide 7 says: If $\bar{R} = H(X)$, stop searching — you cannot do better.

7. Connection Between Entropy and Uncertainty

The slides then make an important conceptual statement: Higher entropy → higher average number of bits required.

Why? Entropy represents the uncertainty of the source. More uncertainty means the source is harder to represent efficiently. So, within this context:

$$ \boxed{\text{Higher uncertainty} \Rightarrow \text{higher entropy} \Rightarrow \text{more bits on average}} $$

8. Efficiency of a Code

The slides define:

$$ \boxed{\eta = \frac{H(X)}{R}} $$

Here $R$ represents the average code length. Think of it as: How close is our actual average representation to the theoretical minimum?

If $H(X)=2$ and $R=2.2$, then $\eta = \frac{2}{2.2} = 0.9091$. So efficiency is about $90.91\%$.

The source coding theorem gives $R \ge H(X)$, therefore $\eta \le 1$. The closer $\eta$ is to 1, the more efficient the code.

9. Why This Gives Compression

Suppose every symbol was originally represented using 8 bits. But after source coding, we need only $2.2 \text{ bits/symbol}$ on average. Then we are representing the same source information using fewer bits. That is compression.

Hence the slide connects: Efficient representation → fewer bits → compression. And source coding can be applied to speech, text, images, video, etc.

10. Huffman Coding

Now comes the practical question: How do we actually construct such an efficient variable-length prefix code? The slides introduce Huffman Coding.

Huffman coding uses the source probabilities. Its goal is to construct a prefix code with a minimum average number of bits. So Huffman coding simultaneously aims for the Prefix condition and Minimum average code length.

11. The Huffman Idea

The procedure is very intuitive.

  • Step 1 — Arrange probabilities: Put symbols in decreasing probability order.
    For example: $0.37,\ 0.33,\ 0.16,\ 0.07,\ 0.04,\ 0.02,\ 0.01$
  • Step 2 — Pick the two smallest: The two smallest are $0.01$ and $0.02$. Combine them: $0.01 + 0.02 = 0.03$. Now treat that combination as one node.

12. Why Combine the Smallest?

Because these are the least probable symbols. They can afford to receive longer codewords. The Huffman construction therefore pushes low-probability symbols deeper into the tree. High-probability symbols remain closer to the root and therefore receive shorter codewords.

$$ \boxed{\text{High probability} \rightarrow \text{short code}} \quad \boxed{\text{Low probability} \rightarrow \text{long code}} $$

13. Continue Combining

After obtaining $0.03$, we combine it with the next smallest probability:
$0.04 + 0.03 = 0.07$
$0.07 + 0.07 = 0.14$
$0.14 + 0.16 = 0.30$
$0.30 + 0.33 = 0.63$
$0.63 + 0.37 = 1$
Eventually everything becomes $\boxed{1}$ because all source probabilities together equal 1. This creates the Huffman tree.

14. Where Do the 0s and 1s Come From?

Every time two nodes are joined, we assign one branch → 0 and the other branch → 1.

Then to obtain a symbol's codeword: Start at the root and follow the branches until reaching that symbol. The sequence of 0s and 1s encountered is its codeword. That's why Huffman naturally creates a prefix code.

15. First Huffman Example

Symbol Probability Length
$x_1$0.371
$x_2$0.332
$x_3$0.163
$x_4$0.074
$x_5$0.045
$x_6$0.026
$x_7$0.016

Notice the pattern: Most probable → shortest, Least probable → longest.

16. Calculating Entropy

The entropy is:

$$ H(X) = -\sum_{k=1}^{7}P(x_k)\log_2P(x_k) $$

For this example: $\boxed{H(X) = 2.1152 \text{ bits}}$. This is the theoretical lower bound.

The Huffman code gives: $\boxed{\bar{R} = 2.1700 \text{ bits}}$. Check the source coding theorem: $2.1152 \le 2.1700 < 3.1152$. Correct.

17. Calculating Average Code Length

The average length is:

$$ \bar{R} = \sum n_k P(x_k) $$

For this example:
$\bar{R} = 1(0.37) + 2(0.33) + 3(0.16) + 4(0.07) + 5(0.04) + 6(0.02) + 6(0.01) = \boxed{2.1700}$

So the average source symbol requires 2.17 bits.

18. Efficiency

Now $\eta = \frac{H(X)}{\bar{R}}$.

Therefore, $\eta = \frac{2.1152}{2.1700} = \boxed{0.9747}$ or approximately $\boxed{97.47\%}$.

So this Huffman code is quite close to the theoretical limit.

19. Huffman Codes Are Not Unique

This is an important subtle point. The same probabilities can sometimes produce different Huffman trees. Why? Because during construction, two nodes can sometimes have equal probabilities, and there can be different valid ways to combine them.

Therefore you can get different codewords while still having the same codeword lengths → same average length → same efficiency.

For the second example: $H(X) = 1.9781$ and $\bar{R} = 1.9900$, so $\eta = \frac{1.9781}{1.9900} = 0.9940$. Both possible Huffman codes have the same $\boxed{\eta = 0.9940}$. Therefore: Huffman coding is not necessarily unique.

20. The Perfect Case: $\eta = 1$

Slide 20 gives a particularly clean probability distribution: $\frac{1}{2}, \frac{1}{4}, \frac{1}{8}, \frac{1}{16}, \frac{1}{32}, \frac{1}{64}, \frac{1}{64}$.

Notice something beautiful: $\frac{1}{2} = 2^{-1}$, $\frac{1}{4} = 2^{-2}$, $\frac{1}{8} = 2^{-3}$, and so on. Therefore the self-information ($-\log_2P(x)$) gives $1, 2, 3, 4, 5, 6, 6$ bits. And the Huffman code lengths are exactly $1, 2, 3, 4, 5, 6, 6$.

So: $\boxed{\bar{R} = H(X)}$ and therefore $\boxed{\eta = 1}$. This is perfect efficiency.

21. What Does D-adic Mean Here?

The slide defines a probability distribution as D-adic if every probability has the form $D^{-n}$ for some integer $n$. Here we're using binary coding, so $D=2$. Thus probabilities such as $2^{-1}, 2^{-2}, 2^{-3}$ are 2-adic.

Why does this matter? Because their self-information is $-\log_2(2^{-n}) = n$, which is an integer. So the required information for the symbol is already an integer number of bits. That lets Huffman assign exactly that many bits.

$$ \boxed{\text{integer self-information} \Rightarrow \text{possibility of } \eta = 1} $$

The slide emphasizes that real-world probabilities are not always like this.

22. Why Encode Blocks?

Until now, we encoded one source symbol at a time. But this has a limitation. The source coding theorem gives $H(X) \le \bar{R} < H(X)+1$. There can be almost 1 extra bit per symbol in the worst bound.

The idea now is: Instead of coding one symbol, combine several symbols into a block and code the entire block. Suppose $B=2$. Then instead of $x_1, x_2$, we consider $x_1x_2$ as one combined source symbol.

23. Why Block Coding Helps

For a block of $B$ symbols:

$$ \boxed{B \cdot H(X) \le \bar{R}_B < B \cdot H(X) + 1} $$

Here $\bar{R}_B$ is the average number of bits for the whole block. Divide everything by $B$:

$$ H(X) \le \frac{\bar{R}_B}{B} < H(X) + \frac{1}{B} $$

This is the key insight. For one symbol: $H(X) \le \bar{R} < H(X)+1$. For blocks: $H(X) \le \bar{R} < H(X) + \frac{1}{B}$. As $B$ gets larger, $\frac{1}{B} \rightarrow 0$. Therefore the upper bound gets closer and closer to entropy.

24. The Slide 24 → 25 Example

For the original symbol-by-symbol coding: $H(X) = 1.5589$ and $\bar{R} = 1.6000$. Therefore $\eta = 0.9743$. So we are close, but not perfect.

Now instead of coding individual symbols, we code pairs. Since there are 3 possible symbols ($x_1, x_2, x_3$), there are $3 \times 3 = 9$ possible pairs: $x_1x_1,\ x_1x_2,\ \ldots,\ x_3x_3$.

The probability of a pair is obtained from the individual probabilities. For example: $P(x_1x_1) = 0.4 \times 0.4 = 0.16$ and $P(x_1x_2) = 0.4 \times 0.35 = 0.14$. Then Huffman coding is applied to these pairs as if each pair were one large source symbol.

25. Why the Entropy Becomes $2H(X)$

For a block containing 2 symbols: $\boxed{H(\text{pair}) = 2H(X)}$.

The slide gives $2H(X) = 3.1177$, so $H(X) = 1.5589$. The Huffman coding of the pairs gives $2\bar{R} = 3.1775$. Therefore $\bar{R} = \frac{3.1775}{2} = 1.5888$.

Compare:

  • Symbol-by-symbol: $\bar{R} = 1.6000$
  • Two-symbol blocks: $\bar{R} = 1.5888$

So block coding has improved the average bits per symbol. Consequently $\eta = 0.9812$ instead of $0.9743$. Hence: $\boxed{\text{Block coding gives better efficiency here}}$.
