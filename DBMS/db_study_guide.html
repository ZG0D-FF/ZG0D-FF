Part 2 — Answers (Navathe, Ch. 1 Review Questions)

1.1 Key Term Definitions

  • Data: Known facts that can be recorded and have implicit meaning.
  • Database: A logically coherent collection of related data with inherent meaning, designed, built, and populated for a specific purpose to reflect an aspect of the real world (the miniworld).
  • DBMS: A general-purpose software system enabling users to create and maintain a database by defining, constructing, manipulating, and sharing it.
  • Database System: The database itself together with the DBMS software.
  • Database Catalog: Repository storing descriptions of structure, data types, formats, and constraints — a.k.a. meta-data.
  • Program-Data Independence: Data file structures are stored in the catalog separate from access programs, so structural changes don't require program changes.
  • User View: A tailored subset of the database for a specific group of users.
  • DBA: Chief administrator — authorizes access, coordinates/monitors use, acquires hardware/software resources.
  • End User: People whose jobs require accessing the database for querying, updating, reporting.
  • Canned Transaction: Standard, pre-tested queries/updates run routinely by naive users (e.g., bank tellers).
  • Deductive Database System: Provides deduction rules to infer new info from stored facts.
  • Persistent Object: A program object/data structure that survives program termination and can be retrieved later.
  • Meta-Data: Data about data — structure, constraints, types stored in the catalog.
  • Transaction-Processing Application: High-volume OLTP apps requiring atomicity/isolation (e.g., banking, flight booking).

1.2 Four Main Types of Database Actions

  1. Defining: Specifying data types, structures, and constraints.
  2. Constructing: Storing initial data onto DBMS-controlled media.
  3. Manipulating: Querying, updating, and generating reports.
  4. Sharing: Allowing multiple users/programs concurrent access.

1.3 Database Approach vs. File Systems

  • Self-Describing Nature: Data + structure (meta-data) both stored in a catalog, vs. hardcoded structures per program.
  • Program-Data Independence & Abstraction: Programs use a conceptual view; catalog changes don't break programs. File systems break all dependent programs on format change.
  • Multiple Views: DBMS presents customized subsets without altering storage.
  • Sharing & Multiuser Transactions: Concurrency control prevents corruption; file systems force isolated, duplicated, inconsistent copies.

1.4 DBA vs. Database Designer Responsibilities

DBA: authorizes access/security, coordinates and monitors usage/performance, defines schemas and standards, performs backups and storage maintenance.

Database Designers: communicate with end users to gather requirements, identify data/structures/relationships/constraints, develop and integrate user views into a unified conceptual design.

1.5 Types of End Users

  1. Casual: Occasional access, varied needs, sophisticated query interfaces.
  2. Naive/Parametric: Large group running canned transactions via simple forms/apps (tellers, agents, clerks).
  3. Sophisticated: Engineers/scientists/analysts building their own complex applications.
  4. Standalone: Maintain personal databases with ready-made menu/GUI software (e.g., personal finance apps).

1.6 DBMS Capabilities

  • Controlling Redundancy — normalized storage or controlled denormalization.
  • Restricting Unauthorized Access — passwords, privilege levels.
  • Persistent Storage — preserves complex structures across runs.
  • Efficient Query Processing — indexes, buffering, optimization.
  • Backup & Recovery — restores consistent state after crashes.
  • Multiple User Interfaces — GUIs, apps, query languages, NL interfaces.
  • Complex Relationships — models interrelated records.
  • Integrity Constraints — types, uniqueness, referential integrity.
  • Inferencing & Active Rules — deduction rules, triggers, stored procedures.

1.7 Database Systems vs. Information Retrieval Systems

DBMS: structured text/numeric data in tables; exact-match declarative queries (SQL); strict schema, ACID, concurrency control.

IR Systems: unstructured textual data (web pages, docs); keyword queries with relevance ranking; focused on indexing/classification/search, no relational structure or updates.

1.9 Controlled vs. Uncontrolled Redundancy

Uncontrolled: Same data stored in multiple independent files with no synchronization — wastes space, doubles effort, causes inconsistency. Example: a birth date stored differently in a Registration File vs. an Accounting File.

Controlled: Deliberate denormalization where the DBMS auto-synchronizes all copies. Example: storing Student_name redundantly in GRADE_REPORT for faster reports, kept in sync with STUDENT.

  2. SECTION → GRADE_REPORT (1:N) via Section_identifier.
  3. COURSE → SECTION (1:N) via Course_number.
  4. COURSE → PREREQUISITE (1:N, self-relationship) via Course_number/Prerequisite_number.

1.13 When Traditional File Processing Makes Sense

  1. Simple, single-user apps with fixed requirements, no concurrency (e.g., a phonebook).
  2. Embedded real-time systems with strict memory/timing limits (e.g., engine controllers, avionics).
  3. Specialized high-speed systems — CAD drawing objects, telecom call routing needing direct specialized memory access.

6 columns across 5 tables:

  • COURSE: Department ('CS'→'CSSE'); Course_number prefix (e.g., CS1310→CSSE1310).
  • STUDENT: Major ('CS'→'CSSE').
  • SECTION: Course_number.

1.14b Restructuring for a Single-Column Update

Yes — use a surrogate primary key:

  1. Create a DEPARTMENT table: Dept_id, Dept_name, Dept_code.
  2. Restructure COURSE: numeric Course_id as PK; foreign key Dept_id instead of text prefix.
  3. Restructure SECTION and PREREQUISITE to reference Course_id instead of text course strings.

Result: renaming CS → CSSE requires updating just one cell — Dept_code in DEPARTMENT.

Part 4 — Answers (Navathe, Ch. 2 Review Questions)

2.1 Key Term Definitions

  • Data Model: Conceptual tools describing structure (types, relationships, constraints) plus operations for retrieval/update.
  • Database Schema: The overall structural design, specified at design time, changes infrequently.
  • Database State: Actual data at a moment in time (snapshot/extension).
  • Internal Schema: Lowest-level schema — physical storage, record formats, access paths.
  • Conceptual Schema: Logical structure for the whole enterprise, hides physical storage.
  • External Schema: A user view describing a relevant part of the DB, hides the rest.
  • Data Independence: Ability to change one schema level without changing the next higher level.
  • DDL: Defines conceptual/external schemas.
  • DML: Retrieves/inserts/updates/deletes data.
  • SDL: Specifies internal physical schema.
  • VDL: Specifies external views and their mapping to the conceptual schema.
  • Query Language: High-level DML used interactively.
  • Host Language: General-purpose language (C++, Java, Python) embedding DML.
  • Data Sublanguage: DML embedded within a host language.
  • Database Utility: DBA tools — loading, backup, reorganization, monitoring.
  • Catalog: Repository of meta-data — schemas, constraints, mappings.
  • Client/Server Architecture: Work split between client (UI/local processing) and server (storage/transactions).
  • Three-Tier Architecture: Adds an app/Web server layer between client and DB server for logic and security.
  • N-Tier Architecture: Functionality split across n > 3 layers for finer modularity.

2.2 Categories of Data Models

  1. High-Level/Conceptual: Entities, attributes, relationships — close to user perception.
  2. Representational/Implementation: Record-based (relational, network, hierarchical) — close to disk organization but still user-understandable.
  3. Low-Level/Physical: Record formats, orderings, indexes.
  4. Self-Describing: Schema bundled with data values (XML, NoSQL, key-value).

Relational: flat tables, rows/columns, SQL. Object: objects with state + behavior, class hierarchies. XML: tree-structured, tagged/nested elements, flexible web interchange.

2.3 Schema vs. State

Schema (intension): structural design, defined at design time, static. State (extension/snapshot): actual data records at a given moment, changes with every insert/update/delete.

2.4 Three-Schema Architecture

Internal level — physical storage/access paths. Conceptual level — logical structure for the enterprise. External level — multiple user views.

Why mappings: physical data exists only at the internal layer; mappings translate requests from external → conceptual → internal, and results back up.

Languages: DDL → conceptual schema; SDL → internal schema; VDL → external views. Modern SQL merges DDL, VDL, DML into one language.

2.5 Logical vs. Physical Data Independence

Logical: modify conceptual schema without breaking external views/programs. Physical: modify internal schema (storage, indexes) without touching the conceptual schema/views.

Harder to achieve: Logical — because structural/constraint changes must not break dependent application programs.

2.6 Procedural vs. Nonprocedural DML

Procedural (record-at-a-time): specifies what AND how, loops over records, embedded in general-purpose languages.

Nonprocedural (set-at-a-time/declarative): specifies only what is needed (e.g., SQL); DBMS handles optimization.

SELECT Name FROM STUDENT WHERE Class = 2; — selects the Name column, from STUDENT, filtered to sophomores, with no manual access loops.

2.7 User Interfaces by User Type

  1. Menu-based/Browsing: casual users.
  2. Mobile apps/Forms: naive/parametric users running canned transactions.
  3. GUIs (schema diagrams): casual/standalone users building queries visually.
  4. Natural language/Keyword search: casual/non-technical users.
  5. Speech I/O: mobile/automated phone service users.
  6. Parametric/Function-key: naive users, high-frequency repetitive tasks.
  7. DBA interfaces: privileged commands for administrators.

2.8 DBMS Interaction with Other Software

OS: disk I/O scheduling, file systems, CPU scheduling, memory buffering. Compilers/Precompilers: host-language compilation; DML precompilers extract embedded DB statements. Communications/Network Software: enables remote clients/Web servers/distributed nodes to reach the DB server.

2.9 Two-Tier vs. Three-Tier

Two-Tier: Client (UI + app logic) ↔ Server (SQL processing + storage), via ODBC/JDBC. Three-Tier: adds an intermediate app/Web server holding business logic/rules, improving security and scalability for Web apps.

2.10 Database Utilities

  • Loading: converts external files into DB format.
  • Backup: full/incremental dumps for recovery.
  • Storage Reorganization: reindexes/reorganizes files.
  • Performance Monitoring: runtime stats for tuning.
  • Expanded Data Dictionary/CASE Tools: design assistance and stored design rationale/standards.

2.11 N-Tier (n > 3) Additional Functionality

  • Finer layering of business logic (presentation/application/middleware sub-layers).
  • Heterogeneous integration via middleware across multiple vendor back-ends (ERP/CRM).
  • Enhanced security & compression — encryption layers and data compression for network transmission.

2.13 Sample Schema — Library Management System

Tables: BOOK(Book_id, Title, Author, Category, Price) · MEMBER(Member_id, Name, Email, Phone) · LOAN(Loan_id, Book_id, Member_id, Issue_date, Return_date).

Sample rows: B101 "Database Systems" (Navathe, $85.00); M201 Alice Smith; L301 links B101↔M201, issued 2026-09-01, due 2026-09-15.

Constraints: unique Book_id/Member_id/Loan_id; Price > 0; Issue_date ≤ Return_date; Book_id/Member_id in LOAN must exist in BOOK/MEMBER.

Views: MY_BORROWED_BOOKS (member's own active loans) and OVERDUE_LOANS (librarian view of late returns).

2.14 Architecture for a Web-Based Airline Reservation System

Chosen: Three-Tier (or N-Tier).

Why: app/Web server layer hides DB credentials and centralizes business logic (seat rules, pricing, payment validation); scales web traffic with lightweight clients.

Why not others: Centralized architecture can't scale to millions of Web/mobile users; Two-Tier exposes direct SQL connections to public clients — security and performance risks.
