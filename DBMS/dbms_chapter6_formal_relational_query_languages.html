Chapter map: three languages, one relational world

A relational query asks for a relation as its answer. These languages differ mainly in how the query is expressed: as operations, as conditions on whole tuples, or as conditions on individual attribute values.

Use this map to remember the main distinction: algebra gives a procedure; calculus gives a logical specification.

Procedural

Describe how to build the result by composing relational operations.

Tuple-oriented

Describe tuples that qualify, using tuple variables and logical predicates.

Domain-oriented

Describe combinations of attribute values that satisfy a logical predicate.

Vocabulary trap: relational-algebra select is the operation denoted by σ and corresponds roughly to SQL's WHERE, not SQL's SELECT. Algebraic projection (π) is closer to choosing the output columns.

6.1 The Relational Algebra

Relational algebra is a procedural query language. Each operation takes one or two relations as input and produces a relation. The fundamental operations are selection, projection, union, set difference, Cartesian product, and rename. Intersection, joins, and assignment are additional conveniences that can be defined using the fundamental operations.

A relation-valued result can become the input to another operation, so expressions compose.

6.1.1 Fundamental operations

Selection — σ (choose rows)

Selection retains tuples satisfying a predicate. The predicate is written as a subscript; the relation appears in parentheses.

σdept name = "Physics"(instructor)

This returns all instructor tuples whose department is Physics. For the chapter's sample relation, the result contains Einstein (salary 95,000) and Gold (salary 87,000).

σsalary > 90000(instructor)

Selection predicates may use =, ≠, <, ≤, >, ≥, and logical connectives AND (∧), OR (∨), NOT (¬). They may compare two attributes too:

σdept name = building(department)

Meaning: retain departments whose name equals their building value.

Projection — π (choose columns)

Projection returns only the specified attributes. Because a relation is a set in the basic model, duplicate result rows are eliminated.

πID, name, salary(instructor)

The output contains ID, name, and salary, omitting department name. Projection changes the schema of the result and may also reduce its number of tuples if different input tuples become identical after unwanted columns are removed.

Composition of operations

The output of one operation is itself a relation and can be used as another operation's input. To find names of instructors in Physics:

πname(σdept name = "Physics"(instructor))
  1. Selection first: keep instructor tuples whose department is Physics.
  2. Projection next: keep only the name column.

Union — ∪

Union returns tuples found in either relation or both. The two input relations must be union-compatible: same arity (number of attributes) and compatible corresponding attribute domains.

πcourse id(σsemester="Fall" ∧ year=2009(section))
∪
πcourse id(σsemester="Spring" ∧ year=2010(section))

The chapter's example result contains CS-101, CS-315, CS-319, CS-347, FIN-201, HIS-351, MU-199, and PHY-101. CS-101 is retained once even though it appears in both inputs.

Set difference — −

r − s returns tuples in r that are not in s. Like union, the operands must be union-compatible.

πcourse id(σsemester="Fall" ∧ year=2009(section))
−
πcourse id(σsemester="Spring" ∧ year=2010(section))

The supplied example yields CS-347 and PHY-101.

Cartesian product — ×

The Cartesian product combines every tuple of one relation with every tuple of the other. If r has m tuples and s has n, then r × s has m × n tuple combinations. The output schema concatenates the input schemas.

Why product alone is usually not enough: instructor × teaches pairs every instructor with every teaching record, including unrelated combinations. To obtain meaningful pairs, select where instructor.ID = teaches.ID.
πname, course id(σinstructor.ID = teaches.ID(σdept name="Physics"(instructor × teaches)))

This sequence first restricts instructors to Physics, forms combinations with teaching records, selects ID matches, and projects the instructor name and course ID. The resulting pair in the chapter's example is Einstein — PHY-101; Gold is absent because the teaching relation records no course taught by Gold.

Rename — ρ

Rename assigns a usable name to a relation-valued expression or changes its attribute names. It is especially useful when a relation is referenced twice.

ρd(instructor)

This refers to the same instructor relation under the temporary name d. A form that renames attributes as well is:

ρx(A₁, A₂, …, Aₙ)(E)

To find the maximum salary, compare the instructor relation with a renamed copy. The temporary expression below finds salaries for which a larger salary exists:

πinstructor.salary(σinstructor.salary < d.salary(instructor × ρd(instructor)))

Subtracting those salaries from all instructor salaries leaves the highest salary:

πsalary(instructor) − πinstructor.salary(σinstructor.salary < d.salary(instructor × ρd(instructor)))
Alternative notation: positional names such as $4 and $8 can identify attributes by position in a product, but the text notes that this is less readable than relation and attribute names.

6.1.3 Additional relational-algebra operations

Intersection — ∩

Intersection returns tuples common to both compatible relations. It is a convenience, not a new source of expressive power, because it can be written using set difference:

r ∩ s = r − (r − s)

The course-set example for offerings in both Fall 2009 and Spring 2010 produces CS-101.

Natural join — ⋈

Natural join matches tuples that agree on every attribute name common to the two schemas, combines matching tuples, and emits each common attribute only once. It is equivalent to a Cartesian product, selection on equality of common attributes, and projection to remove duplicate copies of those attributes.

instructor ⋈ teaches

Here, the common attribute is ID. The output contains instructor-course pairs with matching IDs; it has 15 rows in the sample table shown in Figure 6.14 of the supplied text. Only instructors who have a matching tuple in teaches appear.

πname, course id(instructor ⋈ teaches)

To obtain the names and course titles for courses taught by Computer Science instructors:

πname, title(σdept name="Comp. Sci."(instructor ⋈ teaches ⋈ course))

Natural join is associative in the chapter's examples: (instructor ⋈ teaches) ⋈ course and instructor ⋈ (teaches ⋈ course) are equivalent.

Natural-join caution: every common attribute name is used for matching. If two relations share a name that should not be part of the match, a natural join may discard valid pairs. In Chapter 4's SQL syntax, the related remedy is an explicit JOIN ... USING or ON condition.

Theta join — ⋈θ

Theta join fuses a Cartesian product and a selection with a chosen predicate θ:

r ⋈θ s = σθ(r × s)

Unlike natural join, theta join does not restrict the matching condition to identically named attributes.

Assignment — ←

Assignment stores an intermediate relation in a temporary relation variable. It makes long algebraic queries easier to read as a sequential series of steps. Assignment does not add expressive power, and assigning to a permanent relation would instead be a database modification.

temp1 ← r × s
temp2 ← σr.A₁=s.A₁ ∧ … ∧ r.Aₙ=s.Aₙ(temp1)
result ← πR∪S(temp2)

Outer joins

Inner joins omit unmatched tuples. Outer joins preserve them by padding attributes contributed by the other relation with null values.

OperationWhat is preserved?Unmatched tuples
Left outer joinAll tuples from the left inputLeft tuple is retained; right-only attributes become NULL
Right outer joinAll tuples from the right inputRight tuple is retained; left-only attributes become NULL
Full outer joinAll tuples from both inputsUnmatched tuples from either side are NULL-padded

The source example's left join retains instructors Califieri, Gold, and Singh even though they have no matching teaching tuples.

A left outer join can be expressed using basic relational-algebra operations as described in the source:

r ⟕ s = (r ⋈ s) ∪ ((r − πR(r ⋈ s)) × { (NULL, …, NULL) })

The null-only constant relation is on the attributes of S − R, meaning attributes from the right schema not supplied by the left. The same general idea applies symmetrically to right and full outer joins. Outer-join results can contain nulls, so operations over such results need an explicit understanding of null semantics.

6.1.4 Extended relational-algebra operations

Generalized projection

Generalized projection extends ordinary projection by allowing expressions (not just attribute names) in the projection list. Expressions can use constants, arithmetic operators, and functions such as string operations when supported by the model.

πID, name, dept name, salary ÷ 12(instructor)

This returns each instructor's ID, name, department, and monthly salary.

Aggregation and grouping — 𝒢

Aggregation applies functions such as sum, avg, count, min, and max to a collection of values and returns a summary value. The relation-algebra aggregate symbol is calligraphic 𝒢; its subscript gives the aggregates and optional grouping attributes.

One aggregate for the whole relation

𝒢sum(salary)(instructor)

All instructors form one group; the result is one row containing the total salary.

Aggregate within each department

dept name 𝒢avg(salary)(instructor)

Tuples with the same department name form a group; the result has one average per department.

For the sample instructor data, the department averages shown in the supplied text are Biology 72,000; Comp. Sci. 77,333; Elec. Eng. 80,000; Finance 85,000; History 61,000; Music 40,000; Physics 91,000.

To count distinct instructors who taught in Spring 2010:

𝒢count-distinct(ID)(σsemester="Spring" ∧ year=2010(teaches))

Grouping attributes identify groups: values of all group attributes are the same within a group and differ across groups. With no grouping attributes, the entire input is a single group. The collection being aggregated is a multiset—duplicate occurrences may count. For example, on {1, 1, 3, 4, 4, 11}, sum = 24, average = 4, count = 6, minimum = 1, and maximum = 11.

Multiset relational algebra

Basic relational algebra treats relations as sets, whereas SQL permits duplicate rows. Multiset relational algebra models duplicates by tracking the number of copies of each tuple.

  • If a tuple occurs c₁ times in r₁ and satisfies selection, it occurs c₁ times after selection.
  • Projection maps every tuple copy to a projected tuple copy; different source tuples may therefore create duplicate projected values.
  • If tuple t₁ has c₁ copies in r₁ and t₂ has c₂ copies in r₂, their concatenated tuple has c₁ × c₂ copies in r₁ × r₂.
r₁ = {(1,a), (2,a)} r₂ = {(2), (3), (3)}
πB(r₁) = {(a), (a)}
πB(r₁) × r₂ = {(a,2), (a,2), (a,3), (a,3), (a,3), (a,3)}

Multiset union, intersection, and difference can be defined analogously to SQL's duplicate-aware set operators. Aggregation already works over multisets.

SQL and relational algebra

A basic SQL query and its corresponding multiset-algebra shape are connected as follows:

SELECT A₁, A₂, …, Aₙ
FROM r₁, r₂, …, rₘ
WHERE P
πA₁, A₂, …, Aₙ(σP(r₁ × r₂ × … × rₘ))

If SQL omits WHERE, the predicate is true. A grouped SQL query using GROUP BY A₁, A₂ and SUM(A₃) corresponds to product, selection, projection/group-key retention, and aggregation over the relevant attributes. Subqueries in SQL's WHERE or SELECT do not map as straightforwardly because basic relational algebra has no direct subquery operator.

6.2 The Tuple Relational Calculus

Tuple relational calculus (TRC) is nonprocedural: it states the conditions a result tuple must satisfy without prescribing an algorithm that constructs the result.

{ t | P(t) }

Read this as: “the set of all tuples t for which predicate P(t) is true.” The notation t[A] denotes the value of tuple t on attribute A; t ∈ r means tuple t belongs to relation r.

Unlike algebra, TRC describes a qualifying result rather than listing the operations to perform.

6.2.1 Example queries

All instructor tuples with salary above 80,000

{ t | t ∈ instructor ∧ t[salary] > 80000 }

Because t is constrained to be an instructor tuple, the result consists of complete instructor tuples meeting the salary predicate.

IDs of instructors with salary above 80,000

{ t | ∃ s ∈ instructor (t[ID] = s[ID] ∧ s[salary] > 80000) }

The existential clause ∃ s ∈ instructor (Q(s)) means there exists a tuple s in instructor for which Q(s) is true. The output tuple t has only the ID attribute, so the result schema is (ID).

Names of instructors whose department is in the Watson building

{ t | ∃ s ∈ instructor (t[name] = s[name] ∧
∃ u ∈ department (u[dept name] = s[dept name] ∧ u[building] = "Watson")) }

First find a department tuple located in Watson; then match instructor tuples by department name and return the instructor name. The supplied example result is Einstein, Crick, and Gold.

Courses offered in Fall 2009 or Spring 2010

{ t | ∃ s ∈ section (t[course id] = s[course id] ∧ s[semester] = "Fall" ∧ s[year] = 2009)
∨ ∃ u ∈ section (t[course id] = u[course id] ∧ u[semester] = "Spring" ∧ u[year] = 2010) }

Logical OR (∨) represents membership in either semester's course set. Since the result is a mathematical set, a course offered in both semesters appears once.

Courses offered in both semesters

Change the OR (∨) in the preceding expression to AND (∧): the course ID must satisfy both existence conditions.

Courses offered in Fall 2009 but not Spring 2010

{ t | ∃ s ∈ section (t[course id] = s[course id] ∧ s[semester] = "Fall" ∧ s[year] = 2009)
∧ ¬∃ u ∈ section (t[course id] = u[course id] ∧ u[semester] = "Spring" ∧ u[year] = 2010) }

Negated existence excludes any course ID that has a qualifying Spring 2010 section.

Students who have taken every Biology course

{ t | ∃ r ∈ student (r[ID] = t[ID]) ∧
∀ u ∈ course (u[dept name] = "Biology" ⇒
∃ s ∈ takes (t[ID] = s[ID] ∧ s[course id] = u[course id])) }

For every Biology course, there must exist a takes tuple matching that course ID and the candidate student's ID. The source highlights an important edge case: if no Biology courses exist, the universal condition is vacuously true for every student, which is why the query separately restricts t[ID] to actual student IDs.

6.2.2 Formal definition

A TRC expression has the form {t | P(t)}. A tuple variable is free unless quantified by ∃ or ∀; a quantified variable is bound. For example, in t ∈ instructor ∧ ∃ s ∈ department (t[dept name] = s[dept name]), t is free and s is bound.

Atomic formulas

  • s ∈ r: tuple variable s belongs to relation r.
  • s[x] θ u[y]: attribute values from tuple variables are compared.
  • s[x] θ c: a tuple attribute is compared with a constant.

Here, θ may be <, ≤, =, ≠, >, ≥, where the corresponding attribute domains can be compared.

Building formulas

  • An atom is a formula.
  • If P₁ is a formula, then ¬P₁ and (P₁) are formulas.
  • If P₁ and P₂ are formulas, then P₁ ∨ P₂, P₁ ∧ P₂, and P₁ ⇒ P₂ are formulas.
  • If P₁(s) is a formula, then ∃ s ∈ r (P₁(s)) and ∀ s ∈ r (P₁(s)) are formulas.

P₁ ∧ P₂¬(¬P₁ ∨ ¬P₂)Both predicates hold

6.2.3 Safety of expressions

Some unrestricted calculus expressions can generate infinite results. For instance:

{ t | ¬(t ∈ instructor) }

includes every tuple that is not in instructor, including tuples containing values never mentioned in the database. The chapter therefore introduces the domain of a formula, written dom(P): all values explicitly mentioned in the formula or appearing in tuples of relations named in it.

Safety rule: an expression {t | P(t)} is safe if every value appearing in its result comes from dom(P). Safe expressions are guaranteed to produce finite results. The unrestricted negation-only expression above is unsafe.

6.2.4 Expressive power

The safe tuple relational calculus has the same expressive power as basic relational algebra (using union, difference, product, selection, and projection, without extended operations such as aggregation). Each basic algebra expression has an equivalent safe TRC expression and vice versa. The chapter notes that aggregation is not built into this calculus, though it can be extended; arithmetic expressions can also be added in a straightforward way.

6.3 The Domain Relational Calculus

Domain relational calculus (DRC) is another nonprocedural language. Instead of variables representing entire tuples, it uses domain variables that represent individual attribute values.

Its theoretical role is similar to tuple calculus, but its variable granularity is different. The supplied text identifies DRC as a theoretical basis for QBE (Query-By-Example), just as relational algebra underlies SQL.

6.3.1 Formal definition

{ ⟨x₁, x₂, …, xₙ⟩ | P(x₁, x₂, …, xₙ) }

The result is a set of value-tuples for which predicate P holds. An atom may have one of these forms:

  • ⟨x₁, x₂, …, xₙ⟩ ∈ r: the value tuple belongs to an n-attribute relation.
  • x θ y: compare two domain variables.
  • x θ c: compare a domain variable with a constant.

The comparison operator θ is drawn from <, ≤, =, ≠, >, ≥, with compatible domains.

Formulae are built from atoms using negation, conjunction, disjunction, implication, and quantifiers. In DRC, quantification ranges over domain values rather than requiring a tuple variable to be bound directly to a relation. A shorthand such as ∃ a,b,c (P(a,b,c)) means nested quantification: ∃a(∃b(∃c(P(a,b,c))) ).

6.3.2 Example queries

All instructor fields where salary exceeds 80,000

{ ⟨i,n,d,s⟩ | ⟨i,n,d,s⟩ ∈ instructor ∧ s > 80000 }

Here i, n, d, and s represent instructor ID, name, department, and salary values.

IDs of instructors whose salary exceeds 80,000

{ ⟨i⟩ | ∃ n,d,s (⟨i,n,d,s⟩ ∈ instructor ∧ s > 80000) }

The tuple of output values contains only the ID. The source excerpt's displayed version of this example uses a variable resembling the name variable in its result tuple; the expression above uses the ID variable consistently with the stated request.

Instructor names and course IDs for Physics instructors

{ ⟨n,c⟩ | ∃ i,sec,sem,yr,dep,sal (
⟨i,c,sec,sem,yr⟩ ∈ teaches ∧
⟨i,n,dep,sal⟩ ∈ instructor ∧ dep = "Physics") }

This matches the instructor and teaching records using the ID value, restricts the instructor's department to Physics, and returns the name and course ID.

Courses in Fall 2009 or Spring 2010

{ ⟨c⟩ | ∃ a,sec,sem,yr,b,room,slot (
⟨c,sec,sem,yr,b,room,slot⟩ ∈ section ∧ sem="Fall" ∧ yr=2009)
∨ ∃ sec₂,sem₂,yr₂,b₂,room₂,slot₂ (
⟨c,sec₂,sem₂,yr₂,b₂,room₂,slot₂⟩ ∈ section ∧ sem₂="Spring" ∧ yr₂=2010) }

The common value c is required to occur in either qualifying set of sections. A course occurring in both remains a single member of the result set.

Students who have taken all Biology courses

{ ⟨i⟩ | ∃ n,d,tc (⟨i,n,d,tc⟩ ∈ student) ∧
∀ x,title,dep,credits (
⟨x,title,dep,credits⟩ ∈ course ∧ dep="Biology" ⇒
∃ sec,sem,yr,grade (⟨i,x,sec,sem,yr,grade⟩ ∈ takes)) }

The outer membership condition restricts the output to actual student IDs. For every Biology course tuple, the predicate requires a matching enrolment by that student. If there are no Biology courses, the universal condition is true for every student, matching the vacuous-truth note in the supplied text.

6.3.3 Safety of expressions

As in tuple calculus, unsafe DRC expressions can permit infinitely many values not found in the database. The expression below is unsafe because its result can contain arbitrary values outside the domain of the expression:

{ ⟨i,n,d,s⟩ | ¬(⟨i,n,d,s⟩ ∈ instructor) }

DRC safety must also restrict the values considered by quantifiers. For an expression {⟨x₁,…,xₙ⟩ | P}, the source gives three conditions:

  1. All values in result tuples must come from dom(P).
  2. For each existential subformula ∃ x (P₁(x)), truth is determined by whether some value x from dom(P₁) satisfies P₁.
  3. For each universal subformula ∀ x (P₁(x)), the predicate must hold for every value x from dom(P₁).

These restrictions make the quantified search finite, instead of requiring consideration of infinitely many possible values.

6.3.4 Expressive power

Safe domain relational calculus and safe tuple relational calculus have the same expressive power. Therefore, the following three languages are equivalent in expressive power when restricted as indicated:

  • Basic relational algebra (without extended operations)
  • Tuple relational calculus restricted to safe expressions
  • Domain relational calculus restricted to safe expressions

As with tuple calculus, DRC does not directly include the aggregation operation, although extensions can add aggregation and arithmetic expressions.

6.4 Summary

  • Relational algebra gives relation-to-relation operations that can be composed to express queries.
  • Its operations include basic operations, additional operations definable from them, and extended operations—some of which add expressive power.
  • Commercial database systems use more convenient syntax; SQL, covered in Chapters 3–5 of the supplied textbook, is strongly connected to relational algebra.
  • Tuple and domain relational calculus are nonprocedural languages that express conditions a result must satisfy.
  • Basic relational algebra and both relational calculi restricted to safe expressions have equivalent expressive power.
  • The calculi' concise formal notation is not intended as casual end-user syntax; the source connects them to user-friendlier approaches such as QBE and Datalog in Appendix B.

1. What is the difference between selection and projection?

Selection (σ) filters tuples by a predicate. Projection (π) chooses output attributes and, in set-based relational algebra, eliminates duplicate result tuples.

2. What makes two relations compatible for union or difference?

They must have the same arity, and corresponding attributes must have the same or compatible domains.

3. Why is a Cartesian product often followed by selection?

The product makes every pair of tuples. A selection predicate, often equality on matching IDs, discards unrelated pairings.

4. How do natural join and outer join differ?

Natural join retains only matching pairs and removes duplicate common attributes. An outer join additionally preserves specified unmatched tuples by padding the other side's attributes with NULL.

5. What do ∃ and ∀ mean in tuple calculus?

∃ means at least one tuple in the named relation satisfies the predicate. ∀ means every tuple in the named relation satisfies it.

6. Why are safety restrictions necessary?

Without safety, a calculus expression can return infinitely many tuples or values that never occur in the database. Safety bounds outputs and quantified evaluation to values in the formula's domain.

7. State the expressive-power equivalence.

Basic relational algebra, safe tuple relational calculus, and safe domain relational calculus are equivalent in expressive power. The chapter does not treat aggregation as a built-in operation of either calculus.

8. Convert this SQL shape to relational algebra.
SELECT A1, A2
FROM r, s
WHERE r.ID = s.ID AND P;

One equivalent basic-algebra shape is:

πA₁,A₂(σr.ID=s.ID ∧ P(r × s))
