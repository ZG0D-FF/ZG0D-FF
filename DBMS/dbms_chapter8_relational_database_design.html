What is relational design trying to achieve?

A good relational design stores each fact in an appropriate place without unnecessary repetition, while still allowing the facts to be retrieved conveniently.

Normalization is not just a way to split long tables. It is a rule-driven process: understand the constraints of the real enterprise, express them as dependencies, then choose relation schemas whose structure respects those dependencies.

Redundancy

One fact is repeated in multiple rows, increasing storage and update risk.

Lossless decomposition

Splitting a relation should not create spurious tuples or lose the original information.

Dependency preservation

Important dependencies should ideally be checkable without joining decomposed tables.

Normalization trade-off

BCNF reduces FD-based redundancy strongly; 3NF can preserve dependencies when BCNF cannot.

Chapter-level distinction: losslessness concerns whether the original information can be reconstructed exactly; dependency preservation concerns whether constraints can be checked from the decomposed relations.
8.1

Features of Good Relational Designs

Relation schemas can be derived from an E-R design, but an E-R diagram does not automatically guarantee that every resulting schema is good. Enterprise rules may reveal dependencies that indicate a relation should be decomposed.

8.1.1 Larger schemas: the inst_dept example

Suppose the separate instructor and department relations are replaced by a single natural-join-like relation:

inst_dept(ID, name, salary, dept_name, building, budget)

For every instructor in a department, the department's building and budget are repeated. For example, the Computer Science department facts (Taylor, 100000) appear for instructors Katz, Srinivasan, and Brandt.

Why the combined design is problematic
ProblemWhat can happen?
RedundancyThe same department budget and building are stored once per instructor.
Update anomalyIf one repeated budget value is changed but the others are not, the database becomes inconsistent.
Insertion limitationA department with no instructor cannot be represented directly without introducing unrelated or null values.

The enterprise rule that each department name determines one budget is represented by the functional dependency:

dept_name → budget

In the combined relation, dept_name is not a superkey because one department can have several instructors. Thus the budget is repeated even though it depends only on the department name.

8.1.2 Smaller schemas: not every decomposition works

The natural decomposition of inst_dept is into instructor(ID, name, dept_name, salary) and department(dept_name, building, budget). However, a decomposition can itself be bad if the join of the pieces cannot reconstruct the original tuples exactly.

Lossy decomposition example
Decompose employee(ID, name, street, city, salary) into employee1(ID, name) and employee2(name, street, city, salary). If two employees are both named Kim, joining the decomposed relations can pair each ID with both addresses and salaries, creating false combinations. The decomposition has lost the ability to identify which Kim owns which data.

Lossless

The natural join of the projections reproduces exactly the original relation.

Lossy

The join may produce spurious tuples or otherwise fail to preserve the original association of facts.

8.2

Atomic Domains and First Normal Form (1NF)

A domain is atomic when its values are treated as indivisible units. A relation schema is in first normal form if the domains of all its attributes are atomic.

Non-atomic examples

An attribute whose value is a set of children's names, or an address treated as a composite value containing street, city, state, and ZIP.

Atomic in database use

An integer is usually atomic. A code such as CS-101 can be treated atomically when the database does not split and interpret its characters.

Atomicity depends on how the database uses a value, not merely on whether a human can see subparts inside it. Encoding a department inside an employee ID may require extra application logic and can make a department change force ID changes across the database.

Why multivalued attributes cause trouble

Storing a set of instructor IDs in each section and a set of section IDs for each instructor duplicates the teaching relationship in two places. Both copies must be updated consistently. A separate relation such as teaches(ID, course_id, sec_id, semester, year) represents each association as a tuple.

Practical nuance: some modern database systems support complex or non-atomic values. This chapter restricts its formal design discussion to first-normal-form relations.

8.3

Decomposition Using Functional Dependencies

Design reasoning needs rules about all legal instances of a relation, not just patterns noticed in one current snapshot. Those rules are expressed with keys and functional dependencies.

8.3.1 Keys and functional dependencies

Let r(R) be a relation schema and let α, β ⊆ R. The functional dependency α → β holds when any two tuples with the same values for all attributes in α must also have the same values for all attributes in β.

If t₁[α] = t₂[α], then t₁[β] = t₂[β].

A functional dependency is a constraint on every legal instance of a schema. A current instance may happen to satisfy a dependency by coincidence, even though the enterprise rules do not require it.

  • A superkey K functionally determines all attributes in R: K → R.
  • A candidate key is a minimal superkey.
  • A functional dependency α → β is trivial when β ⊆ α, for example AB → A.
  • F⁺ is the closure of F: every functional dependency logically implied by F.

In the supplied relation instance on attributes A, B, C, D, the data satisfy A → C, while C → A fails: two rows have C = c2 but different A values. A single instance can disprove a proposed dependency, but cannot by itself establish a business rule for all legal instances.

8.3.2 Boyce–Codd Normal Form (BCNF)

A schema R is in BCNF with respect to F if for every dependency α → β in F⁺, at least one condition holds:

  1. The dependency is trivial: β ⊆ α.
  2. α is a superkey for R.

The inst_dept schema violates BCNF because dept_name → building, budget holds but dept_name is not a superkey. Decomposing into instructor and department gives schemas where the determinants of their nontrivial dependencies are keys.

General BCNF decomposition rule

For a violating nontrivial FD α → β, decompose R into (α ∪ β) and (R − (β − α)).

Further decomposition may be needed if either resulting schema still violates BCNF.

8.3.3 BCNF and dependency preservation

Consider dept_advisor(s_ID, i_ID, dept_name) with the dependencies:

i_ID → dept_name
s_ID, dept_name → i_ID

These follow from the constraints that an instructor advises in one department and each student has at most one advisor per department. BCNF decomposition yields (s_ID, i_ID) and (i_ID, dept_name). Both are BCNF, but the dependency s_ID, dept_name → i_ID cannot be checked by looking at either schema alone. The decomposition is therefore not dependency preserving.

8.3.4 Third Normal Form (3NF)

A schema R is in 3NF with respect to F when, for every α → β in F⁺, at least one holds:

  1. α → β is trivial.
  2. α is a superkey of R.
  3. Every attribute in β − α belongs to some candidate key of R. The attributes do not all have to belong to the same candidate key.

BCNF is stricter: every BCNF schema is in 3NF, but some 3NF schemas are not in BCNF. The third 3NF condition relaxes the BCNF requirement in a way that enables a dependency-preserving 3NF decomposition.

8.3.5 Higher normal forms

Functional dependencies alone do not capture every cause of redundancy. If an instructor has two children's names and two independent phone numbers, storing (ID, child_name, phone_number) requires all four child/phone combinations. This is redundant even if the relation is in BCNF. Multivalued dependencies and 4NF address this kind of independent multi-valued information.

8.4

Functional-Dependency Theory

8.4.1 Closure of a set of FDs and Armstrong's axioms

F⁺ contains all dependencies logically implied by F. The core inference rules, known as Armstrong's axioms, are sound and complete.

RuleFormIntuition
Reflexivityβ ⊆ α ⇒ α → βA set determines any subset of itself.
Augmentationα → β ⇒ αγ → βγAdding the same attributes to both sides preserves the FD.
Transitivityα → β, β → γ ⇒ α → γDetermination chains can be composed.

Useful rules derived from these axioms:

  • Union: if α → β and α → γ, then α → βγ.
  • Decomposition: if α → βγ, then α → β and α → γ.
  • Pseudotransitivity: if α → β and γβ → δ, then αγ → δ.

For the example F = {A → B, A → C, CG → H, CG → I, B → H}, we can infer:

  • A → H by A → B and B → H.
  • CG → HI by union.
  • AG → I by A → C and CG → I (pseudotransitivity).

8.4.2 Closure of an attribute set

The closure α⁺ under F is the set of all attributes functionally determined by α. Compute it by starting with α and repeatedly adding the right-hand attributes of any FD whose left side is already included.

  1. Initialise result := α.
  2. For each FD γ → δ in F, if γ ⊆ result, add δ to result.
  3. Repeat until no attribute can be added.
Uses of α⁺
To test a superkey, check whether α⁺ contains every attribute of R. To test whether α → β follows from F, check whether β ⊆ α⁺.

Worked closure: With the F above, compute (AG)⁺. Start at AG; A → B adds B; A → C adds C; CG → H adds H; CG → I adds I. The result is (AG)⁺ = {A, B, C, G, H, I}, so AG is a superkey for the schema (A, B, C, G, H, I).

8.4.3 Canonical cover

A canonical cover Fc is an equivalent, simplified set of dependencies: F⁺ = Fc⁺, no dependency contains an extraneous attribute, and no two dependencies have the same left side after combining is possible.

An attribute is extraneous if removing it does not change the closure of the FD set. Test left-side and right-side attributes with care; the checks are not symmetric.

  1. Combine dependencies with identical left sides using the union rule.
  2. Test for extraneous attributes on left and right sides using the current cover.
  3. Remove extraneous attributes and discard any dependency with an empty right side.
  4. Repeat until the set stops changing.

Example: F = {A → BC, B → C, A → B, AB → C}. Combine the A dependencies; B is extraneous in AB → C; and C is extraneous on the right side of A → BC. One canonical cover is:

Fc = { A → B, B → C }
Important: a canonical cover need not be unique. Different valid simplification paths can produce different covers with the same closure.

8.4.4 Lossless decomposition

A decomposition of R into R₁ and R₂ is lossless if, for every legal instance r, joining the projections returns exactly r:

πR₁(r) ⋈ πR₂(r) = r

A sufficient and necessary test for a binary decomposition under functional dependencies is that at least one of these belongs to F⁺:

(R₁ ∩ R₂) → R₁
or
(R₁ ∩ R₂) → R₂

In plain language, the common attributes must functionally determine all attributes of at least one side. For inst_dept decomposed into instructor and department, the common attribute is dept_name; it determines the department's building and budget, making the decomposition lossless.

8.4.5 Dependency preservation

For each decomposed schema Rᵢ, restrict F⁺ to dependencies involving only attributes in Rᵢ. Let F′ be the union of these restrictions. The decomposition is dependency preserving exactly when:

F′⁺ = F⁺

Then dependencies can be checked on individual decomposed relations without joining them. One convenient sufficient condition is that each original FD can be checked directly in one component. If that simple check fails, it does not prove the decomposition is not dependency preserving; use the full test.

8.5

Algorithms for Decomposition

8.5.1 BCNF decomposition

To check a nontrivial FD α → β, compute α⁺. If α⁺ does not contain every attribute in R, α is not a superkey and the FD violates BCNF.

Testing nuance: for the original schema, checking the given set F is sufficient to detect BCNF violations. For a schema created during decomposition, a violating FD may be in F⁺ without being explicitly listed in F.

The BCNF decomposition algorithm repeatedly replaces a violating schema Rᵢ using a nontrivial dependency α → β where α is not a superkey:

Rᵢ becomes (Rᵢ − (β − α)) and (α ∪ β)

The algorithm produces a lossless decomposition. For the chapter's class schema, the dependencies course_id → title, dept_name, credits and (building, room_number) → capacity lead to the familiar three schemas:

  • course(course_id, title, dept_name, credits)
  • classroom(building, room_number, capacity)
  • section(course_id, sec_id, semester, year, building, room_number, time_slot_id)

8.5.2–8.5.3 3NF synthesis algorithm

The 3NF algorithm creates schemas from a canonical cover, rather than repeatedly splitting the original schema. Its design guarantees 3NF, dependency preservation, and losslessness.

  1. Compute a canonical cover Fc.
  2. For each FD α → β in Fc, create a schema containing α ∪ β.
  3. If no created schema contains a candidate key for R, add a schema containing any candidate key.
  4. Remove any schema that is contained in another schema.

Because each dependency gets a schema and at least one schema contains a candidate key, the method preserves dependencies and produces a lossless decomposition. The result is not necessarily unique and can sometimes be BCNF already.

8.5.4 Comparing BCNF and 3NF

PropertyBCNF3NF
RestrictionEvery nontrivial FD must have a superkey determinant.Also permits an FD when every attribute on the right but not the left belongs to a candidate key.
RedundancyStronger removal of FD-based redundancy.Some redundancy may remain.
LosslessnessBCNF decomposition algorithm is lossless.3NF synthesis is lossless.
Dependency preservationMay not be preserved.A dependency-preserving 3NF design is always obtainable.
Design priority stated in the source: aim for BCNF, losslessness, and dependency preservation. Since all three cannot always be achieved together, a common choice is between stronger normalization with BCNF and dependency preservation with 3NF.

Standard SQL does not have a general declarative FD syntax beyond key constraints such as PRIMARY KEY and UNIQUE. Assertions that could enforce more complex FDs are not supported by most widely used systems and can be expensive to test.

8.6

Decomposition Using Multivalued Dependencies

Some schemas remain redundant even after BCNF because functional dependencies do not describe every independent relationship between multi-valued facts.

8.6.1 Multivalued dependencies (MVDs)

A multivalued dependency α →→ β expresses that, for a given α value, the set of β values is independent of the values of the remaining attributes R − α − β. Unlike an FD, which restricts tuples, an MVD requires certain tuple combinations to exist.

Example schema: inst(ID, dept_name, name, street, city). An instructor can work with multiple departments and have multiple addresses. If addresses are independent of department associations, then:

ID →→ street, city

The combined relation repeats every address for every department. For instructor 22222, if the departments are Physics and Math and the addresses are North/Rye and Main/Manchester, all four department-address combinations must be represented. Omitting combinations would incorrectly imply a relationship between a particular department and a particular address.

MVD rules
Every FD implies an MVD: if α → β then α →→ β. Also, if α →→ β holds on R, then α →→ (R − α − β) holds. An MVD α →→ β is trivial if β ⊆ α or α ∪ β = R.

8.6.2 Fourth Normal Form (4NF)

A schema R is in 4NF with respect to a set D of functional and multivalued dependencies if, for every MVD α →→ β in D⁺, one of these is true:

  1. The MVD is trivial.
  2. α is a superkey for R.

Every 4NF schema is in BCNF, but a BCNF schema need not be in 4NF.

8.6.3 4NF decomposition

For a nontrivial MVD α →→ β where α is not a superkey, decompose R into:

R₁ = α ∪ β    and    R₂ = R − (β − α)

For (ID, dept_name, street, city), this yields:

  • r21(ID, dept_name)
  • r22(ID, street, city)

This decomposition is lossless under the MVD. For a binary decomposition into R₁ and R₂, the losslessness condition can be expressed as either:

(R₁ ∩ R₂) →→ R₁   or   (R₁ ∩ R₂) →→ R₂ ↑ Back to top
8.7

More Normal Forms

Beyond 4NF, project-join normal form (PJNF), called fifth normal form in some books, is associated with join dependencies. Domain-key normal form (DKNF) is associated with an even more general class of constraints.

These forms are rarely used in practice because the constraints can be difficult to reason about and lack a convenient set of sound and complete inference rules. The chapter notes that second normal form (2NF) is omitted from detailed discussion because it is mainly of historical interest.

Normal formDependency ideaDesign goal
1NFAtomic domainsAttribute values are treated as indivisible.
BCNFFunctional dependenciesEvery nontrivial FD determinant is a superkey.
3NFFunctional dependencies with candidate-key relaxationAchieve dependency-preserving, lossless designs.
4NFMultivalued dependenciesEliminate redundancy from independent multivalued facts.
PJNF / 5NFJoin dependenciesHandle further join-related redundancy.
DKNFDomain and key constraintsExpress constraints through domain and key definitions.

8.8

Database-Design Process

8.8.1 E-R modeling and normalization

A careful E-R design should generate relation schemas that need little further normalization. If functional dependencies expose a badly modeled entity—for example, dept_name → dept_address inside an instructor relation—the E-R model may need a separate department entity and a relationship to instructor.

Many-to-many relationships and multivalued attributes often naturally create separate schemas and therefore help avoid redundancy. The universal-relation approach instead starts from a single schema containing all attributes of interest and then normalizes it.

8.8.2 Naming attributes and relationships

  • Prefer the unique-role assumption: an attribute name should have a consistent meaning. Calling both a phone number and a room number simply number can make joins or queries semantically confusing.
  • Use the same name for attributes with the same meaning where that helps generalization, such as name in both instructor and student.
  • List primary-key attributes first as a practical convention, even though attribute order does not change schema meaning.
  • Name relationship schemas consistently. Singular or plural relation names are both acceptable if the chosen convention is applied consistently.

8.8.3 Denormalization for performance

Denormalization deliberately introduces redundancy to speed up important operations. For example, storing a join of course and prerequisite can make course details faster to display, but course information must be repeated and updated consistently. A materialized view is an alternative: keep normalized base relations and let the DBMS maintain a stored join result.

Denormalized table

Potentially faster reads, but application logic must keep duplicate facts consistent.

Materialized view

Stored query result with view maintenance handled by the database system; costs storage and update work.

8.8.4 Other design issues

Normalization does not catch every bad design. Temporal data are a key example, but repeated year-specific schemas and crosstab columns are also problematic.

Alternative representationProblemPreferred pattern
total_inst_2007, total_inst_2008, total_inst_2009A new relation and new queries are needed each year.total_inst(dept_name, year, size)
dept_year(dept_name, total_2007, total_2008, total_2009)Every new year changes the schema and complicates queries.Use a row per department-year; create crosstabs for display when needed.

Crosstabs are convenient for reports and spreadsheets, but are usually poor base relational designs because an attribute value is encoded in the column name.

8.9

Modeling Temporal Data

Temporal data have an associated time interval during which the data are valid. A snapshot is the value of the data at a particular point in time.

Examples include tracking instructors' past addresses, a course title changing over time, the period when a student belongs to the university, or when a prerequisite relationship becomes valid.

Representing a time-varying fact

One practical approach is to design the database initially for current facts, then add validity intervals to relations whose values change over time. A temporal course relation could be:

course(course_id, title, dept_name, start, end)
Illustrative course-title history from the source pattern
course_idtitlestartend
CS-101Introduction to Programming1985-01-012000-12-31
CS-101Introduction to C2001-01-01Before next title change
CS-101Introduction to JavaAt new title's effective date9999-12-31 (if current)

When a value changes, close the old tuple's validity interval and insert a new tuple with the new value and its start date. The source uses 9999-12-31 as an example of a far-future end date for a value that is still current; a null end date is another possible convention mentioned in the text.

Temporal functional dependencies

A regular FD such as ID → street, city may no longer hold across the entire history because one instructor can have several addresses over time. The intended rule becomes: an ID has one street and city at any given time.

X →t Y holds when every snapshot satisfies X → Y.

Design cautions

  • The original primary key may no longer uniquely identify historical tuples; adding start/end time to a key may help, but does not by itself prevent overlapping intervals.
  • A foreign key to a temporal relation must clarify whether it refers to the current value or a specific historical version.
  • If the reference must identify the value at a particular time, the referencing relation may need temporal information too.
  • If most references mean “current value,” a separate history relation (for example, instructor_history) can store older versions while the main table stores current facts.
Big idea: ordinary normalization alone does not solve temporal modeling. The designer must decide what “valid at a time” means for attributes, entities, relationships, and references.

8.10

Chapter Summary & Review Terms

  1. Good design avoids repeated information and inability to represent meaningful facts. Decompositions should be lossless.
  2. 1NF requires atomic attribute domains.
  3. Functional dependencies encode constraints on legal data and underpin BCNF and 3NF.
  4. Attribute closure tests superkeys and implied dependencies; Armstrong's axioms derive FDs.
  5. Canonical covers simplify an FD set without changing its closure.
  6. BCNF decomposition removes FD-based redundancy and is lossless, but may fail to preserve dependencies.
  7. 3NF synthesis provides a lossless, dependency-preserving design, with possible remaining redundancy.
  8. Multivalued dependencies capture independent multi-valued facts; 4NF removes the associated redundancy.
  9. PJNF and DKNF address still more general constraints but are rarely used.
  10. Design also requires consistent naming, considered denormalization, and an explicit strategy for temporal facts.

Self-check questions

1. Why is inst_dept a poor design?

It repeats building and budget for every instructor in a department, creating update anomalies. It also cannot naturally represent a department with no instructor.

2. What is the difference between a lossless and dependency-preserving decomposition?

Lossless means the join of projections exactly reconstructs the original relation. Dependency preserving means all dependencies can be enforced using the decomposed relations without needing to join them.

3. What is the key BCNF test for a nontrivial FD α → β?

α must be a superkey. Compute α⁺; if it does not contain every attribute of R, α is not a superkey and the dependency violates BCNF.

4. Why can 3NF be preferred to BCNF?

3NF always allows a lossless, dependency-preserving decomposition. BCNF may not preserve all dependencies.

5. Why can a BCNF relation still have redundancy?

BCNF addresses redundancy represented by functional dependencies. Independent multivalued facts can still produce repetition, motivating multivalued dependencies and 4NF.

6. What does attribute closure help determine?

It tests whether a set is a superkey and whether a dependency α → β is implied by F (when β ⊆ α⁺).

7. Why are separate year-specific tables often a bad design?

Each year requires schema growth and query changes. Storing year as a row attribute is more extensible; crosstabs can be generated for presentation.

8. What must temporal design clarify about a foreign key?

Whether the reference identifies the current version of a fact or a particular historical version valid at a specific point in time.

Fast recall chain: FD theory → attribute closure and candidate keys → canonical cover → BCNF / 3NF synthesis → losslessness and dependency preservation → MVDs and 4NF → design-process and temporal concerns.
