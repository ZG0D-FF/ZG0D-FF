Chapter Roadmap: How Intermediate SQL Fits Together

Intermediate SQL bridges basic table queries with multi-user enterprise database engineering. It systematically manages six interconnected dimensions:

1. Joins Determine which tuple combinations survive through explicit matching conditions and outer-join null-padding.
2. Views Shape modular data access, encapsulate complex queries, and support specialized external schemas.
3. Transactions Guarantee ACID properties so multi-statement business workflows execute atomically and durably.
4. Integrity Enforce domain checks, unique constraints, and cascading referential integrity rules across tables.
5. Types & Schemas Organize databases into distinct namespaces and user-defined domains to prevent semantic mixing.
6. Authorization Regulate authenticated access through granular privileges (GRANT, REVOKE) and reusable roles.

The join and view demonstrations throughout this guide use two standard university relations linked via the common attribute ID.

takes ID, course_id, sec_id, semester, year, grade Student Tanaka (ID 98988) has a NULL grade in BIO-301 because it has not yet been awarded.

4.1 Join Expressions Overview

A join combines tuples from two relations according to an explicit condition. In SQL, join semantics are determined by two orthogonal choices:

Join DimensionAvailable SQL OptionsOperational Purpose
Join Condition NATURAL, USING (A1, A2), ON predicate Defines which tuple pairs match across relations.
Join Type INNER, LEFT OUTER, RIGHT OUTER, FULL OUTER Determines whether unmatched non-participating tuples are discarded or preserved with NULL padding.

4.1.1 Join Conditions: ON vs. WHERE

The ON clause allows an explicit predicate over the relations being joined. 

SELECT *
FROM student JOIN takes
  ON student.ID = takes.ID;

While for an INNER JOIN this yields the identical result as placing student.ID = takes.ID in a WHERE clause, the two behave fundamentally differently in outer joins!

Crucial Semantic Difference in Outer Joins: The ON clause determines which tuples match during the join step, allowing unmatched rows from the preserved side to be generated with NULLs. In contrast, the WHERE clause executes after the join, filtering out rows from the final result set and discarding the very NULL-padded rows the outer join was designed to preserve!

4.1.2 Outer Joins: LEFT, RIGHT, and FULL

An outer join avoids data loss by preserving tuples that have no corresponding match in the joined relation.

Outer Join TypePreserved RelationMissing Attribute Treatment
LEFT OUTER JOIN All tuples from the left relation survive. Right-side columns are padded with NULL if no match exists.
RIGHT OUTER JOIN All tuples from the right relation survive. Left-side columns are padded with NULL if no match exists.
FULL OUTER JOIN All tuples from both relations survive. Unmatched attributes from either relation are padded with NULL.

Finding Students Not Enrolled in Any Course

SELECT student.ID, student.name
FROM student LEFT OUTER JOIN takes
  ON student.ID = takes.ID
WHERE takes.course_id IS NULL;

Because an enrolled student has a valid non-NULL course_id, testing takes.course_id IS NULL reliably isolates students (such as Snow) who possess zero course registrations.

4.2 Views: Virtual Relations

A view is a virtual relation defined by a query over underlying base tables or other views. 

CREATE VIEW faculty AS
SELECT ID, name, dept_name
FROM instructor;

In the standard case, the database does not compute and store a separate physical copy of the query result. Instead, it stores the view's query definition in the data catalog. Whenever a user executes a query referencing faculty, the DBMS query processor substitutes the view definition inline into the executing query tree.

4.2.3 Materialized Views & View Maintenance

A materialized view differs from a standard virtual view because its physical result set is computed and stored on disk.

DimensionStandard Virtual ViewMaterialized View
Storage Mechanism Stores only the SQL query text in the catalog; zero row storage on disk. Stores the complete query result set physically on disk as a cached table.
Query Execution Time Computed dynamically on demand; can be slow for multi-table joins or massive aggregations. Extremely fast; reads pre-aggregated results directly without table joins.
Data Freshness & Maintenance Always 100% real-time and up-to-date with underlying base tables. Subject to staleness unless refreshed immediately via triggers, log scans, or periodic batches.
View Maintenance: The automated process of refreshing a materialized view's stored rows when underlying base tables are modified. Systems often employ incremental view maintenance, computing only the mathematical delta rather than re-executing the entire query from scratch.

4.2.4 Updatability of Views

Modifying a database through a view (via INSERT, UPDATE, or DELETE) can lead to severe logical ambiguity because the change must translate unambiguously into updates on the underlying base tables.

SQL Standard Updatability Criteria: A view is legally updatable only if all of the following conditions hold:
  1. The FROM clause references exactly one base relation (no joins).
  2. The SELECT clause contains only attribute names (no expressions, calculations, or aggregate functions like SUM, AVG, or COUNT).
  3. Any attribute not listed in the SELECT clause can legally accept NULL values in the base table (or has a defined DEFAULT).
  4. The query does not contain GROUP BY or HAVING clauses.

4.3 Transactions & ACID Guarantees

A transaction is a logical unit of database work consisting of one or more SQL operations. A transaction begins implicitly with the first SQL statement and terminates with either:

  • COMMIT: Persistently records all changes into the database.
  • ROLLBACK: Completely undoes all modifications executed during the transaction, restoring the database to its pre-transaction state.

The ACID Principles

Atomicity "All or nothing": Either every operation in the transaction succeeds and commits, or all updates are rolled back with zero trace left behind.
Consistency Execution of a transaction in isolation preserves database invariants and integrity constraints (e.g., total account balances remain balanced).
Isolation Concurrent transactions execute without interfering with one another; intermediate uncommitted states remain invisible to other transactions.
Durability Once a transaction successfully commits, its changes survive permanently on non-volatile storage, even during sudden hardware crashes.

4.4 Advanced Integrity Constraints

SQL provides declarative mechanisms to guarantee consistency across multi-table relationships:

1. Attribute and Tuple Constraints

  • NOT NULL: Forbids insertion of NULL into designated attributes.
  • UNIQUE(A1, A2): Candidate key constraint ensuring no two tuples share identical values across the specified attribute combination (though NULLs are permitted in standard SQL).
  • CHECK (P): Evaluates arbitrary predicate P on every insert or update; rejected only if P evaluates strictly to FALSE (unknown/null passes).

2. Referential Integrity & Cascading Actions

CREATE TABLE course (
    course_id VARCHAR(8) PRIMARY KEY,
    dept_name VARCHAR(20),
    FOREIGN KEY (dept_name) REFERENCES department(dept_name)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

If a department's name is renamed in department, ON UPDATE CASCADE automatically propagates the new name across all referencing course tuples. If a department is deleted, ON DELETE SET NULL resets the dept_name in dependent courses to NULL.

4.5 SQL Data Types & Schemas

Beyond standard scalar types (INT, VARCHAR), intermediate SQL introduces temporal formats and user-defined domains:

  • Temporal Types: DATE (year, month, day), TIME (hour, minute, second), and TIMESTAMP (date + time + fractional seconds).
  • User-Defined Domains: 
    CREATE DOMAIN Dollars AS NUMERIC(12,2)
    CHECK (VALUE >= 0.0);
    Domains allow attaching semantic validation rules and default values to reusable column types.
  • Distinct Types: CREATE TYPE Dollars AS NUMERIC(12,2) FINAL; creates a strictly typed scalar that cannot be accidentally compared against or added to another numeric type (like Euros) without explicit casting.

4.6 SQL Authorization: GRANT, REVOKE & Roles

Database security controls which authenticated users have privileges to execute specific DDL and DML operations.

PrivilegeGranted Capability
SELECTAllows reading and querying tuples from the relation.
INSERTAllows inserting new rows; can be scoped to specific columns.
UPDATEAllows modifying existing column values.
DELETEAllows deleting tuples from the relation.
REFERENCESAllows declaring foreign key constraints referencing the table's primary key.

Granting and Revoking Privileges

GRANT SELECT, UPDATE(salary) ON instructor TO dean;
REVOKE SELECT ON instructor FROM dean;
Cascading Revocations: If user A grants a privilege to user B WITH GRANT OPTION, and B subsequently grants it to C, revoking the privilege from B by default cascades, automatically revoking it from C as well (unless RESTRICT is specified).

Role-Based Access Control (RBAC)

CREATE ROLE teaching_assistant;
GRANT SELECT ON takes TO teaching_assistant;
GRANT teaching_assistant TO 'john_doe';

Roles simplify security administration by allowing privileges to be assigned to institutional responsibilities rather than maintained individually across hundreds of employee accounts.
