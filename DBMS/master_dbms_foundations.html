1. Core DBMS Concepts vs. File-Processing Systems

A database management system is general-purpose system software that facilitates defining, constructing, manipulating, sharing, and protecting data for various applications. It emerged to solve the severe limitations of early file-processing systems where each application maintained its own private, isolated files.

Feature / Dimension Traditional File-Processing System Database Management System (DBMS)
Data & Program Independence Tight coupling: File formats are hardcoded directly into application code. Any format change breaks programs. Program-data independence: Metadata is stored in a centralized catalog; access is mediated through conceptual schemas.
Redundancy & Consistency Uncontrolled redundancy: Multiple departments duplicate the same data, leading to conflicting records and storage waste. Controlled redundancy: Data is logically unified and normalized; physical denormalization is synchronized by the engine.
Concurrency & Sharing Inadequate concurrency: Simultaneous writes overwrite each other or lock whole files, degrading performance. Robust concurrency control: Transactions guarantee ACID isolation through row-level locking or multi-versioning.
Integrity & Security Enforced in ad-hoc code: Each programmer writes custom checks, leaving high risk of corrupted or unauthorized data. Declarative constraints: The DBMS automatically enforces entity integrity, referential integrity, and role-based permissions.
The Miniworld Concept: A database models a specific, bounded aspect of the real world—referred to in database literature as the miniworld or Universe of Discourse (UoD). Changes in the miniworld are faithfully reflected as state updates in the database.

2. Three-Schema Architecture & Data Independence

Proposed by ANSI/SPARC, the three-schema architecture separates user applications from physical storage structures. It provides three distinct levels of abstraction:

The Three Schema Levels and Their Mappings

1. External Level Individual user views (VDL). Hides irrelevant data; provides tailored representations for specific groups (e.g., student grade view vs. billing view).
2. Conceptual Level Enterprise-wide logical structure (DDL). Defines entities, data types, relationships, constraints, and business rules without storage details.
3. Internal Level Physical storage schema (SDL). Specifies file allocations, record layouts, clustering, B+ tree indexes, and data compression techniques.

Physical vs. Logical Data Independence

Independence Type Definition & Mechanism Why It Matters / Difficulty
Physical Data Independence The capacity to alter the internal schema (e.g., rebuilding indexes, changing block sizes, migrating to SSDs) without changing the conceptual schema or external views. Relatively straightforward to achieve because DBMS query engines rewrite low-level access paths transparently without affecting logical query semantics.
Logical Data Independence The capacity to alter the conceptual schema (e.g., adding an attribute, splitting an entity) without modifying existing external schemas or breaking legacy user applications. Significantly harder to achieve because changing logical enterprise structures requires complex view rewrites and updated mappings so existing queries remain valid.

3. Phased ER Database Design Lifecycle

Designing a robust database requires an orderly multi-phase lifecycle. Jumping directly to creating SQL tables frequently introduces update anomalies, missing relationships, and costly schema restructuring.

The Four Main Database Design Phases

1. Requirements Analysis Interviews with domain experts to document required data entities, attributes, transactions, and business policies in textual form.
2. Conceptual Design Creation of a high-level, DBMS-independent Entity-Relationship (ER) diagram representing entities, relationships, cardinalities, and constraints.
3. Logical Design Systematic mapping of the ER schema into the implementation data model (e.g., relational tables, primary keys, and foreign keys), followed by normalization.
4. Physical Design Selection of physical storage formats, indexes (B+ trees, hash indexes), file clustering, and access paths to optimize high-frequency queries.
The Danger of Skipping Conceptual Modeling: Direct table creation leads to uncontrolled redundancy, awkward NULLs for inapplicable relationships, and severe late-stage refactoring costs once production software depends on fragile column definitions.

4. The Relational Model Formalisms

Formulated by Edgar F. Codd in 1970, the relational model represents all data uniformly as mathematical relations.

  • Domain (D): A named set of atomic (indivisible) scalar values (e.g., valid department codes: {'CS', 'EE', 'ME'}).
  • Attribute (A): The role played by a domain in a relation schema, functioning as a named column.
  • Relation Schema R(A1, A2, …, An): The blueprint specifying the relation name R and its list of attributes with their associated domains.
  • Degree (Arity): The number of attributes in the relation schema. A table with 6 columns has degree 6.
  • Tuple (t): An ordered list of values <v1, v2, …, vn> where each vi ∈ dom(Ai) or is NULL.
  • Cardinality: The current number of tuples populated in the relation instance.
  • Relation State r(R): A mathematical subset of the Cartesian product of the attribute domains: r(R) ⊆ dom(A1) × dom(A2) × … × dom(An).
Key Relational Properties:
  1. Tuples are unordered: Mathematically, a relation is a set of tuples; order has no formal meaning.
  2. No duplicate tuples: Set theory dictates every element in a set must be distinct.
  3. Attribute values are atomic: Under First Normal Form (1NF), composite or multivalued attributes are strictly prohibited in basic relational theory.

5. Keys & Integrity Constraints

Integrity constraints guarantee that data modifications do not result in inconsistency or invalid application states.

The Hierarchy of Relational Keys

Superkey (SK) Any set of attributes that uniquely identifies every tuple in a relation. May include unnecessary, redundant columns (e.g., {ID, Name, Street}).
Candidate Key (CK) A minimal superkey. Uniqueness holds, and removing any single attribute destroys the uniqueness guarantee (e.g., {ID} or {SSN}).
Primary Key (PK) The designated candidate key officially chosen by the database designer to identify tuples and be referenced by foreign keys.

Core Relational Integrity Constraints

Constraint Type Formal Requirement Violation Example & DBMS Response
Domain Constraint Every attribute value must belong to the specified data domain and type. Inserting string text into an INTEGER credit column → Rejected.
Entity Integrity No attribute participating in the primary key may ever be NULL: t[PK] ≠ NULL. Inserting a tuple with NULL in student_id → Rejected.
Referential Integrity A foreign key FK in referencing relation R1 must either match an existing primary key in referenced relation R2, or be entirely NULL. Enrolling a student with course_id = 'CS999' when that course does not exist → Rejected.
Referential Action Policies on DELETE/UPDATE:
  • RESTRICT / NO ACTION: Rejects the parent row deletion if child rows currently reference it.
  • CASCADE: Deleting the parent automatically deletes all dependent referencing child tuples.
  • SET NULL: Deleting the parent automatically sets the referencing foreign key attributes in children to NULL.
  • SET DEFAULT: Resets referencing foreign key columns to a pre-configured default value.

6. Relational Algebra Operations

Relational algebra is a formal, procedural query language where operations take one or two relations as input and produce a new relation as output.

Core Operations Overview

Operation Symbol & Syntax Type Purpose & Semantics
Selection σcondition(R) Unary Filters rows: returns only tuples satisfying the Boolean condition.
Projection ΠA1, A2(R) Unary Filters columns: outputs only designated attributes; removes duplicate rows.
Cartesian Product R × S Binary Combines every tuple of R with every tuple of S, yielding |R| × |S| rows.
Natural Join R ⊄ S Binary Equi-join over all identically-named attributes, projecting common columns once.
Set Difference R − S Binary Returns tuples present in R that do not appear in S (requires union compatibility).

Worked Step-by-Step Relational Algebra Query

Query: "Find names of all employees living in Miami earning > $100,000"

Πperson_name( σcity = 'Miami'(employee) ⊄ σsalary > 100000(works) )
Step 1: Row Selection Filter employee tuples where city = 'Miami'.
Step 2: Salary Filter Filter works tuples where salary > 100000.
Step 3: Natural Join (⊄) Join filtered sets on the shared attribute person_name.
Step 4: Projection (Π) Extract the requested person_name column, eliminating duplicate rows.

7. ER-to-Relational Logical Mapping Algorithm

Transforming an ER conceptual diagram into a relational schema follows a rigorous 7-step algorithm:

Step 1: Regular Entities Create relation R with all simple attributes. Choose key as PK.
Step 2: Weak Entities Create relation W. Include all simple attributes + foreign key pointing to owner's PK. PK of W is {Owner PK, Partial Key}.
Step 3: 1:1 Relationships Include foreign key in the relation having total participation (or merge tables if both are total).
Step 4: 1:N Relationships Place the primary key of the "1" side as a foreign key inside the relation on the "N" (many) side.
Step 5: M:N Relationships Create a dedicated relationship relation T. PK of T is composite of both entity PKs as FKs.
Step 6: Multivalued Attributes Create a new relation containing the attribute and the entity's PK as a foreign key.
Step 7: N-ary Relationships Create a relation containing the PKs of all participating entities as foreign keys.

8. Visual Reasoning & Exam Concept Maps

Exam Map 1 · Primary Key Verification Algorithm

1. Uniqueness Test Could two distinct valid tuples ever share the exact same value in future valid database states?
2. Minimality Test Can any single attribute be removed from the key candidate while uniqueness still strictly holds?
3. Non-Null Rule Is any component attribute capable of taking a NULL value? If yes, it fails entity integrity.
4. Final Designation Declare as primary key; explicitly document data assumptions if domain constraints permit duplicates.

Exam Map 2 · Classifying Constraint Violations

Entity Integrity Violation Attempting to insert a tuple with a NULL primary key component.
Referential Integrity Violation Child foreign key does not exist in parent table (on insert), or deleting parent while referenced (on delete).
Key / Uniqueness Violation Inserting a duplicate value into a column designated as primary key or unique.
Domain Constraint Violation Supplying data out of range, violating datatype, or failing CHECK predicate.

Practice 1.1 — Two Major Disadvantages of a Database System
Silberschatz Ch 1

Question:

What are two major disadvantages of utilizing a database system?

Lucid Solution:

  1. High Upfront Cost and Overhead: Acquiring enterprise DBMS software, robust server hardware, specialized administration personnel, and operational migration represents substantial financial expenditure compared to rudimentary file scripts.
  2. Complexity and Processing Overhead for Trivial Workloads: Enforcing ACID transactions, concurrency locking, logging, and security checks imposes measurable computational overhead. For tiny, single-user, read-only utilities, flat files are simpler and faster.
Exam Takeaway: A DBMS delivers multi-user sharing, transactional safety, and integrity guarantees, but incurs financial, architectural, and operational overhead.

Silberschatz Ch 1

Question:

List five ways programming language type systems (Java/C++) differ from database Data Definition Language (DDL).

Programming Language Type Declarations Database DDL (Data Definition Language)
Specify transient in-memory structures bound to process execution. Specify persistent database catalog schemas surviving process lifetimes.
Scoped to an individual program, module, or package. Globally cataloged and shared across heterogeneous enterprise applications.
Structures disappear automatically upon process termination. Definitions and data remain permanently recorded on non-volatile storage.
Cannot natively enforce cross-table relational constraints. Declaratively declares primary keys, foreign keys, and referential actions.
Any structure change requires recompiling and redeploying code. Schema mappings and metadata provide program-data independence.
Practice 1.5 — Video Platform: Actual Video Bytes vs. Video Metadata
Silberschatz Ch 1

Question:

Analyze how file processing vs. DBMS concerns apply to video payloads vs. structured metadata (title, tags, views).

Lucid Solution:

Dimension Actual Video Media Payload (BLOB) Structured Metadata (Title, Uploader, Views, Tags)
Storage Strategy Stored in optimized blob/object storage (e.g., S3/CDN); database holds immutable URI pointers. Stored in normalized relational tables with indexing on titles, categories, and tags.
Integrity & Consistency Validated via byte checksums and format codecs. Enforced via foreign keys (uploader must exist) and check constraints.
Concurrency & Transactions Read-heavy, append-only streams; cache-friendly. High-write concurrent counters (views, likes, comments) requiring transactional consistency.
Exercise 2.1 — Identifying Primary Keys in Employee Database
Silberschatz Ch 2

Question:

Determine suitable primary keys for: employee(person_name, street, city), works(person_name, company_name, salary), company(company_name, city), and manages(person_name, manager_name).

Lucid Solution:

  • employee: person_name (assuming names are unique in the miniworld; otherwise an artificial employee_id is preferred).
  • works: person_name if employees work for at most one company; (person_name, company_name) if multi-company employment is permitted.
  • company: company_name (guaranteed unique enterprise identifier).
  • manages: person_name assuming each employee reports to at most one direct supervisor.
Exercise 2.2 — Foreign Key Violation Scenarios
Silberschatz Ch 2

Question:

Give examples of insert and delete operations violating instructor.dept_name → department.dept_name.

Lucid Solution:

  1. Insert Violation: Attempting to insert an instructor with dept_name = 'Cybernetics' when 'Cybernetics' does not exist as a primary key in department.
  2. Delete Violation: Attempting to delete the 'Computer Science' department tuple while instructor records still reference 'Computer Science' (under default RESTRICT mode).
Exercise 2.4 — Sample Rows vs. General Key Proof
Silberschatz Ch 2

Question:

If no two instructors in a sample table share a name, does that prove name is a candidate key?

Lucid Solution:

No. A candidate key is a constraint on all possible future valid states of a relation, not merely a coincidence observed in a sample extension. Two instructors could easily share a name in the real world. A key must be guaranteed unique by structural enterprise rules.
