Chapter roadmap

This chapter connects six areas of intermediate SQL: joins decide which row combinations survive; views shape query results; transactions make multi-step work atomic; constraints protect consistency; types and schemas organise data; authorization controls access.

Section 4.1

Join expressions

A join combines tuples from two relations according to a matching rule. Natural join was introduced in Chapter 3; this chapter adds explicit join predicates and joins that preserve unmatched tuples.

Join condition

Specifies which tuple pairs match. SQL offers NATURAL, USING, and ON forms in the supplied excerpt.

Join type

Specifies whether nonmatching rows are discarded (INNER) or preserved on the left, right, or both sides (OUTER).

Section 4.1.1

Join conditions: ON

The ON condition allows a general predicate over the relations being joined. It is written like a WHERE predicate, but uses the keyword ON and appears at the end of the join expression.

Example: explicit join predicate 
SELECT *
FROM student JOIN takes
  ON student.ID = takes.ID;

This joins a student tuple to each takes tuple with the same ID. The result contains two columns named ID—one from student and one from takes—even though those values must match.

The following query is equivalent for this inner-join example:

SELECT *
FROM student, takes
WHERE student.ID = takes.ID;

To display the ID only once, list the desired attributes explicitly:

SELECT student.ID AS ID, name, dept name, tot cred,
       course id, sec id, semester, year, grade
FROM student JOIN takes
  ON student.ID = takes.ID;
Why have ON if WHERE can express the same condition? The ON clause makes join logic easier to read, separating it from other filters. More importantly, ON and WHERE are not interchangeable in outer joins; see Section 4.1.2.
Section 4.1.2

Outer joins

An inner join discards tuples that do not match. An outer join preserves selected nonmatching tuples by adding a result row in which attributes from the missing side are NULL.

In the source data, Snow (ID 70557) is present in student but has no tuple in takes. A natural inner join therefore omits Snow. A left outer join keeps Snow and fills the takes-only attributes with NULL.

Join typeWhat is preserved?What happens to unmatched tuples?
INNER JOINOnly tuples with a match on both sides.Discarded from the result.
LEFT OUTER JOINAll tuples from the left relation, plus matches from the right.Unmatched left tuples are retained; right-side attributes are padded with NULL.
RIGHT OUTER JOINAll tuples from the right relation, plus matches from the left.Unmatched right tuples are retained; left-side attributes are padded with NULL.
FULL OUTER JOINAll tuples from both relations.Unmatched tuples from either side are retained with missing-side attributes set to NULL.

Left outer join: retain all students

SELECT *
FROM student NATURAL LEFT OUTER JOIN takes;

The matching rows are returned as in a natural join. In addition, Snow appears with the student's values and NULL for course id, sec id, semester, year, and grade.

Find students who have not taken a course

SELECT ID
FROM student NATURAL LEFT OUTER JOIN takes
WHERE course id IS NULL;

Because a real matched takes row has a course identifier, course id IS NULL identifies student rows preserved without a matching course-taking record in this example.

Right outer join: reverse the relation order

SELECT *
FROM takes NATURAL RIGHT OUTER JOIN student;

This preserves the tuples from student, like the previous left-outer-join expression, with the result attributes arranged according to the order of the relations and join form.

Full outer join: preserve unmatched tuples from both inputs

The chapter’s example asks for all Computer Science students and all sections offered in Spring 2009, including sections not taken by a Computer Science student. The query first forms two filtered relations, then full-outer-joins them.

SELECT *
FROM (SELECT *
      FROM student
      WHERE dept name = 'Comp. Sci.')
NATURAL FULL OUTER JOIN
     (SELECT *
      FROM takes
      WHERE semester = 'Spring' AND year = 2009);
Exam point: Outer joins introduce NULL-padded tuples specifically for rows that did not contribute to the corresponding inner-join result. They do not simply mean “join, then keep every row regardless of later filters.”

Why moving ON to WHERE can change the result

Compare these two queries:

-- A: the ID match is part of the left outer join
SELECT *
FROM student LEFT OUTER JOIN takes
  ON student.ID = takes.ID;
-- B: join on TRUE, then filter in WHERE
SELECT *
FROM student LEFT OUTER JOIN takes ON TRUE
WHERE student.ID = takes.ID;

Query A preserves Snow with nulls on the takes side because Snow has no matching ID. In Query B, ON TRUE makes the join condition true for every pair, so no null-padded row is generated for Snow at the join stage. The later WHERE predicate then removes combinations whose IDs differ. Snow disappears.

Section 4.1.3

Join types and conditions

SQL separates the join type from the join condition. The keyword INNER is optional: an ordinary join without an outer prefix is an inner join. Natural join is likewise equivalent to natural inner join.

DimensionAvailable forms in this excerptRole
Join typeINNER, LEFT OUTER, RIGHT OUTER, FULL OUTERDetermines which unmatched tuples survive.
Join conditionNATURAL, USING (A1, A2, ...), ON predicateDetermines how tuples match.

For example, these two expressions are equivalent:

SELECT *
FROM student JOIN takes USING (ID);
SELECT *
FROM student INNER JOIN takes USING (ID);
Remember: NATURAL automatically uses all same-named attributes as matching attributes; USING states exactly which same-named attributes to match; ON permits a general predicate.
Section 4.2

Views

A view is a virtual relation defined by a query. It lets a user work with a tailored representation of the data without needing direct access to every underlying relation or every attribute.

Why use views?

Security

A clerk may need an instructor's ID, name, and department, but should not see salary data. A view can expose only those permitted attributes.

Personalised data representation

A user may need only Physics course sections in Fall 2009, with building and room details, rather than the complete logical model.

Why not store every query result as a normal relation? If the underlying instructor, course, or section data changes, a separately stored result can become stale. A normal view stores the query definition and computes the result when the view is used.
Section 4.2.1

View definition

The general form of a view definition is:

CREATE VIEW view_name AS
<query expression>;

The view name identifies the virtual relation; the query expression defines its contents.

Example 1: hide instructor salaries

CREATE VIEW faculty AS
SELECT ID, name, dept name
FROM instructor;

The faculty view conceptually contains the tuples produced by the query, but the normal view is not precomputed and stored. The database stores the defining query and computes the view relation when it is accessed.

Example 2: Physics sections in Fall 2009

CREATE VIEW physics_fall_2009 AS
SELECT course.course id, sec id, building, room number
FROM course, section
WHERE course.course id = section.course id
  AND course.dept name = 'Physics'
  AND section.semester = 'Fall'
  AND section.year = 2009;

This view combines course and section data, then restricts it to Physics offerings from Fall 2009.

Give derived attributes meaningful names

When a selected expression such as SUM(salary) has no convenient attribute name, a view can specify the view attribute names explicitly.

CREATE VIEW departments_total_salary (dept name, total salary) AS
SELECT dept name, SUM(salary)
FROM instructor
GROUP BY dept name;

Build a view from another view

CREATE VIEW physics_fall_2009_watson AS
SELECT course id, room number
FROM physics_fall_2009
WHERE building = 'Watson';

The definition reuses the earlier physics_fall_2009 view. Conceptually, the database can substitute the defining query of that earlier view into the new view's definition.

Section 4.2.2

Using views in SQL queries

A view name can be used wherever a relation name may appear. Querying a view is conceptually querying the relation returned by its defining query.

For example, to find Physics courses offered in the Watson building in Fall 2009:

SELECT course id
FROM physics_fall_2009
WHERE building = 'Watson';

The view's defining query supplies the relevant columns and rows; the outer query adds the building condition.

How nested views connect

  1. Define the base view. physics_fall_2009 joins course and section information and filters by department, semester, and year.
  2. Define the narrower view. physics_fall_2009_watson selects the course ID and room number for Watson-building rows from the first view.
  3. Evaluate when referenced. The view definition is expanded conceptually into the surrounding query; the result reflects the underlying data at evaluation time.
Exam phrase: A normal view is defined by a query; the system stores the view definition and recomputes the result when the view is accessed. Do not confuse this with a materialized view.
Section 4.2.3

Materialized views

A materialized view stores the result of a view query. If the underlying relations change, the stored result must be maintained so that it corresponds to the defining query.

For the view departments_total_salary, inserting or deleting an instructor—or changing an instructor's salary—can change the stored total for the relevant department.

View maintenance strategies described in the source

StrategyWhen maintenance occursImplication
ImmediateWhen an underlying relation is updated.The materialized result is maintained at update time.
LazyWhen the view is accessed.Maintenance work is deferred until use.
Periodic recomputationAt intervals selected by the system or administrator.The stored result may be stale between refreshes.

Potential benefits

Frequently used views may be faster when stored. Queries that aggregate large relations can be answered quickly from a much smaller stored aggregate result.

Costs and risks

Materialization uses storage and adds overhead to updates. If refresh is periodic, the result may be stale and unsuitable when current data is required.

Standardisation note from the source: SQL does not define one standard way to declare a materialized view. Database systems may provide their own extensions and different maintenance policies.
Section 4.2.4

Update of a view

Queries through a view are often straightforward, but updates are harder: a change expressed against a virtual relation must be translated into changes to the actual underlying relations. Sometimes that translation is ambiguous or cannot produce the requested view result.

Case 1: an insertion omits an underlying attribute

Consider the faculty view that exposes ID, name, and department but not salary:

CREATE VIEW faculty AS
SELECT ID, name, dept name
FROM instructor;

A user attempts:

INSERT INTO faculty
VALUES ('30765', 'Green', 'Music');

The underlying instructor relation also requires a salary value. The source describes two reasonable responses:

  • Reject the insertion and return an error.
  • Insert ('30765', 'Green', 'Music', NULL) into instructor.

Case 2: the requested view tuple cannot be represented by underlying rows

The source defines a view combining instructor and department data:

CREATE VIEW instructor_info AS
SELECT ID, name, building
FROM instructor, department
WHERE instructor.dept name = department.dept name;

Suppose a user inserts:

INSERT INTO instructor_info
VALUES ('69987', 'White', 'Taylor');

If no instructor with ID 69987 exists and no department is in building Taylor, attempting to use NULL values in the underlying instructor and department relations still does not create the requested join result. The insertion cannot be translated into underlying tuples that make the intended row appear in the view.

Why updates are restricted: One row in a view may depend on more than one base relation, or omit attributes needed to create a valid base tuple. An apparently simple view change may not have a unique, correct translation.

When does the source describe a view as updatable?

The excerpt gives the following conditions for a view to be updatable in general:

  1. The FROM clause has only one database relation.
  2. The SELECT clause contains only attribute names from that relation—no expressions, aggregates, or DISTINCT.
  3. Every base-relation attribute omitted from the view can be set to NULL; it must not have a NOT NULL constraint and must not be part of a primary key.
  4. The query has no GROUP BY or HAVING clause.

The following view fits the stated pattern:

CREATE VIEW history_instructors AS
SELECT *
FROM instructor
WHERE dept name = 'History';

Use WITH CHECK OPTION to enforce the view condition

Even when a view is updatable, an inserted row might fail the view's own filter. For example, the source notes that inserting a Biology instructor into the history_instructors view could place the tuple in instructor without making it appear in the view. By default, the source says SQL would allow this operation.

CREATE VIEW history_instructors AS
SELECT *
FROM instructor
WHERE dept name = 'History'
WITH CHECK OPTION;

With WITH CHECK OPTION, inserts are rejected if the inserted tuple does not satisfy the view's WHERE condition; updates are similarly rejected if their new values no longer satisfy it.

Do not overgeneralise: These are the conditions and examples stated in the supplied excerpt. It also notes that SQL:1999 has more complex rules permitting updates through a broader class of views, and that database systems differ in their supported behaviour.
4.3 · Reliability of multi-step work

4.3 Transactions

A transaction is a sequence of query and/or update statements treated as one indivisible unit of database work. The aim is to avoid leaving the database in a partially updated, inconsistent state.

COMMIT WORK

Makes all updates performed by the current transaction permanent. A new transaction starts automatically. Once committed, its effects cannot be undone by ROLLBACK WORK.

ROLLBACK WORK

Undoes the updates performed by the current transaction and restores the database state to what it was before the transaction's first statement.

The keyword WORK is optional in both statements. The SQL standard says a transaction begins implicitly when an SQL statement is executed and must end with a commit or rollback. If a program terminates without either statement, the standard does not dictate whether its changes are committed or rolled back; that choice is implementation-dependent.

Why atomicity matters

Imagine transferring money between two accounts. The transaction must debit one account and credit the other. A crash between those updates could otherwise lose or create money. The same risk appears in the university example: recording a successful course completion in takes and updating the student's tot cred must succeed together.

-- Illustrative transaction body; transaction-start syntax is implementation-dependent
UPDATE account
SET balance = balance - 500
WHERE account_number = 'A';

UPDATE account
SET balance = balance + 500
WHERE account_number = 'B';

COMMIT WORK;

The example shows the two logically linked updates described in the source. On an error, the application should roll back the transaction rather than commit a partial transfer.

  1. Success path: execute all statements, then commit so all effects become permanent.
  2. Error or incomplete path: roll back so earlier updates do not remain as a partial result.
  3. Failure recovery: the DBMS guarantees that uncommitted transaction effects are rolled back after a failure; after a system crash, this recovery occurs when the system restarts.
Autocommit caveat: Many SQL implementations treat each statement as its own transaction by default and commit it immediately. Autocommit must be disabled when several statements need to form one transaction; how this is configured depends on the implementation. The source also describes SQL:1999's BEGIN ATOMIC ... END form, which is supported by only some implementations.
4.4 · Rules that protect consistency

4.4 Integrity Constraints

Integrity constraints are conditions that database changes must preserve. They guard against accidental data inconsistency, even when changes are made by authorised users.

Example requirementConstraint idea
An instructor's name cannot be absent.NOT NULL
No two instructors share the same instructor ID.PRIMARY KEY (or a suitable UNIQUE constraint with non-null handling)
Every course department must exist in department.Foreign key / referential integrity
A department budget must be positive.CHECK (budget > 0)

Constraints are usually identified during schema design and declared in CREATE TABLE. The source notes that one may also add a constraint to an existing relation with ALTER TABLE table_name ADD CONSTRAINT ...: the system first checks the existing relation; if it violates the new rule, the command is rejected.

4.4.1–4.4.3 · NOT NULL and UNIQUE

name   VARCHAR(20) NOT NULL,
budget NUMERIC(12,2) NOT NULL,
UNIQUE (email)

NOT NULL prohibits a missing value for that attribute. Primary-key attributes are already required to be both unique and non-null. In contrast, UNIQUE (A1, ..., An) specifies a candidate-key-like condition: no two tuples may be equal on all listed attributes. Under the source's description, the attributes in a UNIQUE constraint may still contain NULL unless separately declared NOT NULL; remember that SQL's treatment of null values differs from ordinary equality.

4.4.4 · The CHECK clause

CHECK(P) requires each tuple to satisfy predicate P. It can restrict allowed values in a domain-like fashion.

CREATE TABLE department (
  dept_name VARCHAR(20) PRIMARY KEY,
  building  VARCHAR(15),
  budget    NUMERIC(12,2) CHECK (budget > 0)
);

CREATE TABLE section (
  course_id VARCHAR(8),
  sec_id    VARCHAR(8),
  semester  VARCHAR(6)
            CHECK (semester IN ('Fall', 'Winter', 'Spring', 'Summer')),
  year      NUMERIC(4,0)
            CHECK (year > 1759 AND year < 2100),
  PRIMARY KEY (course_id, sec_id, semester, year)
);

The semester constraint simulates an enumerated type. Although the SQL standard allows a CHECK predicate to contain a subquery, the source reports that widely used database products generally do not support subqueries in CHECK predicates.

4.4.5 · Referential integrity and foreign keys

Referential integrity requires values in a referencing relation to match corresponding values in a referenced relation. More formally, for every tuple in the referencing relation, its non-null foreign-key values must match a referenced key value. This is also called a subset dependency: the set of referencing values must be a subset of the referenced key values.

CREATE TABLE course (
  course_id VARCHAR(8) PRIMARY KEY,
  title     VARCHAR(50),
  dept_name VARCHAR(20),
  credits   NUMERIC(2,0) CHECK (credits > 0),
  FOREIGN KEY (dept_name) REFERENCES department(dept_name)
);

In the usual short form, a foreign key references the primary key of the target table. The referenced columns may be named explicitly, but must be a candidate key declared with a primary-key or UNIQUE constraint. Corresponding key columns must be type-compatible and have matching arity.

What happens when a referenced row changes?

ActionEffect described by the source
Default behaviourReject the delete/update that would violate referential integrity; the transaction performing it is rolled back.
ON DELETE CASCADEDeleting a referenced department also deletes referencing course rows.
ON UPDATE CASCADEChanging the referenced key propagates the new value to referencing rows.
ON DELETE/UPDATE SET NULLSet the referencing field to NULL when the action would otherwise violate the constraint.
SET DEFAULTSet the referencing field to its domain's default value.

Cascades can propagate across a chain of foreign-key dependencies. If a cascade cannot resolve a resulting constraint violation, the system aborts the transaction and undoes its changes. Foreign-key columns may be nullable unless separately restricted; if any column of a composite foreign key is null, the source says the tuple automatically satisfies the constraint.

4.4.6 · Constraint checks within a transaction

A multi-step transaction can temporarily violate a constraint even though its completed state satisfies it. The source's example uses two people, John and Mary, whose spouse attributes reference each other. Inserting either first appears to violate the foreign key; after both are inserted, the constraint holds.

  • INITIALLY DEFERRED specifies that the constraint is checked at the end of the transaction.
  • DEFERRABLE means the constraint is checked immediately by default, but can be deferred when desired.
  • SET CONSTRAINTS constraint_list DEFERRED defers checking of the named deferrable constraints until the transaction ends.

Immediate checking is the default, and the source warns that many implementations do not support deferred constraint checking. Where permitted, inserting both rows initially with a nullable spouse value and updating them afterward is an alternative, but it requires nullable attributes and extra work.

4.4.7 · Complex checks and assertions

A cross-table rule can be harder to express with a basic foreign key. The source gives the example of ensuring that every section.time_slot_id exists in a time_slot relation. A subquery-based check would need to be re-evaluated when the referenced time_slot data changes too—not just when section changes.

An assertion is a predicate describing a condition that the database must always satisfy. Domain and referential-integrity constraints are special forms of assertions, while general assertions express broader rules.

CREATE ASSERTION credits_earned CHECK (
  NOT EXISTS (
    SELECT ID
    FROM student
    WHERE tot_cred <> (
      SELECT SUM(credits)
      FROM takes NATURAL JOIN course
      WHERE student.ID = takes.ID
        AND grade IS NOT NULL
        AND grade <> 'F'
    )
  )
);

This presents the intent of the source's Figure 4.9 in a readable, parenthesised layout: each student's stored total credits should equal credits for successfully completed courses. The excerpt's extracted figure has incomplete punctuation, so do not treat its printed layout as a copy-ready tested statement.

The source also gives the rule that an instructor must not teach in two different classrooms in the same semester at the same time slot as another assertion example. General assertions and subquery-based checks can be costly to test, and the excerpt states that widely used systems generally do not support either subqueries in CHECK or CREATE ASSERTION; triggers may provide equivalent functionality where available.

4.5 · Representing and organising data

4.5 SQL Data Types and Schemas

Beyond numeric and character types, SQL includes date/time types, defaults, large-object storage, user-defined types and domains, table-creation extensions, and a hierarchy for naming database objects.

4.5.1 · Date and time types

TypeMeaningExample
DATECalendar year, month and day.DATE '2001-04-25'
TIMETime of day; TIME(p) controls fractional-second precision. A time-zone variant is available.TIME '09:30:00'
TIMESTAMPCombined date and time; TIMESTAMP(p) controls fractional-second precision. A time-zone variant is available.TIMESTAMP '2001-04-25 10:29:01.45'
INTERVALRepresents a duration used in date/time arithmetic.x - y for dates produces an interval.

Date literals use year-month-day order. SQL provides CAST to convert a string expression to DATE, TIME or TIMESTAMP; EXTRACT(field FROM value) can obtain fields such as year, month, day, hour, minute or second. The source lists CURRENT_DATE, CURRENT_TIME, LOCALTIME, CURRENT_TIMESTAMP and LOCALTIMESTAMP for current date/time values. Dates and times can be compared, and adding/subtracting intervals performs date/time arithmetic.

4.5.2 · Default values

CREATE TABLE student (
  ID       VARCHAR(5) PRIMARY KEY,
  name     VARCHAR(20) NOT NULL,
  dept_name VARCHAR(20),
  tot_cred NUMERIC(3,0) DEFAULT 0
);

INSERT INTO student (ID, name, dept_name)
VALUES ('12789', 'Newman', 'Comp. Sci.');

Because no value is supplied for tot_cred, the default 0 is used. A default differs from NULL: it supplies the specified fallback value when the insertion omits the attribute.

4.5.3 · Index creation

An index is a data structure that helps the DBMS locate tuples with a specified attribute value without scanning every tuple. It is useful when a query selects a small part of a large relation.

CREATE INDEX studentID_index ON student(ID);

The query processor may use the index automatically when it benefits a query. An index can cover one attribute or a list of attributes. The source notes that SQL does not formally define a standard syntax for index creation, even though many systems support forms like the example. Index implementation, including B+-tree indexes, is covered later in the textbook.

4.5.4 · Large-object types

Applications may need to store large character or binary values such as reviews, photographs, medical images or video clips. SQL therefore provides CLOB (character large object) and BLOB (binary large object).

book_review CLOB(10KB)
image       BLOB(10MB)
movie       BLOB(2GB)

Fetching a multi-megabyte or gigabyte object in full may be impractical. Instead, an application may retrieve a locator and fetch the content in smaller pieces, much like reading portions of a file.

4.5.5 · User-defined types and domains

SQL distinct types help detect semantically incorrect assignments even when their underlying representations are the same. The source's currency example defines separate types for dollars and pounds:

CREATE TYPE Dollars AS NUMERIC(12,2) FINAL;
CREATE TYPE Pounds  AS NUMERIC(12,2) FINAL;

Both use a numeric representation, but a strongly typed system can reject assigning a value of type Dollars to a variable or attribute of type Pounds. A cast can convert a value to an underlying numeric type for an operation; saving it back to a distinct type may require another cast.

A domain is similar but not identical. Domains can carry constraints and defaults; they are not strongly typed in the same way, so values of different domains can be assignment-compatible when their underlying types are compatible.

CREATE DOMAIN DDollars AS NUMERIC(12,2) NOT NULL;

CREATE DOMAIN YearlySalary AS NUMERIC(8,2)
  CONSTRAINT salary_value_test
  CHECK (VALUE >= 29000.00);

CREATE DOMAIN degree_level AS VARCHAR(10)
  CONSTRAINT degree_level_test
  CHECK (VALUE IN ('Bachelors', 'Masters', 'Doctorate'));
Distinct typeDomain
Designed to separate semantically different value types, even with the same underlying representation.Can constrain values using rules such as NOT NULL and CHECK.
Constraints/defaults are not specified on the user-defined type in the source's model.Can specify constraints and defaults; values remain more assignment-compatible when the underlying types are compatible.

Implementation note from the source: type/domain support varies. It describes PostgreSQL as supporting domains but using a different CREATE TYPE syntax, DB2 and SQL Server as having their own variants, and Oracle as not supporting these constructs in exactly the forms shown. Check the chosen DBMS manual.

4.5.6 · Creating tables from existing definitions or query results

CREATE TABLE temp_instructor LIKE instructor;

CREATE TABLE t1 AS
  (SELECT *
   FROM instructor
   WHERE dept_name = 'Music')
WITH DATA;

CREATE TABLE ... LIKE creates a table with the schema of an existing table. CREATE TABLE ... AS creates a table from a query result; column names and types are inferred unless specified. Under the SQL:2003 description in the source, omitting WITH DATA creates the table without populating it, although implementations may populate by default. Unlike a view, the new table's contents are fixed at creation and do not automatically reflect later changes to the source relations.

4.5.7 · Schemas, catalogs and environments

Database objects use a naming hierarchy similar to directories in a file system. Catalogs can contain schemas; schemas contain objects such as relations and views. Some systems use the word database where the standard uses catalog.

An object can be named with a three-part name such as catalog5.univ_schema.course. If the catalog is the connection's default catalog, it may be omitted; if the object is in the default schema, the schema can also be omitted. A connection's SQL environment includes the user identifier and default catalog/schema. The source describes CREATE SCHEMA and DROP SCHEMA, while catalog creation/deletion is implementation-dependent and not part of the SQL standard as presented.

4.6 · Who may do what?

4.6 Authorization

Authorization controls what a database user may read or change. The DBMS checks privileges when a query or update is submitted; an unauthorised operation is rejected.

Data privileges in the source include reading (SELECT), inserting (INSERT), updating (UPDATE) and deleting (DELETE). Database-schema authority can additionally permit creating, altering or dropping relations. The database administrator has the broadest authority, including authorising new users and restructuring the database.

4.6.1 · Granting and revoking privileges

GRANT SELECT ON department TO Amit, Satoshi;
GRANT UPDATE (budget) ON department TO Amit, Satoshi;

REVOKE SELECT ON department FROM Amit, Satoshi;
REVOKE UPDATE (budget) ON department FROM Amit, Satoshi;

GRANT confers privileges; REVOKE withdraws them. ALL PRIVILEGES is a shorthand for all allowable privileges. The UPDATE privilege can apply to every attribute or only to named attributes. A restricted INSERT privilege can name the attributes the user may specify; other attributes use defaults or NULL where allowed. The special user PUBLIC means all current and future users. A user who creates a relation is automatically given all privileges on it.

Scope limit: The authorisation mechanism described here grants privileges on whole relations/views or specified attributes, not individual tuples. A view can be used to expose a carefully filtered subset of data, as explained in Section 4.6.3.

4.6.2 · Roles

A role groups permissions according to a person's function (for example, instructor, teaching assistant, student, dean or department chair). Granting permissions to a role avoids repeating the same grants for every new user. Users should still connect under their own user IDs so the database can identify who performed an update.

CREATE ROLE instructor;
GRANT SELECT ON takes TO instructor;
GRANT instructor TO Amit;

CREATE ROLE dean;
GRANT instructor TO dean;
GRANT dean TO Satoshi;

A user's effective privileges are the privileges granted directly to that user plus those of roles granted directly or indirectly to the user. Role grants can form a chain, so a dean role may inherit privileges attached to instructor and teaching-assistant roles as well as privileges attached directly to dean.

4.6.3 · Authorization on views and routines

CREATE VIEW geo_instructor AS
SELECT *
FROM instructor
WHERE dept_name = 'Geology';

GRANT SELECT ON geo_instructor TO geology_staff;

A staff member who should see only Geology instructor rows can be granted access to the filtered view rather than direct access to the full instructor relation. The system must check the user's query authorization before processing the translated query on underlying relations. The view creator does not automatically gain privileges beyond those already held; creating this view requires SELECT on instructor.

The source also discusses execute privileges on functions/procedures. By default, they run with the privileges of their creator in the described model. An SQL:2003 function definition with SQL SECURITY INVOKER runs under the invoking user's privileges instead.

4.6.4 · Authorization on schema

The source describes the schema owner as the party allowed to modify the schema, for example by creating or dropping relations, changing attributes or managing indices. SQL also offers a REFERENCES privilege on specified attributes:

GRANT REFERENCES (dept_name)
ON department TO Mariano;

This permits Mariano to create a foreign key referencing department.dept_name. Such permission matters because adding a foreign key can restrict other users' ability to delete or update referenced department rows. The source says the references privilege is also required for a subquery-based check constraint that references the protected relation.

4.6.5 · Transferring privileges

GRANT SELECT ON department TO Amit WITH GRANT OPTION;

WITH GRANT OPTION lets Amit pass the granted privilege to other users. The creator of an object holds all privileges on that object, including the ability to grant privileges. A privilege-transfer graph represents each grant as an edge from the grantor to the recipient; a user has a privilege when a path from the database administrator to that user exists in the graph.

4.6.6 · Revoking privileges

Cascading revocation occurs when withdrawing one user's grant causes downstream grants to be withdrawn too. If U1 granted a privilege to U4, revoking U1's grant may remove U4's path. If U5 received the privilege independently from both U1 and U2, U5 retains it while at least one valid path remains.

REVOKE SELECT ON department FROM Amit, Satoshi RESTRICT;
REVOKE GRANT OPTION FOR SELECT ON department FROM Amit;

RESTRICT prevents a revocation that would cause cascading changes and returns an error instead. CASCADE explicitly requests cascading behaviour and is the default in the source's description. REVOKE GRANT OPTION FOR withdraws the power to pass on a privilege rather than the privilege itself, though the source warns that some implementations do not support this syntax.

The source highlights a subtle role example: revoking a dean role from a user should not necessarily remove a role that user granted on behalf of the dean role. SQL can associate grants with the current role using SET ROLE role_name and GRANTED BY CURRENT ROLE, so subsequent revocation follows the role identity rather than simply the person who issued the grant.

Security mental model: GRANT creates an authorisation path; WITH GRANT OPTION permits onward delegation; REVOKE removes a grant path; and cascading rules determine whether dependent paths also disappear. Always consider alternative grant paths and implementation support.

Fast self-check

1. Why should a bank transfer be one transaction?

Debiting and crediting are logically one task. Without transaction-level atomicity, a crash between them can leave the account balances inconsistent.

2. How do PRIMARY KEY and UNIQUE differ in the source's description?

Primary-key attributes must be unique and non-null. Attributes under a UNIQUE constraint must not duplicate one another as a complete listed key, but may be null unless separately declared NOT NULL.

3. What is the purpose of ON DELETE CASCADE?

If deleting a referenced row would otherwise violate a foreign key, delete the dependent referencing rows too.

4. Why can an assertion be expensive?

A broad condition may need to be checked whenever any relevant relation changes, including relations mentioned inside a subquery.

5. What is the difference between a domain and a distinct type?

The source presents domains as a place for constraints/defaults on an underlying type, while distinct types separate semantically different values through stronger type checking.

6. What does WITH GRANT OPTION permit?

It allows the privilege recipient to grant that privilege onward to other users or roles.

Exam revision

High-value distinctions

CompareRemember
ON vs WHEREFor an inner join, an equality match can often be expressed either way. For outer joins, moving a predicate from ON to WHERE can remove null-padded rows.
Inner vs outer joinInner join returns matching rows; outer joins preserve unmatched rows from the specified side or both sides using NULL padding.
Normal vs materialized viewA normal view stores the query definition and computes its result when used. A materialized view stores the result and requires maintenance.
Querying vs updating a viewQuerying asks the DBMS to evaluate a defining expression; updating requires translating the requested change into valid changes to underlying relations.
Updatable vs checked viewUpdatability concerns whether a change can be mapped to base data. WITH CHECK OPTION additionally rejects changes that violate the view's filter.

Self-check questions

1. Why does Snow disappear from a natural inner join?

Snow has a tuple in student but no tuple in takes with the same ID, so there is no matching pair. An inner join includes only matching pairs.

2. Which outer join preserves all rows from the left input?

LEFT OUTER JOIN. An unmatched left-side tuple remains, with right-side attributes filled with NULL.

3. Why can Query A and Query B in Section 4.1.2 return different rows?

In Query A, the ID match is the outer join's ON condition, so unmatched students receive null-padded rows. In Query B, joining on TRUE does not identify unmatched students; the later WHERE predicate removes unequal-ID pairs, including all combinations for Snow.

4. Why might a materialized view become stale?

Its stored result may not yet have been refreshed after underlying data changes, especially when the system performs periodic rather than immediate maintenance.

5. What does WITH CHECK OPTION add?

It rejects inserts or updates that would leave the resulting tuple outside the view's defining filter.

One-minute mental model

Join: choose a match rule and decide which unmatched rows survive. View: expose a query as a virtual relation; materialized views store results and need maintenance. Transaction: commit all related changes or roll them all back. Constraint: reject changes that break required rules. Types and schemas: organise valid values and object names. Authorization: grant only needed privileges, track delegation, and reason carefully about revocation.
