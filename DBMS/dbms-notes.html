File Organization & Indexing

1. What is a File?

A file is a named collection of related records on disk, representing one entity type (e.g., all students).

One Entity Type

STUDENT records don't mix with COURSE records in the same file.

Many Records

Each record describes one instance — one student, one order.

Sequence of Blocks

Physically, a file is just disk blocks stored one after another.

2. What is a Record?

A record is one row, built from fields of different types.

FieldTypeSize
Roll_NoINTEGER4 bytes
NameCHAR(30)30 bytes
DepartmentCHAR(10)10 bytes
CGPAFLOAT4 bytes

Record size = 4+30+10+4 = 48 bytes (fixed-length record).

Database → Files → Disk Blocks (Pages) → Records → Fields. Each level physically contains the one below it.

3. Blocks & Blocking Factor

Disks read/write in blocks (typically 4–16 KB), not individual records.

bfr = ⌊ B / R ⌋

Example: B = 4096 bytes, R = 100 bytes → bfr = ⌊4096/100⌋ = 40 records/block, wasting 96 bytes.

40 records
96 B unused

4. Fixed-Length Records

Every record occupies the same number of bytes (padding fills short values).

Address(record i) = start_of_file + i × R

Example: R = 48 bytes → record #500 is at offset 500×48 = 24,000 bytes. No scanning needed.

Handling Deletion

Deletion Marker

Flag slot as 'deleted' (tombstone) — fast, leaves a gap.

Free-Slot List

Chain deleted slots so new records can reuse space.

Compaction

Periodically shift records to close gaps.

5. Variable-Length Records

Variable-length fields

e.g. VARCHAR(50) — "Al" shouldn't cost as much as "Alexandra Bartholomew".

Repeating fields

e.g. Courses[] — different number of values per record.

Mixed record types

e.g. Employee vs Manager in one file.

Indexing in Database Systems

7. Why Indexes?

Like a book's index lets you jump to a page instead of reading cover-to-cover, a DB index jumps straight to a record's block instead of scanning the whole file.

Without IndexWith Index
Full linear scan — O(n) block accessesSearch index, jump to block — O(log n) block accesses

8. Single-Level Indexes

Sparse

Primary Index

On ordering primary key of a sorted file. One entry per block (block anchor). Only one per file.
Sparse

Clustering Index

On a non-key field the file is physically ordered by. One entry per distinct value. Only one per file.
Dense

Secondary Index

On any non-ordering field (key or non-key). One entry per record. Multiple allowed per file.

9. Multilevel Indexes

A single-level index can still grow large. Solution: treat it as an ordered file and build a sparse second-level index over it, then a third, until the top level fits in one block.

Reduces cost from O(log₂ r) to about O(log_fo r), where fo = fan-out (entries per block).

10. Dynamic Indexes: B-Tree & B+-Tree

Static multilevel indexes degrade as data changes (overflow/underflow on insert/delete). Dynamic self-balancing trees solve this — nodes split on overflow, merge/redistribute on underflow, and all leaves stay at the same level.

FeatureB-TreeB+-Tree
Data pointersIn internal AND leaf nodesOnly in leaf nodes
Leaf nodes linked?NoYes — sequential linked list
Fan-out per nodeLowerHigher (no data ptrs stored)
Range queriesSlower — revisit treeFast — follow leaf links
Common usageLess commonStandard in most RDBMS

Key Takeaways

  • Single-level indexes: primary & clustering (sparse) vs. secondary (dense).
  • Multilevel indexes: an index over the index, until the top level fits in one block.
  • B-Tree: balanced, data pointers at every level, self-adjusts via splits/merges.
  • B+-Tree: data only in linked leaves — higher fan-out, shorter tree, fast range scans. Industry standard.
