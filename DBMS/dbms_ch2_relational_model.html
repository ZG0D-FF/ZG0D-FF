0Big picture and concept map

The relational model is today the primary data model for commercial data-processing applications. It won that position because of its simplicity, which eases the programmer's job compared with earlier models such as the network and hierarchical models.

The chapter has one storyline: data is stored in tables (§1) → a schema describes them, an instance holds the current data (§2) → keys make tuples identifiable and link tables (§3) → diagrams summarise the design (§4) → query languages retrieve the data (§5) → relational operations are what those languages compute (§6). 1Structure of relational databases

1.1 A database is a collection of uniquely named tables

Intuition. Picture a spreadsheet-like table for each kind of thing you want to record. Each table has a name, a fixed set of column headers, and one row per recorded fact.

Formal meaning. A relational database is a collection of tables, each assigned a unique name. In the university example:

  • instructor (Fig. 2.1) has four columns: ID, name, dept_name, salary. Each row records one instructor, who is identified by the value of ID.
  • course (Fig. 2.2) has course_id, title, dept_name, credits. Each course is identified by course_id.
  • prereq (Fig. 2.3) has course_id and prereq_id. Each row is a pair of course identifiers where the second course is a prerequisite for the first.

1.2 Why it is called “relational”: table, row, column → relation, tuple, attribute

A row represents a relationship among a set of values. A row of prereq relates two course identifiers. A row of instructor relates one ID to its name, dept_name and salary. A table is a collection of such relationships, so it corresponds closely to the mathematical concept of a relation, which gives the model its name. Mathematically, a tuple is simply a sequence (list) of values; a relationship between n values is an n-tuple, and it corresponds to one row.

1.4 Domains and atomicity

Definition. For each attribute there is a set of permitted values, its domain. The domain of salary is the set of all possible salaries; the domain of name is the set of all possible instructor names.

Definition

A domain is atomic if its elements are considered indivisible units. The model requires the domains of all attributes of every relation to be atomic (first-form requirement of the model as presented in Chapters 2–6).

The subtle point: atomicity is about how we use the values, not about what the values “really are”. Take a hypothetical attribute phone_number in instructor:

How phone_number is usedAtomic?Why
Stores a set of phone numbers for an instructorNoEach value is a set, which has subparts (the individual numbers).
Stores a single number, but we split it into country code, area code, local numberNoWe are treating the value as having subparts.
Stores a single number, treated as one indivisible unitYesNo subparts are used.

Chapters 3–6 assume all attributes have atomic domains; Chapter 22 discusses extensions that permit nonatomic domains. The precise definition of each domain is deferred to SQL (Chapter 3).

1.5 The null value

The null value is a special value signifying that a value is unknown or does not exist. If instructor had phone_number, an instructor might have no phone at all, or an unlisted one; both would be recorded as null.

Pitfall

Nulls cause a number of difficulties when accessing or updating the database, so they should be eliminated if at all possible. The source assumes nulls are absent at first; their effect on each operation is described in Section 3.6.

Key takeaway

Table = relation, row = tuple, column = attribute. A relation is an unordered set of tuples over atomic domains; null is the special “unknown or nonexistent” value to avoid where possible.

2Database schema vs instance

2.1 Two things that change at different speeds

Intuition. The blueprint of a database rarely changes; the contents change all the time.

Definitions
  • Database schema — the logical design of the database.
  • Database instance — a snapshot of the data in the database at a given instant.
  • Relation schema — a list of attributes and their corresponding domains.
  • Relation instance — the particular set of tuples the relation holds at some time.

The analogy with programming languages makes this concrete:

2.2 Common attributes link relations

Why it matters. The attribute dept_name appears in both the instructor and department schemas. This is deliberate: using common attributes in relation schemas is one way of relating tuples of distinct relations. (This idea is formalised as the foreign key in §3.)

3Keys and referential integrity

3.1 Why keys exist

Intuition. If a table could hold two indistinguishable rows, we could not say which one to update or refer to. So we need a way to distinguish tuples within a relation, expressed in terms of their attributes: the values of a tuple's attributes must identify it uniquely. In other words, no two tuples in a relation may have exactly the same value for all attributes.

3.2 Superkey

Definition

A superkey is a set of one or more attributes that, taken collectively, allows us to identify uniquely a tuple in the relation.

  • ID is a superkey of instructor (it distinguishes one instructor tuple from another).
  • name alone is not a superkey: several instructors might share a name.
  • A superkey may contain extraneous attributes: {ID, name} is a superkey. In general, if K is a superkey, so is any superset of K.

Formal statement. Let R be the set of attributes of relation r. A subset K ⊆ R is a superkey for r if we restrict attention to instances of r in which no two distinct tuples agree on all attributes in K:

for all t₁, t₂ in r:  t₁ ≠ t₂  ⇒  t₁.K ≠ t₂.K

The pasted text shows “t1 = t2, then t1.K = t2.K”, which is a text-extraction slip (the ≠ signs were lost); the formula above is the intended meaning.

3.3 Candidate key

Definition

A candidate key is a minimal superkey: a superkey no proper subset of which is itself a superkey.

Several distinct attribute sets can be candidate keys. Suppose {name, dept_name} is enough to distinguish instructors. Then both {ID} and {name, dept_name} are candidate keys. Yet {ID, name} is not a candidate key, because its proper subset {ID} is already a superkey.

3.4 Primary key

Definition

A primary key is the candidate key chosen by the database designer as the principal means of identifying tuples in a relation.

Properties and conventions

  • A key (primary, candidate or super) is a property of the entire relation, not of individual tuples. Any two tuples are prohibited from having the same value on the key attributes at the same time.
  • Designating a key represents a constraint in the real-world enterprise being modelled.
  • Primary-key attributes are listed first in the schema and are underlined (e.g. dept_name in department).

Choosing a primary key well

QuestionGuidance from the source
Is a person's name enough?No — many people share a name.
Social-security number?A candidate key in the United States, but non-U.S. residents usually lack one, so international enterprises must generate their own unique identifiers (or use a unique combination of other attributes).
Should values change?The chosen key's values should never, or very rarely, change. An address should not be part of a primary key because it is likely to change.
Enterprise-generated identifiers?Generally stable. Exception: when two enterprises merge, both may have issued the same identifier, and a reallocation may be required to keep them unique.

3.5 Foreign key

Definition

If relation r1 includes among its attributes the primary key of another relation r2, that attribute set is a foreign key from r1, referencing r2.

  • r1 is the referencing relation of the foreign-key dependency.
  • r2 is the referenced relation.

Example. dept_name in instructor is a foreign key from instructor referencing department, because dept_name is the primary key of department. The condition: in any database instance, for any tuple ta of instructor there must be some tuple tb in department whose primary-key value equals ta’s dept_name.

3.6 Referential integrity (and why it is more general than a foreign key)

Definition

A referential integrity constraint requires that the values appearing in specified attributes of any tuple in the referencing relation also appear in specified attributes of at least one tuple in the referenced relation.

The section–teaches case. It is reasonable to require that every section that exists is taught by at least one instructor (possibly several). To enforce it, every (course_id, sec_id, semester, year) combination in section must also appear in teaches. But that combination is not a primary key of teaches, because more than one instructor may teach the same section. Hence:

  • We cannot declare a foreign key from section to teaches.
  • We can declare a foreign key in the other direction, from teaches to section.
  • The section → teaches requirement is still a legitimate referential integrity constraint: a foreign key is only the special case where the referenced attributes form the primary key.

Key takeaway

Keys say how to identify a tuple; foreign keys say how tuples in one relation point to tuples in another. Referential integrity generalises the foreign-key idea and is what keeps those pointers valid.

5Relational query languages

A query language is a language in which a user requests information from the database. These languages are usually at a higher level than a standard programming language, and fall into two families:

FamilyWhat the user does“Pure” language
ProceduralInstructs the system to perform a sequence of operations to compute the resultRelational algebra
NonproceduralDescribes the desired information without giving a specific procedure for obtaining itTuple relational calculus; domain relational calculus
  • Practice vs theory. Languages used in practice include elements of both approaches. The widely used SQL is studied in Chapters 3–5.
  • Why study “pure” languages? They are terse and formal and lack the “syntactic sugar” of commercial languages, but they illustrate the fundamental techniques for extracting data (examined in Chapter 6).
  • Relational algebra: a set of operations that take one or two relations as input and produce a new relation as the result. The main operations are outlined in §6.
  • Relational calculus (tuple and domain versions): uses predicate logic to define the desired result without giving an algebraic procedure for obtaining it.
Key takeaway

Algebra says how (a pipeline of operations on relations); calculus says what (a logical condition on the result). Both consume relations and produce relations, which is why relational operations can be composed.

6Relational operations

6.1 Operations that take relations and return a relation

Intuition. Every procedural relational query language offers a small toolbox of operations. Each one is applied to a single relation or a pair of relations, and each one hands back one relation.

Why it matters. Because the result of a relational query is itself a relation, operations can be applied to the results of queries as well as to the stored relations. That is what lets us combine several operations in a modular way (§6.7). The exact notation differs between languages, but all fit the framework below; the SQL forms appear in Chapter 3.

The most frequent operation selects specific tuples from a single relation that satisfy a predicate. The result is a new relation that is a subset of the original. Example: from instructor (Fig. 2.1), select the tuples whose salary is greater than $85,000.

6.4 Join and Cartesian product (combining two relations)

Join. The join operation combines two relations by merging pairs of tuples, one from each relation, into a single tuple. There are several kinds of join (Chapter 3). The form below is the natural join: a tuple of instructor matches a tuple of department if their dept_name values are the same, and all such matching pairs appear in the result. In general, a natural join matches tuples whose values agree on all attribute names common to both relations.

Intuitively this answers “for each instructor, show me their department's details”: every instructor tuple is paired with the one department tuple for that instructor's department. This is the operation behind the Watson-building lookup of §2.2.

Cartesian product. The Cartesian product also combines tuples from two relations, but unlike a join its result contains all pairs of tuples, regardless of whether their attribute values match.

Worked comparison (derived from the sample data)

instructor has 12 tuples and department has 7, so their Cartesian product has 12 × 7 = 84 pairs. Only the 12 pairs whose dept_name values agree survive in the natural join of Fig. 2.12 (each instructor has exactly one department). A natural join therefore behaves like a Cartesian product followed by keeping only the matching pairs.

6.5 Set operations

Because relations are sets, ordinary set operations apply to them. The union operation forms the set union of two “similarly structured” tables, for example a table of all graduate students and a table of all undergraduate students, giving all students in a department. Intersection and set difference can be performed as well.

Duplicates: sets versus bags

A query result can contain duplicate tuples. Selecting dept_name from instructor repeats several values; “Comp. Sci.” shows up three times. Languages differ:

ApproachBehaviourTrade-off
Strictly set-basedRemoves duplicatesFaithful to the mathematical definition of a set, but removal needs considerable processing on large results.
Duplicate-retainingKeeps duplicatesCheaper, but the results are then not truly relations in the pure mathematical sense.

6.6 Changing the data: updates

Data must change over time. A relation can be updated by inserting new tuples, deleting existing tuples, or modifying tuples by changing the values of certain attributes. Entire relations can be deleted and new ones created. Queries and updates in SQL are covered in Chapters 3–5.

6.7 Composing operations

How it works. Since every operation returns a relation, the output of one can feed the next. To find the ID and salary of instructors earning more than $85,000, first select the tuples with salary > 85000 from instructor, then select the attributes ID and salary from that intermediate result.

Key takeaway

Selection trims rows, projection trims columns, join and product combine two relations, and set operations treat relations as sets. All return a relation, so they chain into expressions. Practical languages like SQL are based on the relational algebra but add useful syntactic features.

Common misconceptions

Check yourself against these
  • “Row order matters.” No. A relation is a set of tuples; Fig. 2.1 and 2.4 are the same relation (§1.3).
  • “A set-valued attribute is fine if it is just one column.” No. Domains must be atomic; atomicity depends on how values are used (§1.4).
  • “Names make good keys.” No. Several people can share a name; keys must be (very nearly) unchanging (§3.4).
  • “{ID, name} is a candidate key because it identifies tuples.” No. It is a superkey but not minimal.
  • “A key belongs to a tuple.” No. It is a property of the whole relation.
  • “Nulls are harmless.” No. They complicate access and update and should be eliminated where possible (§1.5).
  • “Schema diagrams show every constraint.” No. Only primary keys and foreign keys (§4).
  • “A join is just a Cartesian product.” No. The product keeps every pair; the natural join keeps only pairs that match on common attributes (§6.4).
  • “Operations must be applied in a fixed order.” Not always interchangeable: a projection can discard an attribute a later selection needs (§6.7).
  • “Every query result is a true relation.” Only if duplicates are removed; duplicate-retaining languages return results that are not relations in the pure sense (§6.5).

Self-check questions

1. What do “table”, “row” and “column” correspond to in the relational model?

Relation, tuple, attribute respectively. A relation instance is the set of tuples present at a given time.

2. Why does the order of tuples not matter?

Because a relation is a set of tuples; two displays with the same tuples are the same relation.

3. A phone_number attribute stores one number, but queries split off the area code. Is the domain atomic?

No. Treating the value as having a country code, area code and local number means we use it as divisible. It is atomic only if each number is treated as a single indivisible unit.

4. Distinguish a relation schema from a relation instance with a programming analogy.

Schema ≈ type definition (rarely changes); instance ≈ value of a variable (changes as data is updated).

5. Given that {ID} and {name, dept_name} are both candidate keys of instructor, is {ID, name} a candidate key? Is it a superkey?

Not a candidate key, since {ID} ⊂ {ID, name} is already a superkey (so it is not minimal). It is a superkey, because any superset of a superkey is a superkey.

6. Why can we declare a foreign key from teaches to section but not from section to teaches?

A foreign key must reference the referenced relation's primary key. The section attributes are the primary key of section, but not of teaches, as several instructors may teach one section. The section → teaches requirement is still a referential integrity constraint.

7. Which language family is relational algebra, and which are the calculi?

Algebra is procedural; tuple and domain relational calculus are nonprocedural.

8. Why can relational operations be chained?

Each takes one or two relations and returns a single relation, so the result of one operation is a valid input to the next (§6.1).

9. Which rows does selecting instructors with salary > 85000 return?

Wu (90000), Einstein (95000), Gold (87000), Brandt (92000) — Fig. 2.10.

10. What does the natural join of instructor and department match on, and how many tuples result?

On their common attribute dept_name; 12 tuples (one per instructor, Fig. 2.12). Their Cartesian product would have 12 × 7 = 84.

11. Projecting dept_name from instructor gives “Comp. Sci.” three times. Is the output a true relation?

Only if the language removes duplicates. Languages that retain them, to avoid the processing cost, give results that are not truly relations in the mathematical sense.

12. When does union apply?

To two “similarly structured” tables, such as all graduate students and all undergraduate students.

Final conceptual recap

  1. The relational model stores data in uniquely named tables (relations) of tuples over atomic domains; it dominates because it is simple.
  2. A schema is the stable logical design; an instance is the changing snapshot of the data.
  3. Keys (super → candidate → primary) identify tuples; foreign keys and referential integrity keep references between relations valid.
  4. Schema diagrams show relations, primary keys and foreign-key arrows; ER diagrams (Ch. 7) show more constraints.
  5. Queries are written in procedural (algebra) or nonprocedural (calculus) styles; SQL blends both.
  6. A relation schema includes its attributes and, optionally, attribute types and constraints such as primary and foreign keys; the schema and instance of a whole database are defined the same way.
  7. The operations (selection, projection, natural join, Cartesian product, set operations) all take relations and return a relation, so they combine into expressions. Practical languages such as SQL build on the relational algebra and add syntactic features.
  8. Users can query the tables and insert, delete and modify tuples.
