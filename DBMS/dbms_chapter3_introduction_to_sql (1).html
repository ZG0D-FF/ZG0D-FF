Chapter map: what SQL does

SQL is commonly called a query language, but querying is only one of its jobs. It can define the database structure, read and change stored data, enforce integrity rules, define views, control transactions, and specify access rights.

Source coverage

These notes cover the supplied Chapter 3 excerpt through Section 3.8.7, including additional basic operations, set operations, null values, aggregate functions, and nested subqueries. Topics only mentioned as later-chapter material are identified as such rather than expanded into unrelated coverage.

3.1 · Overview

SQL overview and history

IBM developed the original version of SQL, first called Sequel, as part of the System R project in the early 1970s. The name evolved to SQL (Structured Query Language), which became the standard language used with relational databases.

The main parts of SQL

Data-definition language (DDL)

Defines relation schemas and can delete or modify them. It also supports integrity constraints, views, and authorization-related declarations.

Data-manipulation language (DML)

Queries information and inserts, deletes, or modifies tuples in the database.

Transaction control

Provides commands for specifying the beginning and ending of transactions.

Embedded and dynamic SQL

Defines how SQL statements can be embedded in general-purpose languages such as C, C++, and Java.

3.2 · SQL data definition

What does DDL define?

The database system must be told which relations exist through a data-definition language (DDL). In the supplied text, SQL DDL can describe more than column names: it can record the schema and the operational rules for each relation.

Information that DDL can specify

  1. The schema for each relation.
  2. The types of values associated with each attribute.
  3. Integrity constraints that stored data must satisfy.
  4. Indices to be maintained for each relation.
  5. Security and authorization information for each relation.
  6. The physical storage structure of each relation on disk.

The excerpt focuses here on basic schema definition and types, deferring the remaining DDL features to later chapters.

Choose a type that matches the attribute

A column’s type defines what kind of values it can store and, for sized types, what range or representation is allowed.

Reading NUMERIC(p,d)

NUMERIC(3,1) has three digits in total and one digit after the decimal point. The source example says 44.5 can be stored exactly, whereas 444.5 and 0.32 cannot be stored exactly in that type: the first exceeds the total precision, and the second uses more fractional digits than specified.

NULL: absent, unknown, or not applicable

Each type may allow a special value called NULL. In the excerpt, it indicates an absent value that may exist but be unknown, or a value that may not exist at all. A schema can prohibit NULL for selected attributes; see integrity constraints.

CHAR versus VARCHAR

CHAR(10)

Storing 'Avi' adds seven spaces to make the stored string ten characters long.

VARCHAR(10)

Storing 'Avi' does not add spaces merely to reach length ten.

When comparing two values of type CHAR, the shorter value is padded with spaces before comparison. Between a CHAR value and a VARCHAR value, padding behavior can depend on the database system. Therefore, the same displayed text in a CHAR field and a VARCHAR field may compare as unequal in some systems.

Practical recommendation from the source

The excerpt recommends using VARCHAR instead of CHAR to avoid these padding/comparison problems.

3.2.2 · Basic schema definition

Create a relation and state its rules

Use CREATE TABLE to define a relation. For example, a department relation has three attributes and a primary key:

CREATE TABLE department (
    dept_name VARCHAR(20),
    building  VARCHAR(15),
    budget    NUMERIC(12,2),
    PRIMARY KEY (dept_name)
);

Here, dept_name can contain up to 20 characters, building up to 15, and budget is a fixed-point number with 12 digits in total, including two digits after the decimal point. dept_name is declared as the primary key.

Identifier formatting note

The supplied extract’s text rendering shows several multiword identifiers with spaces (for example, “dept name”). They are written with underscores here (for example, dept_name) to make the SQL examples practical while preserving the intended attribute names and meanings.

General form

CREATE TABLE r (
    A1 D1,
    A2 D2,
    ...,
    An Dn,
    integrity_constraint_1,
    ...,
    integrity_constraint_k
);

r is the relation name; each Ai is an attribute name; and Di is its domain/type, optionally with constraints restricting permitted values. A semicolon at the end of SQL statements is optional in many implementations.

Three essential integrity constraints

PRIMARY KEY

The specified attribute or attribute set must be unique and non-NULL. No two tuples can share all primary-key values.

FOREIGN KEY

Values in the referencing attribute(s) must match primary-key values in a referenced relation.

NOT NULL

The attribute cannot contain the NULL value.

A primary key may contain several attributes: PRIMARY KEY (A1, A2, ...). A composite key is unique as a combination; each primary-key attribute must be non-NULL.

For a foreign key, every referenced value must correspond to a key value in the target relation. For example, a course’s dept_name must identify a department that actually exists. Without that constraint, a course could refer to a nonexistent department.

What happens when a constraint is violated?

SQL rejects updates that violate declared integrity constraints. For example, an inserted row cannot have a NULL or duplicate primary-key value; an instructor whose name is constrained by NOT NULL cannot have a NULL name; and a course cannot refer to a department that is absent from department.

Data changes and schema changes

Insert, delete, drop, and alter

Insert a tuple

A newly created relation is empty. The excerpt inserts a Biology instructor named Smith, with ID 10211 and salary 66,000:

INSERT INTO instructor
VALUES (10211, 'Smith', 'Biology', 66000);

Values are supplied in the same order as attributes in the relation schema. The example’s instructor.ID is declared VARCHAR(5); in a strictly type-aligned statement, quote the identifier as a string ('10211'). Acceptance of the unquoted form can depend on the DBMS.

Delete tuples, or remove the table itself

Do not confuse deleting rows with dropping a relation
CommandEffectWhat remains?
DELETE FROM student;Deletes all tuples in student in the form shown.The relation and its schema remain; rows can be inserted later.
DROP TABLE r;Deletes all information about relation r.The table schema is also removed. It must be recreated before new tuples can be inserted.

Alter the schema

ALTER TABLE r ADD A D;

ALTER TABLE r DROP A;

ADD introduces attribute A with type D; existing tuples receive NULL for the new attribute. DROP A removes attribute A. The excerpt notes that many database systems do not support dropping individual attributes, even though they support dropping an entire table.

3.3 · Basic structure of SQL queries

Three clauses, three jobs

SELECT

Lists the attributes or expressions wanted in the output.

FROM

Lists the relations to access while evaluating the query.

WHERE

Specifies the predicate that candidate tuples must satisfy.

SELECT A1, A2, ..., An
FROM r1, r2, ..., rm
WHERE P;

Each Ai is an output attribute or expression, each ri is a relation, and P is a predicate. If WHERE is omitted, the predicate is treated as true.

Meaning is not the same as execution strategy

This conceptual sequence explains the query’s result, not necessarily what the database physically executes. A real SQL implementation may optimise the query and avoid generating all combinations in a large Cartesian product.

More than one instructor may belong to the same department, so this query can return the same department name multiple times. The mathematical relational model treats relations as sets, but SQL permits duplicates in query results; eliminating duplicates can cost additional processing.

DISTINCT requests duplicate elimination, so each department name appears at most once. By contrast, ALL explicitly retains duplicates:

3.3.2 · Queries on multiple relations

Combine information using matching attributes

Information needed for an answer may be split across relations. For example, instructor stores an instructor’s department name, while department stores the building for that department. To return the instructor’s name, department, and building, the two relations must be matched on dept_name.

SELECT name, instructor.dept_name, building
FROM instructor, department
WHERE instructor.dept_name = department.dept_name;

The prefix instructor. or department. disambiguates dept_name, because that attribute occurs in both relations. An attribute that appears in only one relation, such as building in this example, does not need a prefix. The excerpt notes that this naming convention assumes distinct relation names; renaming can help when two tuple instances from the same relation must be combined (covered later in the text).

The logic underneath a multi-relation query

Cartesian product first, then filter

A general query has the form:

SELECT A1, A2, ..., An
FROM r1, r2, ..., rm
WHERE P;

Conceptually, FROM with multiple relations forms their Cartesian product: every tuple from the first relation is paired with every tuple from the second, then with every tuple from each remaining relation. Attributes from the input relations all appear in the product; if names overlap, relation prefixes distinguish them.

For the instructor and teaches relations, the excerpt gives the product schema as the attributes of both relations, including separately qualified instructor.ID and teaches.ID. It illustrates a product of 12 instructor tuples and 13 teaches tuples: 12 × 13 = 156 tuples. In a more realistic example with 200 instructors and 600 teaches tuples, the product would have 200 × 600 = 120,000 tuples.

Join by an explicit WHERE condition

SELECT name, course_id
FROM instructor, teaches
WHERE instructor.ID = teaches.ID;

This returns instructor names with the course identifiers of courses they teach. Only instructors with matching tuples in teaches appear. The excerpt points out that Gold, Califieri, and Singh—who have not taught a course in its example data—are absent. An outer join, discussed in a later section of the source text, can retain such instructors.

Add another condition to restrict the instructors to Computer Science:

SELECT name, course_id
FROM instructor, teaches
WHERE instructor.ID = teaches.ID
  AND instructor.dept_name = 'Comp. Sci.';

Because dept_name occurs only in instructor among these two relations, it could be written without the relation prefix.

Conceptual meaning in three steps

  1. Generate the Cartesian product of the relations in FROM.
  2. Apply the predicates from WHERE to filter combinations.
  3. For each remaining tuple, output the attributes or expressions in SELECT.

Again, this sequence specifies the result’s meaning. A DBMS will normally optimise evaluation instead of blindly constructing every product row.

3.3.3 · The natural join

Join automatically on all common attribute names

When two relations share an attribute name, a common use case is to match rows where the values of that attribute are equal. SQL’s natural join handles this case without writing a separate equality predicate.

SELECT name, course_id
FROM instructor NATURAL JOIN teaches;

This is equivalent, for the example shown, to the explicit condition instructor.ID = teaches.ID. Natural join keeps only tuple pairs that agree on all attributes whose names are present in both relation schemas.

What it does

Matches equal values on every common attribute name. In the instructor and teaches example, the common attribute is ID.

Output shape

Common attributes appear only once. The excerpt orders columns as common attributes first, then attributes unique to the first relation, then attributes unique to the second.

The natural-join trap: common names can mean too much

Suppose the goal is to list instructor names and the titles of courses they teach. First join instructor and teaches, then match the course ID against course:

SELECT name, title
FROM instructor NATURAL JOIN teaches, course
WHERE teaches.course_id = course.course_id;

The excerpt warns that this is not equivalent to:

SELECT name, title
FROM instructor NATURAL JOIN teaches NATURAL JOIN course;

Why? The first natural join yields attributes including dept_name and course_id. The course relation also contains both. A natural join with course therefore matches on both course_id and dept_name. It can wrongly omit an instructor-course pair when the instructor’s home department differs from the department offering the course.

Specify the intended match

Use JOIN ... USING when only selected columns should match

To retain the convenience of a join while avoiding accidental equality on every common name, the excerpt shows JOIN ... USING:

SELECT name, title
FROM (instructor NATURAL JOIN teaches)
     JOIN course USING (course_id);

JOIN ... USING (A1, A2, ...) requires the specified attribute names to occur in both inputs and matches rows when those named values agree. Unlike a natural join, it does not require other same-named attributes to be equal. Here, only course_id is used to match to course, so dept_name may differ between the instructor and the course.

Decision rule

Use NATURAL JOIN when all same-named attributes are intended match keys. Use JOIN ... USING (course_id) when you want to state explicitly that course_id is the match key and other shared names must not add conditions.

3.4 · Additional basic operations

Renaming, strings, ordering, and predicates

These operations make SQL results easier to read and queries more expressive. They also introduce details—especially aliases, pattern matching, and tuple predicates—that are easy to overlook in exams.

3.4.1 Rename with AS

A query result may need a clearer column name, particularly when an output is an expression or when names would otherwise be ambiguous. SQL's AS clause renames a result attribute or a relation reference.

SELECT name AS instructor_name, course_id
FROM instructor, teaches
WHERE instructor.ID = teaches.ID;

Output meaning: the first result column is labelled instructor_name; the second is course_id. Renaming the output heading does not change the stored relation.

Relation aliases shorten names and distinguish separate references to the same relation:

SELECT T.name, S.course_id
FROM instructor AS T, teaches AS S
WHERE T.ID = S.ID;

Here, T names the instructor relation reference and S names the teaches relation reference. These aliases are also called correlation names, table aliases, correlation variables, or tuple variables.

Self-join: compare two instructor rows

To find instructors whose salary is greater than at least one instructor in Biology, the same relation is referenced twice:

SELECT DISTINCT T.name
FROM instructor AS T, instructor AS S
WHERE T.salary > S.salary
  AND S.dept_name = 'Biology';

Each combination compares a candidate instructor T with a Biology instructor S. The condition is true when T.salary is greater than at least one Biology salary. The source notes that the more intuitive equivalent phrasing is “salary greater than the lowest-paid instructor in Biology.”

Dialect note

The source notes that some Oracle versions do not permit AS for table aliases: write instructor T rather than instructor AS T. The AS keyword for output-column aliases may be used or omitted in Oracle.

3.4.3 Select all attributes

* means all attributes in the result relation produced by the FROM clause. A qualified star selects all attributes from one named relation:

SELECT instructor.*
FROM instructor, teaches
WHERE instructor.ID = teaches.ID;

SELECT instructor.* returns all instructor attributes, while SELECT * returns all attributes from the complete FROM-clause result.

3.4.4 Ordering result tuples

Without ORDER BY, the query does not promise a display order. The clause orders the result, ascending by default; use DESC or ASC to specify direction. Multiple sort keys are applied in sequence.

SELECT name
FROM instructor
WHERE dept_name = 'Physics'
ORDER BY name;
SELECT *
FROM instructor
ORDER BY salary DESC, name ASC;

In the second query, salary is the primary sort key, highest first. For equal salaries, name breaks the tie in ascending order.

3.4.5 More WHERE predicates

BETWEEN expresses an inclusive range, equivalent to combining a lower and an upper bound. The source's salary example is:

SELECT name
FROM instructor
WHERE salary BETWEEN 90000 AND 100000;

Equivalent predicate:

WHERE salary >= 90000 AND salary <= 100000

NOT BETWEEN expresses the opposite range test. The source also extends an instructor–teaches query with a department condition:

SELECT name, course_id
FROM instructor, teaches
WHERE instructor.ID = teaches.ID
  AND dept_name = 'Biology';

SQL permits tuple values such as (v1, v2, ..., vn) and tuple comparisons. The source illustrates a compact equality test:

SELECT name, course_id
FROM instructor, teaches
WHERE (instructor.ID, dept_name) = (teaches.ID, 'Biology');

Source notation caveat: tuple ordering

The supplied excerpt calls tuple ordering “lexicographic” but then describes (a1, a2) <= (b1, b2) as requiring both a1 <= b1 and a2 <= b2. Those are different ordering rules. The equality example above is unaffected; for tuple inequality questions, follow the exact convention taught in your course and flag this internal inconsistency in the excerpt.

3.5 · Set operations

UNION, INTERSECT, and EXCEPT

The three operators correspond to mathematical union, intersection, and set difference. For this chapter's example, define c1 as course IDs offered in Fall 2009 and c2 as course IDs offered in Spring 2010.

-- c1: courses offered in Fall 2009
SELECT course_id FROM section
WHERE semester = 'Fall' AND year = 2009;

-- c2: courses offered in Spring 2010
SELECT course_id FROM section
WHERE semester = 'Spring' AND year = 2010;

The source's sample results show c1 containing CS-101, CS-347, and PHY-101; c2 includes CS-101, CS-315, CS-319 twice, FIN-201, HIS-351, and MU-199.

3.5.1 UNION

Find courses offered in Fall 2009 or Spring 2010, or both:

(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
UNION
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

UNION removes duplicates. In the source's result, CS-101 and CS-319 each appear once even when they appear in both inputs or occur in multiple sections.

-- Keep duplicate occurrences
(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
UNION ALL
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

With UNION ALL, occurrences from both inputs are retained and their multiplicities add. If a course appears four times in one input and twice in the other, it appears six times in the combined result.

3.5.2 INTERSECT

Find courses offered in both semesters:

(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
INTERSECT
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

The source's sample result contains CS-101. Ordinary INTERSECT removes duplicates, even if a course has multiple sections in both periods.

-- Retain shared duplicate occurrences
(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
INTERSECT ALL
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

For INTERSECT ALL, the number of copies in the result is the smaller of the two input multiplicities. For example, four copies in one input and two in the other produce two copies.

3.5.3 EXCEPT

Find courses offered in Fall 2009 but not in Spring 2010:

(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
EXCEPT
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

The source's result contains CS-347 and PHY-101. Ordinary EXCEPT eliminates duplicates before performing set difference. Some implementations—Oracle is the example in the source—use MINUS instead of EXCEPT.

-- Retain the positive difference in duplicate counts
(SELECT course_id FROM section
 WHERE semester = 'Fall' AND year = 2009)
EXCEPT ALL
(SELECT course_id FROM section
 WHERE semester = 'Spring' AND year = 2010);

For EXCEPT ALL, the resulting multiplicity is max(count_in_first - count_in_second, 0). If the first input has four copies and the second has two, two remain; if the second count is at least as large, none remain.

Duplicate rule to memorise

UNION ALL adds counts; INTERSECT ALL takes the minimum; EXCEPT ALL subtracts counts but never goes below zero. Without ALL, the set operators remove duplicates.

3.6 · Missing or unknown data

Null values and three-valued logic

A NULL represents a value that may exist but is unknown, or a value that may not exist. It is not the same as zero, an empty string, or an ordinary value.

  • An arithmetic expression involving NULL produces NULL; for example, salary + 5 is NULL for a row whose salary is NULL.
  • A comparison involving NULL generally evaluates to UNKNOWN, not true or false.
  • Use IS NULL and IS NOT NULL to test for nullness.
SELECT name
FROM instructor
WHERE salary IS NULL;

This finds instructors whose salary is recorded as null. A predicate that evaluates to either FALSE or UNKNOWN does not qualify a row for the WHERE result; only TRUE does.

UNKNOWN AND UNKNOWNUNKNOWNNeither value resolves the expression.
TRUE OR UNKNOWNTRUEOne true operand guarantees true.
FALSE OR UNKNOWNUNKNOWNThe unknown operand could make the expression true.
UNKNOWN OR UNKNOWNUNKNOWNThe result cannot be determined.
NOT UNKNOWNUNKNOWNNegation does not reveal the missing value.

For example, when r.A is NULL, both 1 < r.A and NOT (1 < r.A) evaluate to UNKNOWN.

Do not test null using = NULL

The comparison NULL = NULL evaluates to UNKNOWN in a predicate. Use IS NULL instead. Some implementations also provide IS UNKNOWN and IS NOT UNKNOWN to test a comparison's truth value.

For duplicate elimination by SELECT DISTINCT, two rows are treated as identical when corresponding non-null values match and nulls occur in corresponding positions. Thus two rows such as ('A', NULL) are treated as duplicate rows for DISTINCT, even though NULL = NULL is unknown in a predicate. The source says the same treatment applies to UNION, INTERSECT, and EXCEPT.

3.7 · Summarising rows

Aggregate functions, grouping, and HAVING

An aggregate function takes a collection of values and returns one value. SQL's five built-in aggregate functions listed in the source are:

FunctionPurposeInput noted in the source
AVGAverageNumeric values
MINMinimumNumeric or nonnumeric values, such as strings
MAXMaximumNumeric or nonnumeric values, such as strings
SUMTotalNumeric values
COUNTCountRows or values, depending on the expression

3.7.1 Basic aggregation

Average salary in Computer Science:

SELECT AVG(salary) AS avg_salary
FROM instructor
WHERE dept_name = 'Comp. Sci.';

The source example uses salaries $75,000, $65,000, and $92,000, yielding 232000 / 3 = 77333.33 (approximately). AS avg_salary gives the computed result column a meaningful label. The expression returns a query result; it does not modify stored salaries.

Duplicates matter for ordinary aggregation. If a fourth instructor earns $75,000, the correct average is 307000 / 4 = 76750. Removing duplicate salary values first would incorrectly change the calculation.

By contrast, when counting instructors who teach in Spring 2010, each instructor should count once even if they teach multiple sections:

SELECT COUNT(DISTINCT ID)
FROM teaches
WHERE semester = 'Spring' AND year = 2010;

COUNT(*) counts tuples, as in SELECT COUNT(*) FROM course;. The source notes that DISTINCT is not allowed with COUNT(*); DISTINCT may be used with MIN and MAX, although removing duplicates does not change those results. ALL explicitly retains duplicates, but is the default.

3.7.2 Aggregation with GROUP BY

GROUP BY partitions tuples that have the same values for the grouping attributes. The aggregate is then computed separately for each group.

SELECT dept_name, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name;

The supplied sample result is:

Average salary by department in the textbook example
DepartmentAverage salary
Biology72,000
Comp. Sci.77,333
Elec. Eng.80,000

Physics91,000

If GROUP BY is omitted, the whole qualifying relation is treated as one group, so SELECT AVG(salary) FROM instructor; gives one overall average.

To count distinct instructors in each department who taught in Spring 2010, the source joins instructor and teaches, filters by semester/year, and groups by department:

SELECT dept_name, COUNT(DISTINCT ID) AS instr_count
FROM instructor NATURAL JOIN teaches
WHERE semester = 'Spring' AND year = 2010
GROUP BY dept_name;

The source's result lists Comp. Sci. = 3, Finance = 1, History = 1, and Music = 1.

Grouping rule

Every selected attribute that is not inside an aggregate function must appear in the GROUP BY clause. This is erroneous:

SELECT dept_name, ID, AVG(salary)
FROM instructor
GROUP BY dept_name;

A department may contain many IDs, but the query requests one row per department and provides no rule for selecting a unique ID.

3.7.3 Filter groups with HAVING

WHERE filters rows before grouping; HAVING filters groups after grouping and can therefore use aggregate functions.

SELECT dept_name, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name
HAVING AVG(salary) > 42000;

This keeps departments whose average salary is above 42,000. A non-aggregated attribute used in HAVING must also appear in GROUP BY.

Both row filtering and group filtering

For each course section offered in 2009, find the average tot_cred of enrolled students, only if at least two students are enrolled:

SELECT course_id, semester, year, sec_id, AVG(tot_cred)
FROM takes NATURAL JOIN student
WHERE year = 2009
GROUP BY course_id, semester, year, sec_id
HAVING COUNT(ID) >= 2;

The join with section is not needed in this example because takes and student already provide the required information.

3.7.4 Nulls and Boolean aggregates

All aggregate functions except COUNT(*) ignore null input values. Ignoring nulls can leave an empty input collection. For an empty collection, COUNT returns 0, while other aggregate functions return NULL.

The source also notes that SQL:1999 introduced a Boolean type with TRUE, FALSE, and UNKNOWN, plus aggregate functions SOME and EVERY for Boolean collections.

3.8 · Queries inside queries

Nested subqueries

A subquery is a SELECT-FROM-WHERE expression nested inside another query. The source uses subqueries for set membership, set comparison, existence tests, duplicate tests, derived relations, common temporary relations, and single-value expressions.

3.8.1 Set membership: IN and NOT IN

To find courses offered in both Fall 2009 and Spring 2010, check whether each Fall course ID belongs to the set produced by the Spring subquery:

SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2009
  AND course_id IN (
    SELECT course_id
    FROM section
    WHERE semester = 'Spring' AND year = 2010
  );

NOT IN tests absence from the returned set:

SELECT DISTINCT course_id
FROM section
WHERE semester = 'Fall' AND year = 2009
  AND course_id NOT IN (
    SELECT course_id
    FROM section
    WHERE semester = 'Spring' AND year = 2010
  );

The operators can also test membership in a literal list, for example name NOT IN ('Mozart', 'Einstein'). SQL also permits a tuple to be tested against a multi-attribute subquery result. The source's example counts distinct students who took sections taught by instructor ID 10101:

SELECT COUNT(DISTINCT ID)
FROM takes
WHERE (course_id, sec_id, semester, year) IN (
  SELECT course_id, sec_id, semester, year
  FROM teaches
  WHERE teaches.ID = 10101
);

Null caution

Because comparisons involving NULL can yield UNKNOWN, NOT IN can behave unexpectedly if the subquery includes nulls. The section's main purpose is to introduce membership; consider the three-valued logic rules in Section 3.6 when applying it to nullable data.

3.8.2 Set comparison: SOME, ANY, and ALL

> SOME is true if a value is greater than at least one value returned by the subquery. The source example finds instructors whose salary is greater than at least one Biology instructor's salary:

SELECT name
FROM instructor
WHERE salary > SOME (
  SELECT salary
  FROM instructor
  WHERE dept_name = 'Biology'
);

The source says ANY is synonymous with SOME. SQL also permits the other comparison operators with SOME or ALL.

> ALL means the salary must be greater than every salary returned by the Biology subquery:

SELECT name
FROM instructor
WHERE salary > ALL (
  SELECT salary
  FROM instructor
  WHERE dept_name = 'Biology'
);

The source relates these constructs to English: > SOME means “greater than at least one,” while > ALL means “greater than all.” It also notes = SOME is equivalent to IN, and <> ALL is equivalent to NOT IN (subject to SQL's null semantics).

To find departments with the highest average salary, compare each department's average with all department averages:

SELECT dept_name
FROM instructor
GROUP BY dept_name
HAVING AVG(salary) >= ALL (
  SELECT AVG(salary)
  FROM instructor
  GROUP BY dept_name
);

3.8.3 Test for empty relations: EXISTS

EXISTS is true when its subquery returns at least one tuple. The following source example selects courses offered in both Fall 2009 and Spring 2010:

SELECT course_id
FROM section AS S
WHERE semester = 'Fall' AND year = 2009
  AND EXISTS (
    SELECT *
    FROM section AS T
    WHERE semester = 'Spring' AND year = 2010
      AND S.course_id = T.course_id
  );

The inner query refers to S.course_id from the outer query, so this is a correlated subquery. A correlation name may be referenced if it is defined in the current subquery or a containing query; a local definition takes precedence over a same-named outer definition. The source compares this to variable-scope rules in programming languages.

NOT EXISTS tests that the subquery is empty. It can express “for every” conditions by checking that no required item is missing. The source's example finds students who have taken every course offered by Biology:

SELECT DISTINCT S.ID, S.name
FROM student AS S
WHERE NOT EXISTS (
  (SELECT course_id
   FROM course
   WHERE dept_name = 'Biology')
  EXCEPT
  (SELECT T.course_id
   FROM takes AS T
   WHERE S.ID = T.ID)
);

The first inner query returns all Biology courses. The second returns courses taken by the current student. The EXCEPT result is the set of Biology courses not taken by that student. If that difference is empty, NOT EXISTS is true.

Logic pattern: “has taken all”

NOT EXISTS (required set EXCEPT student's set) means there is no required element missing from the student's set. It is a reusable pattern for expressing universal conditions using existence tests and set difference.

3.8.4 Test for duplicates: UNIQUE

The source describes UNIQUE(subquery) as true when the subquery result contains no duplicate tuples, and NOT UNIQUE as a test for duplicate tuples. This construct is noted as not widely implemented.

SELECT T.course_id
FROM course AS T
WHERE UNIQUE (
  SELECT R.course_id
  FROM section AS R
  WHERE T.course_id = R.course_id
    AND R.year = 2009
);

The intended English request is “courses offered at most once in 2009.” An empty subquery also satisfies the uniqueness test, so a course not offered in 2009 is included by the source's stated semantics.

-- Source's intended duplicate test
SELECT T.course_id
FROM course AS T
WHERE NOT UNIQUE (
  SELECT R.course_id
  FROM section AS R
  WHERE T.course_id = R.course_id
    AND R.year = 2009
);

Apparent error in the supplied excerpt

The source prints 1 <= (SELECT COUNT(...)) as an equivalent version of the “offered at most once” query. That condition instead means “offered at least once,” so it is not equivalent to the preceding UNIQUE test. Based on the stated intention, the count condition for at most once would be COUNT(...) <= 1; for at least once it would be COUNT(...) >= 1. This discrepancy is flagged rather than silently reproduced as a valid equivalence.

The source adds a null-related caveat: formally, its uniqueness test compares tuples for equality, and null fields can make tuple equality fail; therefore a uniqueness test may be true even when repeated tuples include null in at least one field.

3.8.5 Subqueries in the FROM clause

A subquery returns a relation, so it can be used anywhere a relation can appear. The source rewrites the “departments with average salary greater than 42,000” request by first computing department averages and then filtering that result:

SELECT dept_name, avg_salary
FROM (
  SELECT dept_name, AVG(salary) AS avg_salary
  FROM instructor
  GROUP BY dept_name
) AS dept_avg
WHERE avg_salary > 42000;

The inner query creates a derived relation with one row per department. The outer query filters its computed avg_salary. The source notes that nested FROM subqueries are supported by most but not all implementations, and that some Oracle versions do not support renaming the derived relation in the shown style.

To find the maximum across departments of each department's total salary:

SELECT MAX(tot_salary)
FROM (
  SELECT dept_name, SUM(salary) AS tot_salary
  FROM instructor
  GROUP BY dept_name
) AS dept_total;

The source also explains that a normal FROM-clause subquery cannot refer to correlation variables from other relations in that same FROM clause. SQL:2003 introduced the LATERAL keyword for a subquery that needs attributes from a preceding relation. Example from the source:

SELECT I1.name, I1.salary, L.avg_salary
FROM instructor AS I1,
LATERAL (
  SELECT AVG(I2.salary) AS avg_salary
  FROM instructor AS I2
  WHERE I2.dept_name = I1.dept_name
) AS L;

This returns each instructor with their salary and their department's average salary. The source notes that only a few implementations (including IBM DB2 at the time of writing) support LATERAL.

3.8.6 The WITH clause

WITH defines a temporary named relation available only to the query that follows. It can make a multi-stage query easier to read.

WITH max_budget(value) AS (
  SELECT MAX(budget)
  FROM department
)
SELECT department.budget
FROM department, max_budget
WHERE department.budget = max_budget.value;

The named relation max_budget contains the maximum department budget, and the outer query selects department rows whose budget equals it.

For departments whose total salary is at least the average of departmental total salaries:

WITH dept_total(dept_name, value) AS (
  SELECT dept_name, SUM(salary)
  FROM instructor
  GROUP BY dept_name
),
dept_total_avg(value) AS (
  SELECT AVG(value)
  FROM dept_total
)
SELECT dept_total.dept_name
FROM dept_total, dept_total_avg
WHERE dept_total.value >= dept_total_avg.value;

The first named relation computes totals by department; the second computes the average of those totals. The final query compares each department total with that average. The source says WITH was introduced in SQL:1999 and is supported by many, but not all, systems.

3.8.7 Scalar subqueries

A scalar subquery is used where a single value is expected. It must return exactly one tuple containing one attribute; if execution returns more than one tuple, a run-time error occurs.

SELECT dept_name,
       (SELECT COUNT(*)
        FROM instructor
        WHERE department.dept_name = instructor.dept_name)
       AS num_instructors
FROM department;

The inner COUNT(*) without GROUP BY returns one value for each outer department reference, including zero when no instructor matches. The example illustrates correlation: the inner query uses department.dept_name from the outer query. The source says scalar subqueries can occur in SELECT, WHERE, and HAVING; they may also be written without an aggregate, but then the one-row condition must still hold when executed.

Self-check questions

1. Why is a primary key both unique and non-NULL?

Uniqueness ensures no two tuples share all primary-key values; non-NULL ensures every tuple has a complete identifying key value.

2. What does DELETE FROM student; preserve that DROP TABLE student; does not?

DELETE preserves the relation and its schema but removes all tuples. DROP TABLE removes the relation’s schema as well as its data.

3. Why can a query on two relations return a huge number of rows?

The FROM clause conceptually forms a Cartesian product. Without a suitable matching predicate, every tuple from one relation is paired with every tuple from the other.

4. Does selecting salary * 1.1 give each instructor a stored raise?

No. It calculates a value for the query result only; it does not change the underlying instructor relation.

5. Why can NATURAL JOIN unexpectedly omit rows?

It matches on every attribute name common to both inputs. If an additional shared name such as dept_name is not intended to be a matching condition, rows with differing values are discarded. Specify the intended key with JOIN ... USING.

6. What is the difference between % and _ in a LIKE pattern?

% matches any substring; _ matches exactly one character. Thus '___' matches exactly three characters and '___%' matches strings of at least three characters.

7. Why can an aggregate query not select an arbitrary ID when grouping only by department?

Multiple IDs may occur within one department group, while the query produces one row per group. Unless the ID is grouped or aggregated, SQL has no unique value to return.

8. Explain > SOME versus > ALL.

> SOME requires the value to exceed at least one value in the subquery result. > ALL requires it to exceed every value returned.

9. How does NOT EXISTS (required EXCEPT taken) express “taken all required courses”?

required EXCEPT taken lists required courses that are missing from the student's set. NOT EXISTS succeeds when that difference contains no rows.

10. What do aggregate functions do with NULL values?

All listed aggregate functions except COUNT(*) ignore null input values. On an empty input collection, COUNT returns 0, while other aggregates return NULL.
