1. What a DBMS is

Definition

A database-management system (DBMS) is a collection of interrelated data and a set of programs to access that data. The data collection is the database, and it holds information relevant to an enterprise.

Primary goal: store and retrieve information in a way that is both convenient and efficient.

A DBMS is built to handle large bodies of information, so it has to do four jobs:

  • Define structures for storing information.
  • Provide mechanisms to manipulate it (see database languages).
  • Keep data safe despite system crashes or unauthorized access (see atomicity and security).
  • Avoid anomalous results when data is shared by several users (see concurrent access).

How user access to databases evolved

  1. Early days: access was indirect, through printed reports (credit card statements) or agents (bank tellers, airline reservation agents).
  2. ATMs and phone interfaces (interactive voice response) gave users direct access.
  3. The Internet revolution of the late 1990s sharply increased direct access. Phone interfaces became Web interfaces, so browsing a bookstore, placing an order, checking a bank balance, or being shown ads all read from or write to a database.

Industry note from the source: vendors such as Oracle are among the largest software companies, and databases are an important product line for Microsoft and IBM.

3. Why DBMSs exist: problems with file-processing systems

Intuition. In the 1960s, organizations kept data in operating-system files, with a separate application program for each task (add students, register for courses, compute GPAs). Every new need (a new major, a new rule) added more files and more programs. Over time, the data ended up scattered across many files, and rules were duplicated in many programs.

Summary of the seven disadvantages

ProblemCore ideaSource example
Data redundancy and inconsistencySame data duplicated in several files; copies may stop agreeing. Costs extra storage and access time.Double-major student's address in both the Music and Mathematics files; address updated in one only.
Difficulty in accessing dataUnanticipated requests have no ready program; the choices are manual extraction or writing a new program each time.Clerk wants students in one postal-code area, then only those with at least 60 credit hours.
Data isolationData scattered across files in different formats makes new programs hard to write.-
Integrity problemsConsistency constraints are buried in application code; adding one means changing many programs, and it is worse when a constraint spans several files.Department account balance may never fall below zero.
Atomicity problemsAfter a failure, data must return to a consistent state. A multi-step operation must happen entirely or not at all.Transfer of $500 from department A to B.
Concurrent-access anomaliesSimultaneous updates can corrupt data; uncoordinated programs make supervision hard.Two debits on a $10,000 balance; two registrations on a count of 39.
Security problemsNot every user should see all data; ad hoc programs make restrictions hard to enforce.Payroll staff need financial data only, not academic records.

Atomicity in detail

Transfer $500 from A to B involves a debit and a credit. If the system fails in between, A has lost $500 that B never received, which is an inconsistent state. The transfer must be atomic: both happen or neither happens.

Concurrent-access anomalies in detail

Each program does read old value, compute, write back. If two run at the same time, one update overwrites the other (a lost update).

Example A: two clerks debit department A (balance $10,000) by $500 and $100
StepClerk 1 (debit 500)Clerk 2 (debit 100)Stored balance
1reads 10,000reads 10,00010,000
2computes 9,500, writes9,500
3computes 9,900, writes9,900

The correct result is $9,400. Depending on which write is last, the balance is $9,500 or $9,900.

Example B: course registration limit

The program reads the count, checks it is under the limit, adds one, and writes it back. With the count at 39, two students both read 39 and both write 40. The count rises by only 1 although it should be 41. If the limit is 40, both registrations succeed and the limit is violated.

Why files cannot fix this

Supervision is hard because many independently written programs access the same data without coordination. A DBMS centralizes that control.

Key takeaway

These seven problems (redundancy and inconsistency, access difficulty, isolation, integrity, atomicity, concurrency, security) are the reasons database systems were developed. This is a standard exam list, so memorize all seven.

4. View of data

A major purpose of a database system is to give users an abstract view of the data, hiding how it is stored and maintained. Efficiency demands complex data structures, but many users are not computer trained, so the complexity is hidden through levels of abstraction.

4.1 Three levels of abstraction

LevelDescribesWho works here
Physical (lowest)How data is actually stored: complex low-level data structures in detail. A record is a block of consecutive storage locations.Hidden from most programmers; database administrators may know some details.
LogicalWhat data is stored and what relationships exist among it. The entire database in terms of a small number of relatively simple structures.Database administrators (deciding what to keep) and programmers.
View (highest)Only part of the database. Several views can exist for the same database. Also acts as a security mechanism.End users via application programs.
Physical data independence

The logical-level user need not know how simple logical structures are implemented physically. Applications are physically data independent if they do not depend on the physical schema and so need not be rewritten when it changes (see schemas).

4.2 Analogy: programming-language types

A record type defines fields with names and types. The source's example:

type instructor = record
    ID        : char(5);
    name      : char(20);
    dept_name : char(20);
    salary    : numeric(8,2);
end;

Other record types in the university example: department (dept_name, building, budget), course (course_id, title, dept_name, credits), student (ID, name, dept_name, tot_cred).

  • Physical: a record is a block of consecutive storage locations. The compiler hides this from programmers, just as the DBMS does for database programmers.
  • Logical: each record is described by a type definition, and the relationships among record types are defined. Programmers and DBAs work here.
  • View: users see application programs that hide data-type details. Views also restrict access. For example, registrar clerks see student information but not instructors' salaries.

Source footnote: the actual declaration depends on the language. C and C++ use struct; Java has no such declaration, but a simple class gives the same effect.

5. Instances and schemas

Definitions

Instance: the collection of information stored in the database at a particular moment. It changes as data is inserted and deleted.

Schema: the overall design of the database. It changes infrequently, if at all.

Programming analogy: the schema is like variable declarations with their type definitions, and the instance is the values of those variables at one instant.

SchemaLevelNotes
Physical schemaPhysicalHidden beneath the logical schema; can usually be changed easily without affecting applications.
Logical schemaLogicalBy far the most important, since programmers build applications on it.
SubschemasViewSeveral may exist, each describing a different view.
Exam point

Physical data independence holds when applications do not depend on the physical schema, so a physical change forces no rewrite. This is possible because the physical schema sits beneath the logical schema, which is what programs use.

6. Data models

Definition

A data model is a collection of conceptual tools for describing data, data relationships, data semantics, and consistency constraints. It can describe a design at the physical, logical, and view levels.

ModelKey ideasNotes
RelationalA collection of tables (also called relations) represents both data and relationships. Each column has a unique name. Columns correspond to the attributes of a record type; rows are records of that type.A record-based model: fixed-format records of several types, each with a fixed number of fields. Most widely used; most current systems are relational (Chapters 2–8).
Entity-Relationship (E-R)Basic objects called entities and relationships among them. An entity is a "thing" in the real world, distinguishable from other objects.Widely used in database design (Chapter 7).
Object-basedExtends the E-R model with encapsulation, methods (functions), and object identity. The object-relational model combines object-oriented and relational features.Motivated by object-oriented programming (Java, C++, C#). Chapter 22.

Historical models: the network and hierarchical models preceded the relational model. They were tied closely to the implementation and complicated data modeling, so they are now used little, mainly in old code still in service (outlined in the source's online Appendices D and E).

7. Database languages

A database system provides a data-definition language (DDL) to specify the schema and a data-manipulation language (DML) to express queries and updates. In practice they are not separate languages but parts of one, such as SQL.

7.1 Data-manipulation language (DML)

A DML lets users access or manipulate data as organized by the data model. The four kinds of access are:

  1. Retrieval
  2. Insertion
  3. Deletion
  4. Modification
TypeUser specifiesTrade-off
Procedural DMLWhat data is needed and how to get it.Harder to learn and use.
Declarative (nonprocedural) DMLWhat data is needed, without saying how.Easier to learn and use, but the database system must figure out an efficient access method.
Query and query language

A query is a statement requesting retrieval of information. The part of a DML that does retrieval is the query language. Technically incorrect but common practice: "query language" and "DML" are used as synonyms.

SQL is the most widely used query language (Chapters 3–5); other languages are in Chapter 6.

7.2 Abstraction applies to manipulation too

At the physical level, algorithms must give efficient access. At higher levels, the emphasis is ease of use. The query processor (Chapters 12 and 13) translates DML queries into sequences of physical-level actions.

7.3 Data-definition language (DDL)

A DDL specifies the database schema through a set of definitions, and also specifies additional properties of the data. A special type of DDL, the data storage and definition language, defines the storage structure and access methods. These implementation details of the schemas are usually hidden from users.

Consistency constraints

Stored data must satisfy consistency constraints (for example, a department balance must never be negative). The DDL lets you specify them, and the system checks them every time the database is updated. A constraint can in general be an arbitrary predicate, but arbitrary predicates may be costly to test. So systems implement integrity constraints that can be tested with minimal overhead:

ConstraintMeaningSource example
Domain constraintEvery attribute has a domain of possible values (integer, character, date/time types). Declaring the domain restricts the values. The most elementary integrity constraint, tested easily on every new data item.-
Referential integrityA value appearing in certain attributes of one relation must also appear in certain attributes of another. Modifications can violate it; the normal procedure is to reject the action that caused the violation.dept_name in a course record must appear in dept_name of some department record.
AssertionAny condition the database must always satisfy. Domain and referential constraints are special forms of assertions. When created, the system tests it for validity; later modifications are allowed only if they do not violate it."Every department must have at least five courses offered every semester."
AuthorizationDifferentiates users by the type of access allowed on data. A user may have all, none, or a combination of the types below.See list below.
Four authorization types

Read: read but not modify. Insert: insert new data but not modify existing data. Update: modify but not delete. Delete: delete data.

Output of the DDL: the data dictionary

Like any language, the DDL takes statements as input and produces output. Its output is placed in the data dictionary, which contains metadata (data about data). The dictionary is a special table that only the database system itself can access and update, not a regular user. The system consults the data dictionary before reading or modifying actual data.

Key takeaway

DDL defines structure and rules and writes them into the data dictionary. DML then works on the data, and the system checks the dictionary and constraints on every operation. Referential integrity reappears in the relational model, and authorization is one job of the authorization and integrity manager.

8.2 Data manipulation in SQL

SQL is nonprocedural. A query takes one or more tables as input and always returns a single table.

Query 1: names of all instructors in the History department.

select instructor.name
from   instructor
where  instructor.dept_name = 'History';

Clause by clause: from names the input table; where keeps rows whose dept_name is History; select shows only the name attribute. The result is a one-column table labeled name:

Query 2 (more than one table): ID and department name of all instructors in a department with budget greater than $95,000.

from   instructor, department
where  instructor.dept_name = department.dept_name
  and  department.budget > 95000;

8.3 Data definition in SQL

create table department
  (dept_name char(20),
   building  char(15),
   budget    numeric(12,2));

This creates department with three typed columns. It also updates the data dictionary, and the schema of a table is itself an example of metadata (see DDL). Data types are covered in Chapter 3.

8.4 Database access from application programs

SQL is not as powerful as a universal Turing machine: some computations a general-purpose language can do are impossible in SQL. SQL also has no user input, display output, or network communication. These must be written in a host language (C, C++, Java) with embedded SQL. Such application programs include registration, class rosters, GPA calculation, and payroll checks. There are two ways to run DML from the host language:

9. Database design

Databases support the operations of an enterprise whose end product may be information or a service for which the database is only a supporting part. Database design mainly means designing the schema; complete application design needs a broader set of issues (Chapter 9). This text first focuses on writing queries and designing schemas.

9.1 Design process

  1. Requirements: characterize fully the data needs of prospective users, working extensively with domain experts and users. The outcome is a specification of user requirements.
  2. Conceptual design: choose a (high-level) data model and translate the requirements into a conceptual schema. The designer checks that all requirements are satisfied and non-conflicting, and removes redundant features. The focus is on data and relationships, not physical storage.
  3. Logical design: map the conceptual schema onto the implementation data model of the chosen DBMS.
  4. Physical design: specify physical features such as file organization and internal storage structures.

In relational terms, conceptual design decides what attributes to capture (a business decision) and how to group them into tables (a computer-science problem). There are two ways to do the "how": the E-R model or normalization (algorithms that take all attributes and generate tables). A full conceptual schema also indicates functional requirements: the kinds of operations (transactions) to be performed, such as updating, searching, and deleting data.

9.2 Running example: a university

  • Department: unique dept_name, building, budget. Course: course_id, title, dept_name, credits, possibly prerequisites.
  • Instructor: unique ID, name, dept_name, salary. Student: unique ID, name, major dept_name, tot_cred.
  • Classroom: building, room number, capacity. Section (class): identified by course_id, sec_id, year, semester; also building, room number, time slot id.
  • Teaching assignments: which sections each instructor teaches. Registrations: which courses and sections each student has taken.

9.3 The entity-relationship (E-R) model

The E-R model uses entities (a real-world "thing" distinguishable from others, such as a person or a bank account) and relationships among them.

  • Entities are described by attributes. For example, dept_name, building, budget describe the department entity set; ID, name, salary describe the instructor entity set.
  • The extra attribute ID uniquely identifies an instructor, since two instructors may share a name and salary. (In the U.S., organizations often use the social-security number.)
  • A relationship is an association among several entities (for example, member associates an instructor with a department). The set of all entities of one type is an entity set; the set of all relationships of one type is a relationship set.

The E-R model also represents constraints, notably mapping cardinalities: how many entities another entity can be associated with via a relationship set. For example, if each instructor must be associated with a single department, the E-R model can express this. Detail is in Chapter 7.

Source footnote: dept_name is deliberately left out of the instructor entity set's attributes here; this is not an error, and Chapter 7 explains why.

9.4 Normalization

The goal is a set of relation schemas that store information without unnecessary redundancy yet allow easy retrieval. The approach is to design schemas in an appropriate normal form, which requires extra information about the enterprise, most commonly functional dependencies (Section 8.4 of the source).

Exam point: two bad-design symptoms

(1) Repetition of information. (2) Inability to represent certain information. Two ways to design a relational schema: the E-R model, or normalization.

10. Data storage and querying

A database system is partitioned into modules, broadly the storage manager and the query processor.

Why the storage manager matters

Corporate databases range from hundreds of gigabytes to terabytes. (A gigabyte is about 1000 megabytes, actually 1024, or about 1 billion bytes; a terabyte is about 1 million megabytes, or 1 trillion bytes.) Main memory cannot hold this, so data lives on disk and is moved to memory as needed. Disk movement is slow relative to the CPU, so the system must structure data to minimize disk-memory movement.

Why the query processor matters

It lets users work at the view level without understanding physical details, while getting good performance. The system translates updates and queries written in a nonprocedural language at the logical level into an efficient sequence of physical-level operations (see levels of abstraction).

10.1 Storage manager

The component providing the interface between low-level stored data and the application programs and queries. It interacts with the file manager, translates DML statements into low-level file-system commands, and is thus responsible for storing, retrieving and updating data. Raw data sits on disk using the operating system's file system.

Storage manager componentJob
Authorization and integrity managerTests integrity constraints; checks user authority to access data (see DDL).
Transaction managerKeeps the database consistent despite failures; makes concurrent transactions proceed without conflict (see transactions).
File managerManages disk space allocation and the data structures representing on-disk information.
Buffer managerFetches data from disk into main memory and decides what to cache. Critical because it lets the database handle data much larger than main memory.

Physical data structures implemented: data files (store the database); the data dictionary (metadata, especially the schema); indices (fast access to items with a particular value, like a textbook index, for example finding an instructor by ID or by name). Hashing is an alternative to indexing, faster in some but not all cases. (Storage and buffer management: Chapter 10; indexing and hashing: Chapter 11.)

10.2 Query processor

  1. DDL interpreter: interprets DDL statements and records the definitions in the data dictionary.
  2. DML compiler: translates DML statements into an evaluation plan of low-level instructions. A query usually has several alternative plans with the same result, and the compiler performs query optimization: it picks the lowest-cost plan.
  3. Query evaluation engine: executes the low-level instructions from the DML compiler.

Query evaluation is Chapter 12; optimization is Chapter 13.

11. Transaction management

Often several operations form one logical unit of work. In the funds transfer from earlier (atomicity problem), account A is debited and B credited. Three requirements follow:

PropertyMeaningIn the funds transfer
AtomicityAll-or-none: the transfer happens entirely or not at all.Either both debit and credit occur, or neither.
ConsistencyThe database's correctness is preserved.The sum of the balances of A and B is preserved.
DurabilityAfter success, the new values persist despite system failure.New balances of A and B survive a crash.
Transaction

A collection of operations that performs a single logical function in a database application. Each transaction is a unit of both atomicity and consistency. If the database was consistent when it started, it must be consistent when it successfully ends. During execution, temporary inconsistency may be necessary (the debit or credit must come first), which is dangerous if a failure occurs.

  • Programmer's responsibility: define transactions so each preserves consistency. If the transfer is split into two separate programs (debit A, credit B), running them one after the other preserves consistency, but each alone does not move the database from one consistent state to another, so they are not transactions.
  • Atomicity and durability are the job of the recovery manager. Without failures, atomicity is easy. After a failure, the failed transaction must have no effect: the system performs failure recovery (detects failures and restores the state before the failure).
  • Concurrent transactions can break consistency even if each is correct (see the lost-update example). The concurrency-control manager controls their interaction.
  • The transaction manager = concurrency-control manager + recovery manager.

Transactions began in financial applications but are now also used in real-time telecommunication and in long-duration activities such as product design and administrative workflows. (Chapters 14, 15, 16, and 26.)

Key takeaway

Atomicity, consistency and durability are the requirements. Recovery manager: atomicity and durability. Concurrency-control manager: correct interaction of concurrent transactions. Programmer: defining transactions so each preserves consistency.

12. Database architecture

Architecture is strongly influenced by the underlying computer system. Systems can be centralized or client-server (one server machine does work for many clients), can exploit parallel computer architectures, or can be distributed, spanning multiple geographically separated machines. Distributed issues include how to store data, atomicity of multi-site transactions, concurrency control, and high availability (Chapters 17–19). Most users connect through a network, so we distinguish client machines (remote users) from server machines (where the DBMS runs).

13. Data mining and information retrieval

Data mining

The process of semiautomatically analyzing large databases to find useful patterns. It is like knowledge discovery in AI (machine learning) or statistical analysis, but differs in dealing with large volumes of data stored primarily on disk ("knowledge discovery in databases").

  • Rules: for example, "Young women with annual incomes greater than $50,000 are the most likely people to buy small sports cars." Such rules are not universally true; they have degrees of support and confidence. Knowledge can also be equations relating variables, or other mechanisms for predicting outcomes.
  • Semiautomatic: a manual part (preprocessing data, postprocessing patterns to find novel ones, choosing useful pattern types) surrounds the automatic mining. The text concentrates on the automatic part (Chapter 20).

Decision support and data warehouses

Businesses use online data to decide what to stock and how to target customers. Many queries are complicated and some information cannot be extracted even with SQL. Tools let analysts view data in different ways or precompute summaries for fast responses, and the SQL standard has extra constructs for analysis. Large companies with diverse data sources build data warehouses, which gather data from multiple sources under a unified schema at a single site, giving one uniform interface.

Information retrieval

Information retrieval is the querying of unstructured textual data, unlike the rigidly structured data of relational databases. It shares storage and retrieval on secondary storage with databases, but emphasizes keyword queries, relevance of documents, and analysis, classification and indexing of documents (Chapters 20 and 21).

14. Specialty databases

Some application areas are limited by the relational model's restrictions, so other models were developed (see data models).

  • Object-based: extends the E-R model with encapsulation, methods and object identity. Key object-oriented concepts used in data modeling are inheritance, object identity and encapsulation (information hiding, with methods as the interface). It supports a rich type system, including structured and collection types. Several systems based on it appeared in the 1980s. Major vendors now support the object-relational model, which extends the relational model with structured and collection types and object orientation (Chapter 22).
  • Semistructured: items of the same type may have different attributes. XML was designed to add markup to text documents but became important for data exchange; it represents nested structures flexibly, useful for nontraditional data (Chapter 23).

15.2 The database administrator (DBA)

A main reason for using a DBMS is central control of both the data and the programs that access it. The person with that control is the DBA. Functions:

  • Schema definition: create the original schema by executing DDL statements.
  • Storage structure and access-method definition.
  • Schema and physical-organization modification to reflect changing needs or improve performance.
  • Granting authorization for data access; the information is kept in a special structure the system consults on every access attempt (see authorization).
  • Routine maintenance: periodic backups (to tape or remote servers, protecting against disasters such as flooding); ensuring enough free disk space and upgrading it; monitoring running jobs so expensive tasks do not degrade performance.

16. History of database systems

Data processing predates computers: punched cards (Herman Hollerith) recorded U.S. census data early in the twentieth century and were later used to enter data into computers. The theme running through the history below: freedom from sequential access, then from low-level implementation details.

PeriodDevelopments
1950s – early 1960sMagnetic tapes for storage; payroll automated. Tapes and card decks could be read only sequentially, and data far exceeded memory, so programs had to process data in a particular order by reading and merging. Example: salary raises on punched cards were merged, in the same sorted order, with the master tape to write a new master tape.
Late 1960s – 1970sHard disks allowed direct access (any location in tens of milliseconds): data freed "from the tyranny of sequentiality." Network and hierarchical databases stored lists and trees on disk. Codd (1970) defined the relational model and nonprocedural querying; he later won the ACM Turing Award.
1980sRelational databases were initially seen as slower than network/hierarchical ones. System R (IBM Research) developed techniques for efficient relational systems and led to IBM's SQL/DS; Ingres (UC Berkeley) led to a product of the same name. Early commercial systems (DB2, Oracle, Ingres, DEC Rdb) advanced declarative query processing. By the early 1980s they were performance-competitive and replaced network/hierarchical systems because programmers there had to handle low-level details and code procedural queries with efficiency in mind. Relational has reigned since. Parallel and distributed database research and initial object-oriented work also began.
Early 1990sSQL was designed for query-intensive decision support, but 1980s databases were mainly update-intensive transaction processing. Decision support re-emerged; data-analysis tools grew; vendors added parallel and object-relational support.
1990sWeb explosion: very high transaction rates, high reliability, 24×7 availability (no downtime for scheduled maintenance), and Web interfaces.
2000sXML and XQuery; relational still the core of most large applications. Auto-admin techniques; growth of open-source systems (PostgreSQL, MySQL). Later: column-stores (each column stored as a separate array), highly parallel analysis systems, distributed storage for very large Web sites (Amazon, Facebook, Google, Microsoft, Yahoo!), streaming data management (stock tickers, network monitoring), and widely deployed data mining (recommendations, ad placement).

The source cites Codd [1970], Astrahan et al. [1976] and Chamberlin et al. [1981] for System R overviews.

17. Recap and self-check

Conceptual recap

A DBMS stores interrelated data plus the programs to access it. It exists because file-processing systems suffer from seven problems. It hides complexity through three abstraction levels, whose separation gives physical data independence. The schema (design) is stable while the instance (contents) changes. A data model supplies the tools to describe the design, and a declarative DML such as SQL lets users state what they want while the system decides how. The DDL records structure and constraints in the data dictionary. Relational databases store data in tables queried with SQL. Design proceeds from requirements to conceptual, logical and physical schemas, using the E-R model or normalization to avoid repetition and inability to represent information. Internally, the query processor (DDL interpreter, DML compiler with optimizer, evaluation engine) sits on the storage manager (authorization and integrity, transaction, file and buffer managers). Transactions must be atomic, consistent and durable. Applications run as two-tier or three-tier systems, used by naive users, application programmers, sophisticated users and specialized users, and overseen by the DBA.

Common misconceptions

Schema vs instance: the schema is the design; the instance is the data at one moment. Logical vs view level: the logical level describes the whole database, while a view describes only part of it. Query language vs DML: technically a query language is only the retrieval part of DML, though the terms are used interchangeably.

Self-check

1. List the seven disadvantages of file-processing systems.

Redundancy and inconsistency; difficulty in accessing data; data isolation; integrity problems; atomicity problems; concurrent-access anomalies; security problems.

2. Two clerks debit $500 and $100 from $10,000 at the same time. What can go wrong?

Both read $10,000. The final balance becomes $9,500 or $9,900 depending on the last write, instead of the correct $9,400.

3. Which level does a database administrator mainly use, and why can the physical schema change without rewriting programs?

The logical level. Programs depend on the logical schema, not the physical one, which gives physical data independence.

4. Procedural vs declarative DML?

Procedural: specify what is needed and how to get it. Declarative: specify only what is needed, and the system chooses an efficient access method.

5. What distinguishes the semistructured model from the others?

Items of the same type may have different sets of attributes. XML is the usual representation.

6. Name the four integrity-related constraint types in the DDL and the four authorization types.

Domain constraints, referential integrity, assertions, authorization. Authorization types: read, insert, update, delete.

7. What is the data dictionary, and who can access it?

A special table of metadata (data about data), such as table schemas. Only the database system itself reads and updates it; the system consults it before reading or modifying data.

8. Why is the single faculty table a bad design?

Repetition of information (for example, History's building and budget twice, so updates must change every row) and inability to represent a department that has no instructors, unless nulls are used, which are difficult to handle.

9. State the transaction requirements and who ensures them.

Atomicity, consistency, durability. The recovery manager ensures atomicity and durability; the concurrency-control manager controls concurrent transactions; the programmer defines transactions so each preserves consistency.

10. Compare two-tier and three-tier architectures.

Two-tier: the client application calls the database server directly. Three-tier: the client is a front end that talks to an application server holding the business logic, which talks to the database. Three-tier suits large and Web applications.

11. What does the DML compiler do besides translating DML?

It performs query optimization, choosing the lowest-cost evaluation plan among alternatives that give the same result.
