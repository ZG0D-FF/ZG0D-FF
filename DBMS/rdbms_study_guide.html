Practice Exercise 2.1 — Appropriate primary keys for employee, works, company, manages

Question: Consider the relational database of Figure 2.14 (employee, works, company, manages). What are the appropriate primary keys?

  • employee (person_name, street, city): person_name. In this relation schema, person_name serves as the unique identifier for each individual employee record.
  • works (person_name, company_name, salary): person_name. Assuming that each person works for at most one company, person_name uniquely identifies their employment details.
  • company (company_name, city): company_name. The company name uniquely distinguishes each company row.
  • manages (person_name, manager_name): person_name. Assuming each employee has at most one direct manager, person_name uniquely identifies their management relationship record.
Practice Exercise 2.2 — Foreign key violation examples (dept_name → department)

Question: Consider the foreign key constraint from dept_name in instructor referencing department. Give examples of inserts and deletes that cause a violation.

A foreign key constraint requires that any value appearing in foreign key attributes of a referencing table must exist in the primary key of the referenced table.

  1. Insert Violation: Attempting to insert a new instructor tuple with dept_name = 'Astronomy' into instructor when 'Astronomy' does not exist in the department table.
  2. Delete Violation: Attempting to delete the department tuple 'Comp. Sci.' from department when instructor records in instructor still reference 'Comp. Sci.'.
Practice Exercise 2.3 — Why day and start_time are part of the primary key

Question: In the time_slot relation, explain why day and start_time are part of the primary key, while end_time is not.

  • Why day and start_time are included: A single time slot identifier (such as slot 'A') can meet on multiple days of the week (e.g., Monday and Wednesday). Therefore, time_slot_id alone cannot uniquely distinguish individual class meetings. Adding day and start_time guarantees uniqueness for every meeting instance.
  • Why end_time is excluded: A primary key must be a minimal candidate key with no redundant attributes. Once time_slot_id, day, and start_time are fixed, the end_time is determined and does not add any candidate key uniqueness.
Practice Exercise 2.4 — Does no two instructors sharing a name make name a key?

Question: In Figure 2.1, no two instructors have the same name. Can we conclude that name is a superkey or primary key of instructor?

Answer: No.

Explanation: A key is a property of the entire relation schema that must hold for all possible valid states of the database over time, not just a single snapshot. Even if no two instructors share a name in a sample figure, two instructors in the real world could eventually share the same name.

Practice Exercise 2.5 — σ(s_id = ID)(student × advisor)

Question: What is the result of:

σs_id = ID(student × advisor)

Code Breakdown:

  1. student × advisor: Performs a Cartesian product, pairing every single student tuple with every single advisor tuple.
  2. σs_id = ID(...): Performs a Selection, filtering the combined pairs to retain only rows where the student's ID matches the s_id in advisor.

Result: This pairs each student with their assigned advisor, effectively executing an inner join.

Practice Exercise 2.6 — Relational algebra code explanations (a, b, c)

(a) σyear ≥ 2009(takes) ⋈ student

  • σyear ≥ 2009(takes): Selection operator (σ) filters rows from the takes table where year is 2009 or later.
  • ⋈ student: Natural Join operator (⋈) merges those filtered takes tuples with matching rows from student based on the common attribute ID.

Plain English: Retrieves all student information paired with course section details for courses taken in or after 2009.

(b) σyear ≥ 2009(takes ⋈ student)

  • takes ⋈ student: First performs a natural join between takes and student on ID.
  • σyear ≥ 2009(...): Filters the joined relation to keep only records where year ≥ 2009.

Plain English: Produces the exact same result as part (a): student details for courses taken in or after 2009.

(c) ΠID, name, course_id(student ⋈ takes)

  • student ⋈ takes: Joins student records with course records on ID.
  • ΠID, name, course_id(...): Projection operator (Π) keeps only the three specified columns (ID, name, course_id) and removes duplicate rows.

Plain English: Returns a list of student IDs, student names, and course IDs taken.

(a) Names of all employees who live in city "Miami"

Πperson_name(σcity = 'Miami'(employee))

  1. σcity = 'Miami'(employee): Filters employee rows where city equals 'Miami'.

(b) Names of all employees whose salary is greater than $100,000

Πperson_name(σsalary > 100000(works))

  1. σsalary > 100000(works): Selects works tuples with salary > 100000.
  2. Πperson_name(...): Outputs the person_name attribute.

(c) Names of employees who live in "Miami" and earn > $100,000

Πperson_name(σcity = 'Miami'(employee) ⋈ σsalary > 100000(works))

  1. σcity = 'Miami'(employee): Selects Miami residents.
  2. σsalary > 100000(works): Selects high earners.
  3. ⋈: Natural joins both subsets on the common attribute person_name.
  4. Πperson_name(...): Extracts employee names.

Exercise 2.10 — Can s_id remain the primary key with multiple advisors?

Question: In advisor(s_id, i_id), if a student can have multiple advisors, can s_id remain the primary key?

Answer: No.

Explanation: If a student has multiple advisors, s_id will repeat across rows and can no longer uniquely identify a tuple. The new primary key must be the composite key (s_id, i_id).

Exercise 2.11 — Relation vs. relation schema

Question: Difference between relation and relation schema.

  • Relation Schema: The static blueprint or logical design of the table (analogous to a programming type definition), specifying attribute names and domains.
  • Relation (Instance): The actual contents or rows of the table at a specific moment in time, which changes whenever data is inserted, updated, or deleted.

Exercise 2.15 — Procedural vs. nonprocedural languages

Question: Discuss the relative merits of procedural and nonprocedural languages.

  • Procedural Languages (e.g., Relational Algebra): The user explicitly specifies the exact sequence of algebraic operations to compute the desired result.
  • Nonprocedural Languages (e.g., Relational Calculus / SQL): The user declaratively states what data is needed without specifying a step-by-step algorithm, allowing the database query optimizer freedom to choose execution plans.

Review Questions

Question 5.1 — Definitions (Domain, Attribute, Tuple, Schema, State, Degree)
  • Domain: A named set of indivisible (atomic) values defined by a data type and format.
  • Attribute: A column header representing a named role played by a domain in a relation schema.
  • n-tuple: An ordered list of n values <v1, v2, …, vn> where each value belongs to the corresponding attribute domain or is NULL.
  • Relation Schema: R(A1, A2, …, An), consisting of relation name R and a list of attributes Ai.
  • Relation State: r(R), a finite set of n-tuples representing a valid real-world state at a specific point in time.
  • Degree (Arity): The total number of attributes n in a relation schema.
  • Relational Database Schema: S = {R1, R2, …, Rm} along with a set of integrity constraints IC.
  • Relational Database State: DB = {r1, r2, …, rm}, a set of relation states satisfying all integrity constraints in IC.
Question 5.2 — Why tuples are not ordered

A relation is formally defined as a mathematical set of tuples. Elements of a set have no natural order among them.

Question 5.3 — Why duplicate tuples are not allowed

By definition, all elements of a mathematical set are distinct. Since a relation is a set of tuples, duplicate tuples are prohibited.

Question 5.4 — Key vs. superkey
  • Superkey: Any set of attributes that uniquely identifies every tuple in a relation state.
  • Key: A minimal superkey — a superkey from which no attribute can be removed without destroying its uniqueness property.
Question 5.5 — Why designate a primary key

To serve as the official, principal identifier for tuples in a table and to be referenced by foreign keys in other relations.

Question 5.6 — Characteristics of relations vs. ordinary tables/files
  1. Tuples are strictly unordered.
  2. Attribute values within tuples must be atomic (First Normal Form).
  3. Duplicate tuples are strictly prohibited.
  4. Values are restricted to defined atomic domains or NULL.
  5. Facts about entities and relationships are represented uniformly as relations.
Question 5.7 — Reasons leading to NULL values
  1. Value exists, but is unknown.
  2. Value exists, but is currently unavailable or unrecorded.
  3. Attribute does not apply to this tuple (value undefined/inapplicable).
Question 5.8 — Entity integrity vs. referential integrity
  • Entity Integrity: No primary key attribute can be NULL. Crucial because primary keys uniquely identify tuples.
  • Referential Integrity: Foreign key values must either match an existing primary key value in the referenced relation or be NULL. Crucial for maintaining consistent references across tables.
Question 5.9 — Foreign key definition and purpose

A set of attributes FK in a referencing relation R1 whose values must match the primary key PK of a referenced relation R2 or be NULL. Used to establish and enforce relationships between records across tables.

Question 5.10 — Transaction vs. Update operation
  • Transaction: An executing program comprising multiple database operations (reads, updates) that forms an atomic unit of work, leaving the database in a consistent state.
  • Update Operation: A single modification action (Insert, Delete, or Update) executed on a relation.

Exercise 5.20 — Surrogate keys vs. natural keys

(a) Natural Keys: Email address or (First_name, Last_name, Date_of_birth).

(b) Name Changes: Natural key attributes like last names can change; updating requires cascading updates across referencing tables.

  • Disadvantages: Artificial value with no real-world semantic context, requiring secondary unique constraints on natural attributes.

Entity-Relationship (ER) Modeling: Phased Database Design

In the broader context of Entity-Relationship (ER) modeling, designing a database for complex real-world applications requires a systematic, multi-phase approach. Rather than directly creating tables or writing database code, designers follow structured design phases to separate conceptual user requirements from technical and storage details.

1. Requirements Collection and Analysis

  • Data Requirements: The database designer interacts extensively with prospective users and domain experts to document the enterprise's data needs. The outcome is a concise, detailed textual specification of user data requirements.
  • Functional Requirements: In parallel, designers analyze the user operations and transactions (retrievals, updates, searches, and deletes) that will run against the database.

2. Conceptual Design (The Core Role of the ER Model)

  • High-Level Abstraction: The designer translates the textual requirements into a conceptual schema using a high-level conceptual data model — most commonly the Entity-Relationship (ER) model.
  • Structural Specifications: The ER schema formally defines entity types, attributes, relationship types, and structural constraints (such as cardinalities and participation rules).
  • DBMS-Independent Blueprint: The conceptual design ignores implementation details, commercial software specifics, and physical storage structures. This makes the resulting ER diagram a clear communication tool between database designers and nontechnical stakeholders.
  • Functional Alignment: Designers review the conceptual ER schema against the functional requirements to confirm that all required user transactions can be executed smoothly.

3. Logical Design (Data Model Mapping)

  • Mapping to Implementation Models: Once the conceptual schema is finalized, it is transformed from the high-level ER model into the implementation data model of the chosen commercial DBMS.
  • Relational Schema Generation: In relational database systems, this step consists of algorithmically mapping ER constructs (strong entity sets, weak entities, multivalued attributes, and relationships) into relational table schemas, primary keys, and foreign-key constraints.

4. Physical Design

  • Internal Storage & Performance: The system-specific relational schema is mapped to physical file organizations, index structures, access paths, and internal storage parameters.
  • Transaction Implementation: In parallel with physical design, application programs and database transactions are designed and coded.

Key Pitfalls Avoided by Phased ER Modeling

  • Redundancy: Developing a clear ER model first prevents repeating identical attributes unnecessarily across multiple tables, which avoids data inconsistency.
  • Incompleteness: Early ER modeling prevents missing vital real-world concepts, ensuring the database does not require awkward NULL workarounds to represent basic data.
  • Costly Late-Stage Changes: Modifying a physical or logical database schema after application code has already been written is difficult and expensive; conceptual ER modeling catches architectural errors early.
