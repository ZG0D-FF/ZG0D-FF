01

Overview of the design process

Start with what the enterprise needs to remember, not with tables or storage details.

A database application involves more than its schema. It also needs programs that access and update data and a security scheme that controls access. Users’ needs guide the design. The E–R model provides a high-level conceptual framework for describing the data and how items are connected before the design is mapped to a relational database.

The five connected stages

STAGE 1User requirementsWork with users and domain experts to identify required data.
STAGE 2Conceptual designChoose a model; describe entities, attributes, relationships and constraints.
REVIEWValidate the schemaCheck completeness, conflicts and redundant features; consider operations.
STAGE 3Logical designMap the conceptual model to the implementation model, typically relational.
STAGE 4Physical designSpecify file organisation, index structures and other physical features.

Notice the separation of concerns: conceptual design captures meaning; logical design expresses it in the chosen data model; physical design chooses how the system stores and accesses it.

Conceptual schema

What data means

It describes the enterprise in a user-understandable way: entities, their attributes, relationships and constraints. An E–R diagram commonly records this phase.

Functional requirements

What users do

Users also describe transactions, such as inserting or modifying data, retrieving particular data, and deleting data. The designer checks whether the schema supports these operations.

Why careful design matters: after an application is built, physical-schema changes are usually easier than logical-schema changes. A logical change may force edits to many queries and updates embedded across application code, so the logical design deserves particular care.

Two design pitfalls

Redundancy

The same fact is stored repeatedly. If every course offering stores the course title, a title change can leave different offerings with inconsistent titles. Ideally, each fact appears in one appropriate place.

University example: store a course’s title once with the course entity, rather than repeating it in every section.

Incompleteness

The design cannot represent an important real-world state. If course information exists only inside course offerings, a course that has not yet been offered cannot be recorded without inventing section details or using unsuitable nulls.

Design lesson: model course separately from section.

Even after these pitfalls are avoided, more than one sensible design may be possible. For example, a product sale can be represented as a relationship between a customer and a product, or as a separate sale entity connected to each. The best choice depends on which facts the enterprise needs to represent.

02

The Entity–Relationship model

Three core ideas: entity sets, relationship sets and attributes.

The Entity–Relationship (E–R) model supports conceptual database design by representing the overall logical structure of an enterprise. It provides a way to map real-world meanings and interactions into a schema that can later be translated into relation schemas.

Entity and entity set

Entity

A distinguishable thing

An entity is a real-world object or “thing” distinguishable from all other objects. It may be concrete, such as a person or book, or abstract, such as a course, course offering or flight reservation.

Entity set

A type or collection

An entity set contains entities of the same type that share the same attributes. Examples include instructor, student, course and department.

The entity set is the modeled type; its extension is the actual collection of entities currently belonging to that type. This distinction parallels a relation schema versus a relation instance.

Entity sets need not be disjoint. A person in a university may be an instructor, a student, both, or neither. The model therefore need not assume that membership in different sets is mutually exclusive.

Attributes identify and describe entities

An entity is described by the values of its attributes. For example, an instructor may have ID, name, dept name and salary. A course may have course id, title, dept name and credits.

An identifying attribute must distinguish one entity from others in the same set. Since two instructors may share a name, a uniquely assigned instructor ID is a more reliable identifier.

Relationship and relationship set

A relationship is an association among two or more entities. A relationship set is a set of relationships of the same type. For instance, advisor associates instructors with students, while takes associates students with course sections.

If E₁, E₂, …, Eₙ are entity sets, a relationship set R is a subset of
{ (e₁, e₂, …, eₙ) | e₁ ∈ E₁, e₂ ∈ E₂, …, eₙ ∈ Eₙ }, with n ≥ 2.

The entity sets that appear in a relationship participate in that relationship set. A single association of particular named entities is a relationship instance. For example, instructor Katz (ID 45565) advising student Shankar (ID 12345) is one instance of advisor.

Roles, recursive relationships and relationship attributes

A role is the function an entity plays in a relationship. Roles are often obvious when the participating entity sets differ, but explicit role names are important when the same entity set participates more than once.

Recursive example: prereq

The entity set course participates twice: one role is the course that requires a prerequisite (course_id), and the other is the prerequisite course (prereq_id). The ordered pair (C1, C2) means “C2 is a prerequisite for C1”; reversing the pair changes the meaning.

A relationship may have descriptive attributes. In advisor, date can record when the instructor became the student’s advisor. In takes, grade describes the student’s result for a particular section; an attribute such as credit may distinguish taking a class for credit from auditing it.

Important constraint: a relationship instance must be uniquely identifiable from its participating entities, not by relying on descriptive attributes. If the same instructor–student pair needs multiple advising dates, do not create indistinguishable duplicate relationship instances; model date as multivalued, as described in the source.

More than one relationship set may connect the same entity sets. For example, advisor and dept advisor may both connect instructors and students while capturing different meanings.

Relationship degree: binary and ternary

The degree of a relationship set is the number of participating entity sets. A binary relationship has degree 2; a ternary relationship has degree 3.

Binary

takes

student ↔ section: records which sections a student takes.

Ternary

proj guide

instructor, student and project together record which instructor guides which student on a specific project. A binary student–instructor relationship alone cannot express project-specific guidance.

03

Attribute types

Attributes describe entities or relationships; their type determines how values should be interpreted.

Each attribute has a permitted set of values called its domain (or value set). For example, the domain of semester may be {Fall, Winter, Spring, Summer}. Formally, an attribute maps an entity set to a domain. An entity can be described by its attribute–value pairs; for example, an instructor might have (ID, 76766), (name, Crick), (dept name, Biology) and (salary, 72000).

Attribute typeMeaningExample from the chapter
SimpleCannot usefully be divided into subattributes.salary, credits
CompositeCan be divided into meaningful components; components can themselves form a hierarchy.name → first name, middle initial, last name; address → street, city, state, postal code
Single-valuedHas one value for a particular entity.A student’s ID
MultivaluedMay have a set of values for one entity; the notation encloses it in braces.{phone number}, {dependent name}
DerivedComputed from other attributes or related entities rather than stored as an independent value.age derived from date of birth and current date; students advised derived by counting related students
Base / storedA stored value from which a derived value can be computed.date of birth is the base attribute for age

Composite attributes are useful when users sometimes need the whole value and at other times need individual components. A street component can itself be broken into street number, street name and apartment number. Multivalued attributes can also have bounds: a university might record between zero and two phone numbers per instructor.

What does NULL mean?

A null value can mean different things, and these meanings should not be conflated:

  • Not applicable: the value does not exist for this entity, such as an apartment number for an address without an apartment.
  • Missing: the value exists, but the database does not contain it. A missing instructor name is assumed to be this kind of case because every instructor must have a name.
  • Unknown existence or value: we do not know the value, or do not know whether the value exists at all. For example, a null apartment number might mean that it is unknown whether the address has an apartment number.
04

Constraints in the E–R model

Constraints specify which database states are allowed.

The chapter focuses on mapping cardinalities and participation constraints. Together, they express how many entities may or must take part in a relationship.

Mapping cardinalities for binary relationships

For a binary relationship between entity sets A and B, the mapping cardinality describes the maximum number of entities on one side that can be associated with a single entity on the other side.

1 : 1

One-to-one

An entity in A is associated with at most one entity in B, and an entity in B with at most one in A.

1 : N

One-to-many

An entity in A may be associated with zero or more entities in B; each entity in B is associated with at most one in A.

N : 1

Many-to-one

An entity in A is associated with at most one entity in B; an entity in B may be associated with zero or more entities in A.

M : N

Many-to-many

Entities on both sides may be associated with zero or more entities on the other side.

Advisor example: if each student can have only one instructor as an advisor while an instructor can advise several students, advisor is one-to-many from instructor to student. If students can be jointly advised by multiple instructors, the relationship is many-to-many.

Participation: total versus partial

Total participation

Every entity must participate

Every entity in the set appears in at least one relationship instance. In the stated university example, every student is expected to have an advisor, so student participation in advisor is total.

Partial participation

Some entities may not participate

Only some entities in the set need to appear in the relationship. An instructor may advise no students, so instructor participation in advisor can be partial.

Cardinality gives an upper bound or ratio; participation tells whether involvement is compulsory. Do not treat “at most one” as equivalent to “exactly one.”

Reading cardinality limits

A line may carry a minimum–maximum constraint written l..h:

NotationInterpretation
1..1At least one and at most one: exactly one.
0..*Zero or more; no upper limit is specified.
1..*One or more; participation is mandatory, with no fixed maximum.

In the chapter’s advisor example, the student edge is marked 1..1, so each student must have exactly one advisor; the instructor edge is 0..*, so an instructor may advise no students or many. Interpreting the edges backwards reverses the intended constraint.

05

Keys in entity and relationship sets

Keys provide the formal way to distinguish modeled objects and associations.

Entity-set keys

Although entities are conceptually distinct, the database must express their distinction through attribute values. No two entities in one entity set may have identical values for all attributes.

Superkey

A set of attributes that uniquely identifies every entity in the entity set.

Candidate key

A minimal attribute set sufficient to identify every entity.

Primary key

The candidate key selected as the main identifier for the entity set.

These definitions carry over from relation schemas to entity sets. In E–R diagrams, primary-key attributes are underlined.

Keys for relationship sets

Suppose relationship set R connects entity sets E₁, E₂, …, Eₙ. Write PK(Eᵢ) for the primary-key attributes of entity set Eᵢ.

K = PK(E₁) ∪ PK(E₂) ∪ … ∪ PK(Eₙ)

The union of participating entity primary keys forms a superkey for the relationship set. The source also gives the relationship-descriptive-attribute form as:

K′ = PK(E₁) ∪ … ∪ PK(Eₙ) ∪ {a₁, a₂, …, aₘ}

When primary-key attribute names overlap across entity sets, distinguish them by qualifying with the entity-set name. In a recursive relationship, use the role name to keep the participating key attributes distinct.

How cardinality affects the chosen primary key

Advisor relationship rulePrimary key of advisor
Many-to-many between instructor and studentUnion of instructor PK and student PK.
Each student has at most one instructor (many-to-one from student to instructor)Student PK alone is sufficient.
Each instructor is associated with at most one student (many-to-one from instructor to student)Instructor PK alone is sufficient.
One-to-oneEither participating entity’s candidate key can be used.

For a nonbinary relationship with no cardinality constraints, the union of all participating entity primary keys is the candidate key and is selected as primary key. The source notes that choosing keys for nonbinary relationships with cardinality constraints is more involved.

06

Removing redundant attributes

Represent an association as a relationship when it conveys a relationship between modeled things.

After entity sets and attributes are selected, relationship sets may make some attributes redundant. The E–R design should not keep the same connecting fact both as an entity attribute and as a separate relationship, unless there is a clear reason for doing so.

Example A: instructor and department

Suppose instructor initially has ID, name, dept name, and salary; department has dept name, building, and budget. If inst dept models the association between them, the department name in instructor is redundant in the E–R representation because it is already the key of the related department entity.

Using a relationship rather than embedding the department name makes the connection explicit and avoids prematurely assuming that every instructor is associated with at most one department. During relational mapping, dept name may be added back to the instructor relation if each instructor has at most one associated department; if multiple departments are possible, the association is recorded in a separate relation.

Example B: section and time slot

A section may initially list course id, sec id, semester, year, building, room number and time slot id, with (course id, sec id, year, semester) as its key. A time slot is identified by time slot id and has a multivalued composite meeting attribute containing (day, start time, end time). When sec time slot connects section to time slot, the repeated time slot id is redundant in the E–R entity set section.

Example C: section and classroom

If classroom is identified by (building, room number) and has capacity, then the same building and room-number attributes are redundant in section once sec class represents the association between a section and a classroom.

Design rule: first model entities and relationships clearly. Then remove attributes that merely duplicate information already captured by those relationships. The later relational mapping may reintroduce foreign-key attributes where the mapping rules require them.

Learn the symbol system, then read the constraints attached to it.

Relationship attributes in a diagram

Roles and nonbinary cardinality

In a recursive relationship, line labels identify the roles played by the same entity set. For prereq, the roles may be labeled course_id and prereq_id.

For a ternary relationship such as proj guide, an arrow pointing to instructor can express that a student has at most one instructor guiding them on a given project. The chapter permits at most one arrow out of a nonbinary relationship set because multiple arrows can be interpreted in two different ways: either one combination on one side determines a combination on the other side, or every other-side combination determines at most one entity at each arrowed set. The source reserves the precise distinction for the treatment of functional dependencies in Chapter 8.

08

Weak entity sets

When an entity cannot be uniquely identified without its owner, use the owner’s key plus a discriminator.

A strong entity set has enough attributes to form a primary key. A weak entity set does not. It depends on an identifying (or owner) entity set, and each weak entity must be associated with an owner to exist in the modeled enterprise.

Why section can be modeled as weak

Initially, a section can be identified by course id, sec id, year and semester. If we remove course id as a standalone attribute so that the association to course is expressed by sec course, then sec id, year and semester alone are not globally unique: sections of different courses may share those values. The relationship to the owning course supplies the missing identifying information.

Weak-entity vocabulary and rules

TermMeaning in the chapter
Owner / identifying entity setThe strong entity set on which the weak entity depends; here, course.
Identifying relationshipThe relationship connecting weak entity to owner; here, sec course.
Discriminator / partial keyAttributes that distinguish weak entities belonging to the same owner; here, (sec id, year, semester).
Weak entity primary keyOwner’s primary key together with the weak entity’s discriminator.
  • The identifying relationship is many-to-one from weak entity to identifying entity.
  • Weak-entity participation in the identifying relationship is total: every section must be related to a course.
  • The identifying relationship should not have descriptive attributes; such attributes can instead be associated with the weak entity set.
  • In E–R notation, a weak entity uses a double rectangle; the identifying relationship uses a double diamond; the discriminator is underlined with a dashed line.

Even if sec id were made globally unique, a section would still be conceptually dependent on a course. The weak-entity representation makes that existence dependence explicit.

When is an attribute a better model than a weak entity?

A weak entity may instead be represented as a multivalued composite attribute of its owner when it participates only in the identifying relationship and has few attributes. A weak entity set is usually more suitable when it has several attributes or participates in additional relationships. The chapter treats section as a weak entity because it also participates in relationships such as sec time slot.

A weak entity can itself own another weak entity, and it may have more than one identifying entity set. In that case, its primary key consists of the union of the primary keys of all identifying entity sets plus its discriminator.

09

Putting the university E–R model together

Read the schema as a connected model, not as a list of isolated tables.

The chapter’s final university design gathers the entity sets, relationships and additional constraints into one conceptual view. Section is treated as a weak entity, and the diagram expresses several total-participation and at-most-one constraints.

Constraints explicitly described in the chapter’s final model

  • Each instructor must be associated with exactly one department: total instructor participation in inst dept, and an at-most-one constraint toward department.
  • Course and student participate totally in course dept and stud dept, respectively, as described for the final diagram.
  • Section participates totally in sec time slot and is also modeled as a weak entity identified through sec course.
  • takes has the descriptive attribute grade.
  • Each student has at most one advisor in the final figure’s stated constraints.
  • The section discriminator is (sec id, semester, year); its identifying relationship is sec course, which connects it to the strong entity set course.

Exam revision map

High-yield definitions, distinctions and self-checks.

Entity vs entity setAn entity is one distinguishable object; an entity set groups entities of the same type. The extension is the current collection of members.
Relationship vs relationship setA relationship is one association among entities; a relationship set collects associations of the same type.
Cardinality vs participationCardinality constrains the number of associations; participation says whether involvement is mandatory.
Composite vs multivaluedComposite means one value has components; multivalued means one entity may have several values of an attribute.
Stored vs derivedA stored/base value is kept; a derived value is calculated from other values or relationships.
Strong vs weak entityA strong entity set has a primary key of its own; a weak entity needs its owner’s key plus a discriminator.
Redundancy vs incompletenessRedundancy repeats facts and risks inconsistency; incompleteness prevents representing some valid enterprise states.
Conceptual vs logical vs physicalConceptual captures meaning, logical maps to the implementation model, and physical specifies storage and access structures.

Self-check questions

1. Why should course and section be separate entity sets?

Separating them avoids repeating course facts for every offering and lets the database represent a course even when it has not yet been offered.

2. How does a ternary relationship add meaning that binary relationships may lose?

proj guide associates instructor, student and project in one combination, recording which instructor guides which student on a particular project. Separate student–instructor links would not capture the project-specific context by themselves.

3. What is the difference between “at most one” and “exactly one”?

“At most one” permits zero or one association. “Exactly one” requires at least one and at most one; it combines a maximum of one with mandatory participation.

4. Why is section weak in the final E–R model?

The section discriminator (sec id, semester, year) identifies a section only within a course. The course key is required as part of the full key, and every section depends on its owning course.

5. Why can a department name be removed from instructor in the E–R design but reappear in a relational schema?

The E–R relationship inst dept already represents the association. During relational mapping, the department key may be stored with instructor as a foreign-key attribute when each instructor has at most one department; if multiple departments are allowed, a separate relation can represent the association.

6. What are three different meanings of NULL in this discussion?

Not applicable, a value that exists but is missing, and an unknown value or unknown existence of a value.

One-line chapter logic: understand requirements → model entity sets and relationships → assign attributes and keys → express cardinality and participation → remove redundant attributes → read the complete E–R diagram → map the validated conceptual schema to relations.
